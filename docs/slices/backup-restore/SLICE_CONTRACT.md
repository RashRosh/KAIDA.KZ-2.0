# Slice Contract — R2: Backup и restore базы данных и фото (локально, изолированно)

**Статус: подход утверждён PO 2026-10-07 с уточнениями §11.** Контракт-PR; реализация — после его merge. Часть Local readiness track (`EXECUTION_PLAN.md`, решение PO 2026-10-07); продолжение R1 (`v0.0.62`), база — `v0.0.63-d0-e2e-marker-fix`.
Рекомендуемый reasoning effort реализации: **high** (данные, потеря данных, секреты/ПД, согласованность).

## 1. Цель

Оператор может сделать резервную копию установки KAIDA (PostgreSQL + файлы фото Offer) как **один согласованный набор** и восстановить её в **чистое окружение**, получив доказательства, достаточные, чтобы доверять результату. Всё локально, воспроизводимо, без платной инфраструктуры.

## 2. Что показало чтение кода (основа решений)

- Фото = строки `photos` / `offer_photos` в БД + файлы `<PHOTO_STORAGE_DIR>/<id[0:2]>/<id>.{display,thumb}.webp`. Других постоянных файлов у приложения нет.
- Инварианты хранилища (`offer-photos`, `upload-photo.ts`, `photo-storage.ts`): **файлы пишутся раньше строки в БД**; запись атомарна (tmp + rename); **файлы неизменяемы и не удаляются** (очистки нет). Следствие: каталог фото только растёт, лишние файлы допустимы (сироты), строка без файла — нет.
- Секреты и конфигурация (`.env`) вне БД и фото. **Проверено по коду** (зависимости от секретов):
  - **Сессии** (`crypto/session-token.ts`): в БД хранится `sha256(токен)` без секрета; токен случаен. **Смена `IDENTITY_OTP_HMAC_SECRET_HEX` сессии НЕ инвалидирует** — восстановленная копия принимает старые cookie до `expires_at`.
  - **OTP-challenges** (`crypto/otp.ts`): `otp_digest = HMAC(секрет, id, телефон, код)`. При другом секрете ещё не использованные challenges (TTL по умолчанию 300 с) проверить нельзя — вход запрашивается заново; то же для contact-verification.
  - **Валидный секрет обязателен:** без `IDENTITY_OTP_HMAC_SECRET_HEX` (64 hex) вход недоступен (R1: `503 AUTH_UNAVAILABLE`).
  - **VAPID** (`reminders.config.ts`, `web-push-sender.ts`): push включён только при трёх переменных (иначе job не стартует, кнопка скрыта). В БД лежат `endpoint/p256dh/auth` подписок; браузерная подписка привязана к публичному ключу, с которым создана. Код удаляет подписку только на ответ 404/410, прочие ошибки — `failed`. **Не проверено запуском (поведение внешних push-сервисов):** что при другом VAPID-ключе доставка отклоняется — это ожидание по спецификации Web Push, не факт.
  - `INTERNAL_JOB_SECRET` защищает только ручной запуск reminder-job; зависимостей данных нет.
  - **Следствие для безопасности:** восстановленная БД содержит действующие сессии — владелец старого cookie остаётся авторизованным в копии. Отзыва сессий в R2 нет (вне scope); записывается в runbook.
- Dump БД содержит ПД (телефоны), сессии, события поиска, push-подписки.

## 3. Решение (предлагается)

### 3.1 Формат backup — один каталог

```
kaida-backup-<UTC-время>/
  manifest.json   # пишется ПОСЛЕДНИМ; его наличие = backup завершён
  db.dump         # pg_dump -Fc (custom format), снимок одной транзакцией
  photos/         # копия каталога фото с той же раскладкой (без *.tmp)
  SHA256SUMS      # sha256 db.dump и каждого файла фото
```

`manifest.json`: версия формата, UTC-время, git SHA приложения, число применённых миграций и хеш последней, версия PostgreSQL, число строк по таблицам, число/размер файлов фото, sha256 dump. **Без секретов, без значений конфигурации, без текста запросов.**

Каталог backup создаётся только новым (существующий → отказ) и **вне рабочей копии репозитория** (внутри → отказ). Dump делает `pg_dump` внутри контейнера БД (`docker exec`): версия клиента совпадает с сервером, PostgreSQL на хосте не нужен.

### 3.2 Согласованность (механизм, не заявление)

Остановка записи **не требуется** — работают порядок и проверка, опирающиеся на инварианты §2:

1. `pg_dump` — один снимок (MVCC); всё, что он видит, зафиксировано на момент T.
2. **После** dump копируются фото. Любое фото, на которое ссылается снимок, записано на диск до T, не удалялось и не менялось → копия его содержит.
3. Проверка в конце: для каждой строки `photos` **из самого dump** есть оба файла в копии; иначе backup **падает** и manifest не пишется. Фото, загруженные между T и копированием, — сироты в наборе (безвредно, учитываются в manifest).

Ограничение: механизм верен, пока фото неизменяемы и не удаляются. Любой будущий slice «очистка/удаление/замена фото» **обязан** пересмотреть R2 (STOP-условие для того slice).
Альтернатива (не рекомендуется): остановить приложение на время копирования — проще, но даёт простой и при инвариантах не нужна.

### 3.3 Restore

Только в **пустую** цель: БД без пользовательских таблиц (чистая, создана заранее) и **несуществующий или пустой** каталог фото. Порядок: **preflight** (проверка bundle: manifest, версия формата, checksum, совпадение файлов с manifest; проверка цели и guards) → **выполнение** (`pg_restore` в контейнер цели → копия фото) → verify.
- **Preflight-отказ:** невалидный bundle или небезопасная/непустая цель отклоняются **до любого изменения** цели и источника; код выхода 2, цель не тронута.
- **Runtime-сбой** (после начала мутации: обрыв `pg_restore`, нет места, ошибка копирования, verify не прошёл): одноразовая цель **может остаться частично восстановленной**. Инструмент оставляет в цели маркер `restore-incomplete`, печатает «NOT READY», выходит с кодом 3 и **никогда** не сообщает «OK/ready» (готовность — только после успешного verify). Повторный restore в такую цель отклоняется preflight («цель непустая»).
- **Безопасная очистка и повтор:** по runbook оператор удаляет **только** цель по точным именам (контейнер/том/БД цели и её каталог фото), создаёт новую пустую цель и повторяет restore из того же bundle. Источник и bundle при restore только читаются, несвязанные ресурсы не затрагиваются; guard не даёт целью быть источнику. Флага перезаписи **нет**; непустая цель → отказ с объяснением (оператор сам создаёт новую цель). Неудавшийся restore не помечается успешным; цель остаётся «неполной» и пересоздаётся оператором.

Миграции повторно не запускаются: dump несёт схему и `drizzle.__drizzle_migrations`; приложение должно соответствовать migration-хешу из manifest (несовпадение → отказ, §3.4).

### 3.4 Неполные и несовпадающие компоненты

Каждый случай — **preflight-отказ** (код 2, понятное сообщение, цель не тронута): нет `manifest.json` (backup не завершён) · нет `db.dump` или `photos/` · файл фото отсутствует/лишний относительно manifest · checksum не совпал · версия формата новее поддерживаемой · миграции приложения ≠ manifest · цель непустая · цель — dev-стек · каталог backup внутри репозитория.

### 3.5 Изоляция (guards, как в R1 `isolation.ts`, общие для backup и restore)

Отказ до любых действий, если БД — порт `5432`, база `kaida` / `kaida_test`, контейнер/проект dev-стека, или каталог фото = `.data/photos` рабочей копии либо внутри неё. Приёмочные окружения: отдельный compose-проект `kaida-r2-check` с **двумя** контейнерами PostgreSQL (source и restore; свои тома и порты, напр. 55433 / 55434), отдельные каталоги фото во временном каталоге ОС, отдельные порты приложения (напр. 3201 / 3202). Backup самого dev-стека в R2 **не** поддерживается (вне scope; отдельное решение).

### 3.6 Конфигурация и секреты — отдельно

В backup **не входят** `.env` и секреты. Runbook содержит отдельную таблицу: что нужно восстановленному окружению (обязательные/необязательные переменные), что в backup, чего нет. **Подтверждённые последствия** — по §2 (сессии переживают смену HMAC-секрета; незавершённые OTP-challenges — нет; без секрета вход недоступен; сессии в копии действуют). **Неподтверждённое помечается в runbook явно** (поведение push-сервисов при другом VAPID-ключе). Хранение секретов и шифрование backup вне scope; backup содержит ПД и действующие сессии и хранится как конфиденциальный (не в Git, не в evidence).

### 3.7 Операторский workflow (`docs/ops/BACKUP_RESTORE.md`)

1. `pnpm backup:create -- --db-container <имя> --photos <каталог> --out <новый каталог вне репозитория>`
2. Поднять чистую цель: пустая БД, пустой каталог фото, `.env` с собственными секретами.
3. `pnpm backup:restore -- --bundle <каталог> --db-container <цель> --photos <пустой каталог>` (внутри — проверки §3.3–3.5 и verify).
4. Запустить приложение на цели, проверить вход и фото (команды и ожидаемое — в runbook).
5. Очистка одноразовых ресурсов по точным именам.

Форма: небольшие `tsx`-CLI в `ops/backup-restore/` + общий guard-модуль; не более трёх команд в `package.json` (`backup:create`, `backup:restore`, `backup:verify` — последняя только читает restored-цель).

## 4. Scope / вне scope

**В scope:** CLI backup / restore / verify, guards, manifest и checksums, одноразовый compose `kaida-r2-check`, runbook, ссылка в README, проверка восстановленного приложения, отчёт прогона, unit-тесты чистых функций (guards, manifest, сравнение) в обычном наборе.

**Вне scope:** платный хостинг, cloud/off-site backup, расписание, retention/ротация, шифрование и управление секретами, point-in-time recovery/WAL, backup dev-стека, перезапись существующей цели (replace), очистка сирот-фото, S3-хранилище фото, перенос между версиями приложения/PostgreSQL, AI, UX/UI, изменение продуктового поведения, схемы БД и миграций.

## 5. Закрытые contracts

Не пересматриваются, только читаются: `offer-photos` (инварианты хранилища — основа §3.2); `local-bootstrap-verification` (compose-паттерн, guards, runbook; smoke не изменяется); identity/auth (секреты); `actuality-reminders` (VAPID, push-подписки); S15C/D0 (`search_events` входят в dump, `origin` сохраняется); `production-kb-importer` (восстановленная БД уже содержит KB, повторный импорт не нужен). Нарушение закрытого поведения в прогоне → STOP и отчёт, не молчаливое исправление.

## 6. Risk flags

**Фактические:** infrastructure / **data safety** (случайно затронуть dev-БД/фото; перезаписать цель) — главный; **concurrency / consistency** (БД + фото, §3.2); **secrets** (вне backup, §3.6); **privacy** (dump с телефонами и сессиями); **data loss** (restore неверных данных — поэтому non-destructive defaults).
**Не затрагиваются:** DB schema / migrations, public API, auth-логика, внешний сервис, UX/UI, AI.

## 7. Acceptance criteria

1. **Guards:** backup и restore отказывают до любых действий для dev-стека (порт 5432, `kaida` / `kaida_test`, `.data/photos`, каталог backup внутри репозитория); отказы проверены.
2. **Bundle:** backup создаёт новый каталог с `db.dump`, `photos/`, `SHA256SUMS`, `manifest.json` (последним); существующий каталог → отказ; в manifest нет секретов.
3. **Согласованность:** dump раньше копии фото; backup падает без manifest, если фото из снимка отсутствует в копии; детерминированный тест «загрузка между dump и копией» даёт валидный набор (максимум — сироты).
4. **Restore только в пустую цель:** непустая БД или непустой каталог фото → preflight-отказ без изменений; флага перезаписи нет. **Runtime-сбой** (смоделированный) оставляет цель помеченной `restore-incomplete`, выводит «NOT READY», код 3, никогда «OK»; очистка и повтор по runbook на новой цели проходят, источник не затронут.
5. **Неполные/несовпадающие компоненты** (§3.4): каждый случай → preflight-отказ (код 2) без изменения цели; все случаи проверены.
6. **Verify после restore:** число строк по таблицам = manifest; каждая ссылка на фото имеет оба файла с совпавшим sha256; сироты перечислены как INFO.
7. **Восстановленное приложение** (чистое окружение, **другой** HMAC-секрет): вход продавца новым test OTP; старая сессия источника продолжает действовать (подтверждает §2, записывается как факт); продавец видит свои Offers; покупатель находит Offer поиском; фото отдаётся `200 image/webp` побайтно идентично исходному.
8. **Runbook** `docs/ops/BACKUP_RESTORE.md` и README: команды (POSIX и PowerShell), отдельная таблица конфигурации/секретов с подтверждёнными последствиями и явно помеченными непроверенными, очистка и повтор после runtime-сбоя, пределы доказательств; без значений секретов.
9. **Очистка и неизменность dev-стека:** одноразовые контейнеры, тома и каталоги удалены по точным именам; контейнер, том, порт 5432 и число файлов `.data/photos` до/после — без изменений.
10. Branch CI `KAIDA verify` зелёный; продуктовый код, схема и миграции не менялись; находки перечислены, продуктовые не исправлены молча.

## 8. Verification (агентская; не входит в ручные шаги PO)

Прогон на машине PO (Windows, Git Bash, Docker Desktop): source-стек → R1 smoke как **генератор данных** (продавец, 2 Offer, фото) → backup → негативные сценарии §3.4 → restore в чистую цель → verify (§7.6) → проверка приложения (§7.7) → очистка. Отчёт: SHA, версии, команды, время, результаты проверок и счётчики, доказательства очистки и неизменности dev-стека.

Явно «не проверено», если не выполнялось: PowerShell и Linux; backup при интенсивной параллельной записи (только детерминированный тест + прогон без нагрузки); совместимость между версиями PostgreSQL/приложения; объёмы больше smoke-набора.

### Переиспользование R1 smoke

- **Как генератор данных на source — да, без изменений** (`KAIDA_SMOKE_PORT`; guard пропускает порт ≠ 5432; создаёт продавца, точку, 2 Offer, фото).
- **На restored — нет:** smoke проверяет чистый каталог и создаёт данные. Нужна маленькая **read-only** проверка `ops/backup-restore/restored.spec.ts` (порядка 40 строк) с копией ~30-строчного Playwright-конфига и существующими helpers `tests/e2e`. Это не новый фреймворк.

## 9. Manual acceptance (PO)

**Разделение ролей.** Технические команды, управление изолированными окружениями и очистку выполняет **агент**; интеграционные проверки и тесты отказов — агентская верификация (§8). PO проверяет только поведение продавца и покупателя в браузере размера телефона:

1. Агент поднимает окружение-источник и передаёт PO адрес приложения (порт 3201).
2. PO входит продавцом (тестовый код), создаёт карточку **с фото**.
3. Агент выполняет backup и restore в чистое окружение и передаёт PO адрес восстановленного приложения (порт 3202).
4. PO в восстановленной копии: карточка продавца на месте, фото отображается.
5. PO ищет товар как покупатель: карточка находится, фото видно в выдаче и на странице карточки.
6. PO сообщает «принято» / «не принято» и замечания; агент выполняет очистку и передаёт отчёт (список ресурсов пуст, dev-среда не тронута).

PO принимает: карточка и фото видны в восстановленной копии; поиск и отображение изображения работают.

## 10. STOP conditions

Необходимость подключиться к dev-БД/фото; секрет оказался в Git-файле, bundle, manifest или логах; нужно изменить схему, миграции или продуктовый код; обнаружено, что фото удаляются или изменяются (инвариант §3.2 неверен); восстановленное приложение нарушает закрытое поведение.

## 11. Решения PO (приняты 2026-10-07)

Приняты: (1) механизм «снимок БД → затем копия фото → проверка ссылок» без остановки записи — на подтверждённых правилах неизменяемых файлов (§2); (2) небольшие скрипты с общими guards и тремя командами; (3) секреты вне bundle; (4) restore только в пустую цель; (5) backup dev-стека исключён.

Уточнения PO: **(a)** ручная приёмка — только поведение продавца/покупателя (§9), всё техническое делает агент; **(b)** различать preflight-отказ и runtime-сбой, документировать безопасную очистку и повтор (§3.3); **(c)** зависимости от секретов проверять по коду, подтверждённое отделять от непроверенного (§2, §3.6).
