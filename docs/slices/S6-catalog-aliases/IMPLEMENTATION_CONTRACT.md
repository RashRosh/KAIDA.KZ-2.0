## 5. Authoritative normalized-key expression

Use exactly:

```sql
normalize(
  casefold(
    normalize(btrim(value), NFC)
      COLLATE pg_catalog.pg_unicode_fast
  ),
  NFC
) COLLATE pg_catalog.pg_unicode_fast
```

Logical contract:

```text
btrim
→ NFC
→ Unicode full case folding under pg_catalog.pg_unicode_fast
→ NFC
```

`value` is substituted with:

- incoming resolver term;
- `products.name`;
- `product_aliases.name`.

Do not implement an independent JavaScript normalization engine.

PostgreSQL 18 is authoritative for equality semantics.

Do not rely on database default collation.

Do not create or use libc fallback semantics.

No custom collation is required. The required built-in collation is:

```text
pg_catalog.pg_unicode_fast
provider = builtin
locale = PG_UNICODE_FAST
deterministic = true
```

If required PostgreSQL 18 UTF8 semantics are unavailable, migration/runtime verification must fail rather than silently degrade.

## 6. Normalization non-features

Normalization must not:

- collapse internal whitespace;
- remove punctuation;
- map `е` and `ё` together;
- transliterate;
- strip accents beyond NFC canonical equivalence;
- stem words;
- tokenize phrases;
- use LIKE/ILIKE contains matching;
- fuzzy-match;
- use AI/embeddings.

Approved examples:

```text
БАРАНИНА == баранина
   Баранина   == баранина
й == и + combining breve
е != ё
мясо барана != мясо  барана
баранина != баранина!
```

## 7. Canonical Product uniqueness

Migration `0006` must add normalized canonical uniqueness using the approved expression.

Required semantics:

```sql
CREATE UNIQUE INDEX products_name_normalized_unique
ON products (
  (
    normalize(
      casefold(
        normalize(btrim(name), NFC)
          COLLATE pg_catalog.pg_unicode_fast
      ),
      NFC
    ) COLLATE pg_catalog.pg_unicode_fast
  )
);
```

Equivalent formatting generated by PostgreSQL/Drizzle is acceptable only if runtime semantics are identical.

The existing S0 exact `UNIQUE(name)` remains. Do not remove it merely because the normalized index is stronger.

## 8. Alias uniqueness

S6 must reject duplicate normalized alias rows for the same Product but allow the same normalized alias for different Products.

Required logical index:

```sql
CREATE UNIQUE INDEX product_aliases_name_product_normalized_unique
ON product_aliases (
  (
    normalize(
      casefold(
        normalize(btrim(name), NFC)
          COLLATE pg_catalog.pg_unicode_fast
      ),
      NFC
    ) COLLATE pg_catalog.pg_unicode_fast
  ),
  product_id
);
```

Therefore:

```text
alias X → Product A
alias X → Product A
```

is invalid, while:

```text
alias X → Product A
alias X → Product B
```

is valid and intentionally represents ambiguity.

Do not add global `UNIQUE(normalized_alias)`.

## 9. Resolver API contract

Add one Catalog-owned application resolver.

Conceptual result type:

```text
resolved(Product)
not_found
ambiguous
```

Resolver is the single Product-term resolution contract for S6 consumers.

Search and Seller Input must not duplicate canonical/alias matching logic independently.

## 10. Resolver algorithm

Algorithm is fixed:

```text
1. normalize incoming term with the authoritative expression
2. select canonical Product matches by normalized Product.name
3. select alias Product matches by normalized ProductAlias.name
4. combine both candidate sets
5. deduplicate by DISTINCT Product ID
6. classify only after deduplication
```

Classification:

```text
0 distinct Product IDs → not_found
1 distinct Product ID  → resolved(Product)
2+ distinct Product IDs → ambiguous
```

For classification, implementation may stop after two distinct Product IDs, but correctness must be based on distinct Product identity, not raw row count.

### Same-Product canonical/alias collision

If canonical and alias rows both resolve to Product A:

```text
A
A
→ DISTINCT
A
→ resolved(A)
```

This must never be classified as ambiguous.

### Cross-Product collision

If a canonical or alias match resolves to Product A and another candidate resolves to Product B:

```text
A
B
→ ambiguous
```

No ranking, priority or first-row selection may resolve ambiguity silently.


```text

```

- both original Product rows still exist unchanged;
- Product IDs remain unchanged;
- Offers remain unchanged;
- SellerChangeItems remain unchanged;
- `product_aliases` does not remain committed;
- S6 indexes do not remain committed;
- migration journal does not mark `0006` as applied.

Forbidden automatic remediation:

- merge;
- rename;
- delete;
- Product ID reassignment;
- Offer FK reassignment;
- SellerChangeItem FK reassignment.

A conflicting database requires explicit data remediation outside automatic S6 migration.
