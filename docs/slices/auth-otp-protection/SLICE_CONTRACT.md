## 1. One user task

A user signs in through the existing phone/test-code modal, can recover by requesting a replacement code, and understands when repeated requests or wrong guesses require waiting or a new code. The server enforces those bounds even across tabs and restarts.

## 3. Approved initial policy and explicit enforcement contract

| Policy | Approved initial value / semantics |
| --- | --- |
| Minimum request interval | **60 seconds per canonical phone**, shared by initial/replacement requests, tabs and processes. |
| Request budget | **5 accepted requests per rolling 15 minutes per canonical phone**, including consumed, expired and superseded challenges; denied requests do not extend the wait. |
| Wrong-code budget | **5 wrong, well-formed six-digit guesses per challenge**. With four recorded failures, a correct fifth submission still succeeds; a fifth wrong code exhausts that challenge. |
| Recovery | Exhaustion blocks that code, not the User/session/account permanently. Obtain a fresh code when the existing request limits permit; a replacement has a fresh five-guess budget. Existing sessions are not revoked. |

- Validate and normalize the submitted phone with the existing S2 KZ normalizer **before looking up, checking or charging any request limit**. Accepted aliases such as `+7 700 123 45 67`, `87001234567` and `8 (700) 123-45-67` all use the same `+77001234567` budget. Verification derives that canonical phone from the persisted challenge, never a caller-supplied phone. Budgets do not depend on whether a User already exists. No IP/device tracking is added.
- **Every existing login entry point is covered:** buyer More login, contextual seller entry, interest-triggered login, `/login` including seller-return fallback, and direct calls to the existing request/verify endpoints. They all use the shared AuthModal and the same Identity application enforcement. Initial request, resend, exhausted/expired-code recovery and change-number requests use one admission path; none can bypass the limits. This is login OTP protection; separate trading-point contact verification is not a login entry point and is not changed by this slice.
- Requests count only when a challenge transaction commits, before the unchanged post-commit delivery boundary. Delivery failure cannot erase the accepted request budget; old S2 failure behaviour remains otherwise unchanged. Malformed phone/JSON keeps existing validation behaviour and does not count as a valid request.
- Rolling-window membership is `createdAt > now - 900 seconds`; at exactly the 900-second boundary a request drops out. Exactly 60 seconds after the preceding accepted request is eligible if the rolling budget also permits. Eligibility is the later of the interval boundary and the earliest time the rolling budget has capacity.
- A denied request does not supersede the existing challenge, call delivery, reveal a new code or create User/session. It returns HTTP **429**, proposed code `OTP_REQUEST_THROTTLED`, positive integer `retryAfterSeconds` and matching `Retry-After`; existing error shape and `Cache-Control: no-store` remain. A successful 201 retains `challenge`/test `delivery` and adds `retryAfterSeconds` for the earliest next request, computed after accounting for this acceptance. Another tab can move eligibility later; the server remains authoritative.
- Wrong active codes below exhaustion retain HTTP 401 `INVALID_OTP`. The fifth wrong code, and subsequent well-formed submissions to that otherwise-active exhausted challenge (even the correct code), return HTTP **409** with proposed `OTP_ATTEMPTS_EXHAUSTED` and guidance to request a new code. Exhaustion never sets `consumed_at` or marks the OTP successful. Malformed/unknown/expired/consumed/superseded inputs keep current error codes and do not add failures; terminal/expiry checks take precedence.
- **Replacement invalidation:** an admitted new-code request atomically supersedes the previous unfinished challenge and creates the replacement at DB commit. From that commit onward the old code cannot verify, even if it was correct or had guesses left. A throttled request or pre-commit failure leaves the previous challenge untouched. Delivery runs after commit: delivery failure or a lost HTTP response cannot restore the old code or refund the request budget. An ambiguous/failed response must not claim that the old code is certainly still valid; show recovery guidance and retry only through the same limited request endpoint.
- Extend the same OTP step with **Request a new code**, a server-derived wait countdown, clear exhausted/expired recovery and a pending state that prevents duplicate UI submissions. Show the server's wait after admission or a 429; disable request/resend while waiting and verify after known exhaustion, while preserving change-number/close. A successful replacement response clears the typed code and updates the dynamic test-code display. **The timer is guidance, not enforcement:** direct HTTP calls, browser-clock changes, hidden controls and reload cannot bypass the DB policy. If the displayed countdown reaches zero but another tab has moved eligibility, show the updated server wait rather than assume admission. Ignore stale UI responses after a newer request or modal close; preserve existing buyer/seller destinations, change-number and `/login` behaviour.
- Closing/reopening/reloading/changing phone formatting cannot reset server limits. Different real phones have independent budgets. Success does not reset rolling request history. Counter/time configuration is Identity-local with validated positive integers; no production bypass or insecure fallback. Existing OTP/session TTL defaults (300 seconds / 30 days) and crypto are unchanged.

## 4. Storage, concurrency and closed-contract revisions

Use existing PostgreSQL/Identity ownership, no new runtime service or shared limiter framework. Propose an additive migration: persisted bounded failure count on `auth_otp_challenges`, default zero for existing rows, plus a phone/time index if needed for the rolling query. Count accepted requests from existing challenge history; do not delete history inside the live policy window or introduce a new phone/IP retention dataset. No destructive reset/backfill of users, sessions, photos or Offers.

Request-budget check, request-history accounting and replacement must be one serialized transaction per canonical phone. Concurrent eligible requests cannot both spend the same admission slot; after the first commits, the others see its updated history and interval. Failed-count check/increment and successful consume/User/session creation share serialization with replacement for that phone. After resolving a challenge's phone, reload and recheck its lifecycle/expiry/failure count inside that transaction before verifying or mutating it; a stale pre-check cannot authorize login. With four failures, concurrent guesses cannot both pass the remaining failure budget. Correct versus wrong versus replacement operations follow committed serialization order: a correct code wins only while eligible; once exhaustion or replacement commits, it cannot create a session. Wrong-code counter increments must commit before returning their error, rather than roll back with a thrown error; no lost increments or duplicate sessions. Reuse the existing phone-lock boundary, not a general framework. Capture Identity time once inside the serialized decision boundary; preserve fixed-clock tests, no DB `now()` policy or wall-clock sleeps. Budgets persist across restarts and are never memory-only.

**Approval explicitly revises** S2's unconditional request-replacement promise to “replacement only when admitted”; adds exhaustion to verification eligibility while retaining “wrong OTP does not consume”; extends the S2 HTTP error/response surface and auth table schema. It extends UX1A.2's excluded resend/protection scope and error presentation only. No closed source is edited or retroactively labelled approved in this draft. User uniqueness, one-time consume, test delivery boundary, session/cookies/current-user/logout, anonymous Search and seller ownership/navigation remain preserved.

## 5. Out of scope and limits

No SMS purchase/provider/real delivery, removal of test-code display, OTP autofill simulation, passwords/social login, CAPTCHA, WAF, IP/device/global endpoint limits, platform-wide abuse/moderation, account suspension, contact-verification OTP changes, secret/cookie redesign, paid service, Redis or public deployment. Do not equate this slice with completion of O-AUTH or O-ABUSE. **Phone-based limits do not prevent distributed requests across many phones or deliberate exhaustion of another person's request allowance.** They also do not prevent deliberate replacement/exhaustion of an accessible challenge or general malformed/unknown-challenge traffic. A targeted user may temporarily be unable to request a fresh code; no guarantee of attack-proof account availability is made. The correct live code remains usable until exhausted/superseded/expired; there is no permanent account lock and denied traffic does not prolong waits. This is a bounded local protection, not a security exception or public-launch waiver. Test delivery still exposes the code by design.

## 7. Acceptance criteria (for separately authorized implementation)

1. Happy-path first login/re-login, existing test code, persistent sessions/logout, anonymous Search and both contextual destinations retain current behaviour.
2. Normalization precedes limiter access. Phone-format aliases, every listed login entry point, resend/recovery and direct HTTP calls share one persisted budget; 60-second/rolling boundaries are deterministic, including restart and fifth/sixth request cases.
3. Throttled requests return no-store 429/wait response with no delivery/replacement/session side effects. Denials do not prolong cooldown; old valid code still logs in. Admitted replacement invalidates old code at commit, including post-commit delivery/response failure; no refund or resurrection bypass.
4. Each well-formed wrong active code records exactly one failure; four failures followed by correct code succeed, five wrong codes exhaust, and an exhausted code cannot log in. Invalid/terminal cases retain existing semantics.
5. Concurrent wrong/correct/replacement operations enforce the budget and S2 one-time/superseding guarantees atomically; no duplicate User/session or lost failure increment.
6. Recovery through the same modal handles countdown, denied/failed/ambiguous resend, new code, expiry/exhaustion and stale responses in RU/KK without losing caller intent or resetting server budgets. Timer manipulation cannot change admission; another tab's denial refreshes the displayed wait.
7. Secrets/codes are not added to logs or DB plaintext; User existence is not exposed through eligibility/errors. Existing Secure/HttpOnly/SameSite/session contracts remain unchanged.
8. Additive migration upgrades existing challenge/session data safely; request history needed for the live window survives. Limits and counters survive restart; test isolation does not touch dev DB/photos/server.
9. No provider, purchase, platform abuse expansion or claim of public-launch readiness appears in implementation or acceptance evidence.
