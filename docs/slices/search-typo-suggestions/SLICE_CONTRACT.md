# Slice Contract — Search typo correction, automatic (блок UX/search, пункт 5)

**Статус: APPROVED rev 3 (PO, 2026-10-09) + §3.11 «Границы реализации» (уточнение, без расширения scope).** Подача объяснения изменена по решению PO: две строки текста над результатами в стиле Google (без кнопок, рамки, фона и «таблетки»). Нумерация: rev 1 — явный выбор подсказки (снят); rev 2 — автоматическое исправление; **rev 3 (этот файл)** — rev 2 + блокирующий негативный случай «машина → малина» и сужение классов правок, сохранение «как введено» в «последнем поиске», независимость от языка интерфейса, жизненный цикл бюджета и слотов. Реализации нет. Исследование и подготовка разрешены PO; реализация — после утверждения; ограничение на fuzzy остаётся для всего остального. Порядок блока — `EXECUTION_PLAN.md`. Рекомендуемый reasoning effort реализации: **high** (публичный API, additive-миграция D0, ревизии закрытых контрактов). Визуалы — `visuals/index.html` (открыть: `node docs/slices/search-typo-suggestions/visuals/serve.mjs 3300` из корня репозитория, затем `/docs/slices/search-typo-suggestions/visuals/index.html`).

## 1. Пользовательская задача
Если опечатанный запрос не вернул Offers, покупатель сразу видит результаты по правдоподобному исправлению, понимает, что запрос исправлен, и может искать по исходному тексту без исправления.

## 2. Что есть сейчас (факты из кода, контрактов и измерений)
- `searchOffersDetailed`: кандидаты = выбранный Product ∪ exact-resolver ∪ слова названий Offers (начало слова + словоформы). Опечатка без совпадения → `0` Offers, `resolvedProduct = null` («неизвестный запрос»; `search-empty-states`, `v0.0.69`). Совпадение — по **началу слова**.
- Словарь словоформ: 6 949 форм **слов каталога** (проверенные группы), не общий русский язык. Слов каталога ≈ 1 144 (названия, локализованные названия, алиасы) плюс слова названий допустимых Offers.
- PostgreSQL: `pg_trgm` установлен (миграция 0020), `fuzzystrmatch` — нет.
- D0: одно событие на осознанный поиск; подавление повторов 60 с. Адрес `/?q=…[&product=…]` и «последний поиск» (`kaida:last-search`, версии `v:1/2/3`, только `sessionStorage` вкладки) хранят запрос и настройки; восстановление идёт без `intent`.

## 3. Предлагаемое поведение (нормативно)
### 3.1 Что это и чем не является
**Исправление опечатки в слове**: набранное слово, которого нет среди известных, заменяется ближайшим известным при высокой уверенности. **Не** синонимы, **не** перевод, **не** морфология (формы уже ищутся словарём словоформ), **не** смена раскладки, **не** склейка/разрыв слов. **Не определяет язык**: решение принимается только по составу букв и точному совпадению со словарём (§3.4).

### 3.2 Порядок и условия автоматического исправления
1. **Сначала исходный поиск без изменений.**
2. Исправление рассматривается только если: `0` Offers, `resolvedProduct = null`, resolver не `ambiguous`, `productId` не передан, клиент запросил исправление (§3.7), режим включён (§3.8). **Запрос, вернувший Offers, не исправляется никогда.**
3. При **ровно одном достаточно уверенном** исправлении (§3.4) сервер **один раз** ищет по исправленному тексту тем же `searchOffersDetailed` (тот же допуск, окно актуальности, сортировка, направление, геопозиция; без `productId`) и при ≥ 1 Offer возвращает результаты исправленного запроса.
4. Иначе (нет уверенности, неоднозначность, исправленный запрос без Offers или «известный товар без предложений», ошибка, таймаут) — **возвращается исходный нулевой ответ без изменений**. Пустой исправленный результат не показывается.
5. **Петель нет:** один проход на запрос; поиск по исправленному тексту сам не исправляется; «как введено» исправления не просит; клиент не перезапрашивает исправленный текст как новый поиск.
6. **Наличие Offers у исправленного запроса — необходимое, но не достаточное условие.** Оно не доказывает намерение покупателя; доказательством служат только правила §3.4.

### 3.3 Словарь (ограниченный, без новой инфраструктуры)
- **Источники:** слова названий, локализованных названий и алиасов каталога ∪ слова названий допустимых Offers; нормализация как `searchWords` (нижний регистр, ё→е).
- **Два набора:** (а) **«известные слова»** — все слова источников (в т. ч. с казахскими буквами) плюс формы из словаря словоформ — используются только как **защита**; (б) **кандидаты** — только слова из букв `а–я` (после ё→е).
- **Границы:** ≤ 20 000 слов, кэш в памяти с обновлением (≈ 5 минут), без новых таблиц, индексов, расширений. Загрузка словаря — единственный полёт (§3.8).
- **Движок:** собственная функция расстояния в приложении по ограниченным классам правок (§3.4). `pg_trgm` оценён и не выбран (§3.9).

### 3.4 Правила уверенности (подстановка идёт без нажатия, поэтому правила строгие)
Слово **исправляется**, только если выполнено всё:
1. **Алфавит.** Слово состоит только из букв `а–я` (после ё→е). Слова с цифрами, латиницей, смесью, любым другим символом, в т. ч. **казахскими буквами `ә ғ қ ң ө ұ ү һ і`**, не исправляются и не берутся кандидатами. Это проверка набора символов, не определение языка: слова на русских буквах (в т. ч. казахские, записанные ими) обрабатываются по тем же правилам.
2. **Длина** ≥ 5 букв.
3. **Слово неизвестно** — защита «известное слово» (§3.4а).
4. **Классы правок.** Допустимы только: (i) пропущенная или лишняя буква (в т. ч. удвоенная: «сметанна»), (ii) перестановка соседних букв, (iii) замена внутри пар гласных **а↔о, е↔и, и↔ы** (стоимость 0,5). Стоимость: длина 5–7 — не более **1,0**; длина ≥ 8 — не более **2,0** (поэтому у длинных слов допустима и одна замена другой буквы, как «пропуск + вставка»). **Замена согласной или гласной другой буквой вне этих пар у слов длиной 5–7 недопустима.** Первая буква совпадает.
5. **Единственность:** кандидаты группируются по группе словоформ; лучший лучше следующей группы минимум на 0,5, иначе исправления нет.
6. **Несколько слов:** слова проверяются независимо; исправляется ≤ 2 слов; остальные слова известны; более 6 слов, неисправимое неизвестное слово или «все слова известны, но сочетание не найдено» («молоко бетон») — исправления нет.
7. Результат исправленного запроса — ≥ 1 Offer (§3.2); подстановка, ведущая в «известный товар без предложений», не допускается.

### 3.4а Защита «известное слово»: как работает и почему «машина → малина» проходила
Слово считается известным, если оно: (1) есть среди слов каталога/названий Offers, (2) является **началом** такого слова (поиск и так найдёт по началу), (3) является формой из словаря словоформ. Словарь — **словарь товарного рынка**, не общий русский язык: слово «машина» есть в русском языке, но не в каталоге, не начало товарного слова и не форма из словаря → «неизвестно»; одна замена «ш→л» даёт единственного кандидата «малина», и правило rev 2 (допускавшее любую замену стоимостью 1,0) его принимало. Различить «настоящее слово не из каталога» и «опечатку» **по расстоянию и по товарному словарю нельзя**; общий лексикон языка (миллионы форм, отдельная лицензия и размер) в slice **не вводится**.
**Решение rev 3 (блокирующее):** «машина → малина» — **блокирующий негативный случай**. Безопасность достигается сужением классов правок (п. 4): у слов длиной 5–7 замена одной согласной на другую (ш→л) недопустима, поэтому «машина» остаётся без исправления; результат — исходный нулевой ответ. Цена: не исправляются типичные опечатки-замены у коротких слов («груща» → «груша», «лососъ» → «лосось»). Для слов ≥ 8 букв замена допустима (двух правок на 8+ букв достаточно, чтобы кандидат оставался единственным; в измерениях ложных исправлений нет).

### 3.5 Исходный и эффективный запрос
- **Исходный** (как набран) — в поле, адресе, «последнем поиске» и в D0 (как намерение). **Эффективный** — исправленный текст: по нему получены `offers`, релевантность и `resolvedProduct`; он остаётся внутренней деталью ответа и нигде не сохраняется.
- Выбранный Product (`productId`) → `resolution = selected` → исправления нет; эффективный поиск идёт без `productId`. Сортировка, направление, геопозиция — как у исходного запроса.

### 3.6 Показ, «как введено» и его сохранение
- **Две компактные строки текста над результатами** (`role=status`), без рамки, фона, иконки, кнопок и «таблетки»: строка 1 — «Показаны результаты по запросу «**молоко**»» (исправленный запрос выделен жирным шрифтом); строка 2 — ссылка «Искать вместо этого «малако»» (KK: «**молоко**» сұрауы бойынша нәтижелер көрсетілді / «Оның орнына «малако» деп іздеу»). Строки есть только при применённом исправлении.
- **Строка 2 — настоящая ссылка** (`<a href="/?q=малако&typed=1">`, роль `link`, подчёркнута, цвет ссылки макета), а не кнопка: открывается в той же вкладке, работает с клавиатуры (Enter), фокус виден; область нажатия ≥ 44 px по высоте обеспечивается внутренним отступом, компенсированным внешним, так что строки остаются компактными; длинный текст переносится по словам.
- **Ссылка «Искать вместо этого…»** — активирует режим «как введено»: повтор исходного текста без исправления; поле не меняется; обычное состояние нуля (`search-empty-states`), без двух строк и подсказок; события D0 нет.
- **Сохранение режима «как введено»:** признак действует для **этого нормализованного запроса** и переживает перезагрузку, Back, «Поиск» в нижней навигации и смену сортировки/языка; **не сбрасывается молча**. Он снимается только новым осознанным поиском (submit, подсказка каталога, чип) — в т. ч. тем же текстом.
  - **Адрес:** `/?q=…&typed=1`.
  - **«Последний поиск»:** минимальная ревизия формата — новая версия **`v: 4`** = `v: 2/3` + `typed: true`; пишется только когда режим включён, иначе запись остаётся `v: 2/3`; чтение `v: 1/2/3` не меняется; нижняя навигация строит адрес с `&typed=1`; признак игнорируется, если запрос не совпадает с текстом, для которого он был установлен.

### 3.7 API
`/api/search` получает необязательный флаг **`correct=1`**; **без него поведение и ответ прежние**. UI передаёт `correct=1` при обычном поиске (submit, подсказка, чип, восстановление, смена языка/сортировки) и не передаёт при режиме «как введено». При применённом исправлении ответ получает **`correction: { from, to }`** (`from` — исходный текст, `to` — эффективный); `query` — исходный; `offers`/`resolvedProduct` — по эффективному. Невалидное значение `correct` → 400. Отдельного endpoint нет.

### 3.8 Бюджет, одновременность и жизненный цикл (ограниченная фоновая работа)
- **Обычные запросы** — нулевой дополнительный расход. Исправление вычисляется только в «неизвестном нуле».
- **Бюджет ответа — 400 мс.** Это граница ожидания **ответа**, а не работы: по истечении ответ возвращается без исправления.
- **Слот.** Одновременно выполняется не более **3** проходов исправления. Проход **занимает слот до начала работы** (нет слота — исправления нет сразу, **очереди и ожидания нет**). Слот освобождается **только когда фактически завершилась вся работа прохода** (успех, ошибка или таймаут запроса к БД) — в `finally`, **не** при истечении бюджета ответа.
- **Верхняя граница работы прохода.** Единственный дополнительный поиск идёт в короткой транзакции с `SET LOCAL statement_timeout = 1000 мс` (прецедент D0); ожидание соединения ограничено уже заданным пулом (5 с, не более 3 таких ожиданий одновременно, так как слотов 3). Итого один проход живёт не дольше ≈ 6 с в худшем случае и всегда завершает транзакцию (COMMIT/ROLLBACK) и возвращает соединение в пул. Поздний результат **отбрасывается** (не кэшируется и никому не отдаётся); поздняя ошибка перехвачена (нет `unhandledRejection`).
- **Нет безграничной фоновой работы:** нет очереди, повторов, отложенных задач; не более одного прохода на запрос; не более 3 одновременных проходов; словарь загружается **единственным полётом** (один запрос в БД с тем же `statement_timeout`; параллельные запросы ждут тот же результат только в пределах бюджета ответа и продолжают без исправления); неудачная загрузка не запускается заново чаще, чем раз в 30 секунд.
- **Выключатель:** `SEARCH_AUTO_CORRECTION=off` отключает исправление (значение читается при запуске; по умолчанию включено); выключенное = поведение `v0.0.69`.
- Целевая добавка на тестовой БД для «неизвестного нуля»: p95 ≤ 150 мс (замер).

### 3.9 Измерения (evidence; границы утверждений — только эти корпуса)
**Правило rev 3** (алфавит `а–я`, длина ≥ 5, классы правок i–iii, порог 1,0/2,0, единственность по группам словоформ), 1 144 слов каталога dev-БД + 6 949 форм:
| Набор | Результат |
|---|---|
| Положительный корпус, 20 типичных опечаток | **15 исправлено верно**: малако, малоко, картофль, кортофель, говядна, сметанна, помидр, пмидоры, яблко, твораг, морквь, огурци, баранена, свенина, барнина |
| Не исправлены (задокументированные пробелы) | груща, лососъ, тунцц (замена вне пар; «тунец» к тому же без Offers), кумс и мкуа (< 5 букв) |
| **Негативный корпус: 164 правильных слова не из каталога**, **включая «машина»** (телефон, ноутбук, квартира, автобус, ремонт, велосипед, кастрюля, … полный список — в тестах) | **0 ложных исправлений** (до сужения правил: «машина» → «малина») |
| Синтетика: ~600 мутаций слов каталога длиной ≥ 6 | ложных (неверных) исправлений 0; пропуск/лишняя буква: 146/149 верно; перестановка: 145/148; гласные пары: 150/150; замена согласной: 58/150 верно, 0 неверных (только у длинных слов) |
Утверждение «0 ложных исправлений» **ограничено перечисленными корпусами** (негативный корпус + синтетика) и **не является гарантией** для всех слов русского языка; новые контрпримеры, найденные в приёмке или эксплуатации, добавляются в негативный корпус и становятся блокирующими.
`pg_trgm.similarity` (порог 0,3): «малако» — нет кандидатов; «бараина» — «баранина» 0,55 и «барана» 0,50; нет модели путаницы гласных, нужны индекс и запросы к БД — не выбран. 24 % слов каталога (≥ 4 букв) имеют соседа в одну правку — единственность обязательна.

### 3.10 Язык интерфейса не влияет
- Решение об исправлении, исправленный текст и **порядок результатов одинаковы** при `ru` и `kk` для одного и того же запроса: язык интерфейса не является входом исправления и ранжирования (влияет только на подписи и переводы комментариев).
- Казахские и неизвестные слова: слово с казахскими буквами не исправляется и не берётся кандидатом; слово, неизвестное и не прошедшее §3.4, остаётся как набрано (при многословном запросе это делает исправление невозможным). Заявлений о надёжном определении языка нет; поддержка KK-орфографии — отдельным slice.

### 3.11 Границы реализации (уточнение к §3.3 и §3.8; без расширения scope)
- **Только публичные источники словаря:** названия, локализованные названия и алиасы каталога и `title_search` Offers, **допустимых для публичного Search** (тот же допуск и окно актуальности, что у выдачи). Не используются имена и комментарии продавцов, телефоны, запросы покупателей, события D0, любые персональные данные.
- **Размер и обновление словаря:** не более **20 000** слов (сначала слова каталога, затем слова Offers; излишек отбрасывается); слово 2–40 букв; обновление по сроку **300 с**; после неудачной загрузки — не раньше чем через **30 с**; загрузка — единственным полётом, одним запросом с `LIMIT` и `statement_timeout` 1000 мс; ориентир памяти — менее 2 МБ.
- **Ограничение выборки кандидатов и CPU:** словарь индексирован в памяти по первой букве; для неизвестного слова сравниваются только слова с той же первой буквой и разницей длины ≤ 2; не более **3 000** сравнений на слово и **6 000** на запрос; не более 2 неизвестных слов и 6 слов в запросе; слово длиннее 40 букв не обрабатывается; бюджет CPU прохода **25 мс** (проверка каждые 256 сравнений) — при превышении исправления нет.
- **Одновременность на процесс:** 3 слота **на процесс Node** (счётчик в модуле); при нескольких процессах лимит у каждого свой, между процессами координации нет (фиксируется как ограничение развёртывания).
- **Безопасность позднего завершения:** результат прохода, завершившегося после бюджета ответа, **отбрасывается** (признак «ответ уже отправлен»): не пишется в кэш, не используется для D0 и ответа; исключения перехвачены; слот освобождается в `finally` после фактического завершения работы.

## 4. D0 (учёт поиска)
- **Одно событие на осознанный поиск; исходный запрос сохраняется.** Автоподстановка — не второй поиск и отдельным спросом не считается.
- При применённом исправлении событие содержит **исходные** значения (`query_normalized` = исходный, `resolved_product_id = NULL`, `resolution = unresolved`, `result_count = 0`) и **два необязательных поля**: `corrected_query_normalized`, `corrected_result_count` (≥ 1); для остальных событий — `NULL`.
- ссылка «Искать вместо этого», восстановление (адрес, Back, «Поиск», перезагрузка) и повторный показ исправления событий не создают; подавление 60 с не меняется.
- **Additive-миграция:** два nullable-столбца и CHECK («оба `NULL` либо оба заданы; `corrected_result_count ≥ 1`; `corrected_query_normalized ≠ query_normalized`»); существующие строки и значения `entry` не меняются; purge без изменений. Аналитика (D1) обязана читать поля исправления.
- Идентификаторов, исходного написания (только нормализованное), геолокации нет.

## 5. Закрытые contracts
**Ревизии (явно):**
- `S15C / D0 — search demand events`: два nullable-поля исправления и CHECK (миграция).
- `S0 / S6 — форма ответа Search`: необязательные `correct` и `correction`; без параметра ответ идентичен.
- `search-empty-states`: только композиция экрана результатов получает две строки «Показаны результаты по…» / «Искать вместо этого…» над результатами; сам нулевой экран не меняется.
- `search-home-last-state`: адрес — необязательный `typed=1`; формат `kaida:last-search` — версия `v: 4` (`typed: true`), чтение `v: 1/2/3` и восстановление запроса не меняются.
**Только чтение / не меняются:** S7, S9 / Search sort Rev 3, `search-word-forms` (словарь — защита), S15B-2, S15B-3, S13.

## 6. Risk flags
**Фактические:** публичный API: YES (additive флаг и поле); миграция БД: YES (два nullable-столбца + CHECK); ревизии D0, S0/S6, адреса и формата last-state; **тихая подмена дороже подсказки**: известный контрпример «машина → малина» устранён сужением правил, но **«неизвестное» ≠ «опечатка»** остаётся принципиальным ограничением (нет общего лексикона): возможны слова не из каталога, отличающиеся от товарного слова допустимой правкой (пропуск/лишняя буква, перестановка, гласная пара) — защита: Offer-проверка (необходимое, не достаточное условие), явная ссылка «Искать вместо этого», выключатель, пополняемый негативный корпус; **искажение аналитики**, если не читать `corrected_*`; **покрытие**: замены согласных у слов 5–7 букв, слова вне каталога/названий Offers, слова < 5 букв, KK-слова не исправляются (осознанно); **нагрузка**: один дополнительный поиск на «неизвестный нуль», ≤ 3 одновременных прохода, поздняя работа ограничена 1 с БД; формат last-state `v: 4`; новые RU/KK-строки (KK — на вычитку); высота двух строк на 320 px и ×2. **Не затрагиваются:** допуск, релевантность, сортировки, словоформы, resolver, поисковый движок (не внедряется), AI, внешние сервисы.

## 7. Acceptance criteria
1. **Корпуса (границы утверждения — только они):** положительный корпус (≥ 15 пар, §3.9) даёт ожидаемое исправление; **негативный корпус ≥ 150 слов не из каталога, обязательно включающий «машина»**, плюс ничьи, нет близких, известные слова/начала/формы, слова < 5 букв, цифры/латиница, «молоко бетон» — исправления нет; ложных исправлений на негативном корпусе 0; синтетический тест мутаций — неверных исправлений 0. Новые контрпримеры добавляются в корпус.
2. **Порядок и условия:** сначала исходный поиск; запрос с Offers не исправляется никогда; не исправляются `ambiguous`, выбранный Product, запрос без `correct=1`, выключенный режим; при применённом исправлении `correction {from,to}` и результаты эффективного запроса.
3. **Уверенность:** алфавит `а–я`, длина ≥ 5, классы правок и пороги §3.4; единственность по группам словоформ; ≤ 2 исправленных слов, > 6 слов или неисправимое слово — нет исправления; «машина» остаётся без исправления.
4. **Нулевой исправленный запрос:** подстановки нет, исходный нуль как есть; один проход, петель нет (счётчик вызовов).
5. **Эффективный запрос:** допуск, релевантность, окно актуальности, словоформы, сортировка, направление, геопозиция — как у обычного поиска; существующие тесты Search/S9/Rev 3/word-forms без правки утверждений.
6. **Показ и «как введено»:** при исправлении над результатами две строки текста (RU/KK, `role=status`), исправленный запрос выделен, вторая строка — доступная ссылка (`role=link`, Enter, видимый фокус, цель ≥ 44 px) без кнопок, рамки, фона и «таблетки»; поле, адрес и «последний поиск» содержат исходный текст; без исправления строк нет; активация ссылки → обычный нуль без этих строк, события D0 нет.
7. **Сохранение «как введено»:** режим переживает перезагрузку, Back, «Поиск» в навигации (через `kaida:last-search v: 4` и `typed=1`), смену сортировки/языка; не сбрасывается молча; снимается только новым осознанным поиском; для другого запроса игнорируется; чтение `v: 1/2/3` работает.
8. **D0:** одно событие на поиск с исходными значениями и заполненными `corrected_*`; для неисправленных `NULL`; «как введено», восстановление, повторный показ событий не создают; подавление 60 с не меняется; миграция additive, проходит upgrade-тест, CHECK отвергает неполные пары.
9. **API:** без `correct` ответ `/api/search` идентичен прежнему (snapshot); с `correct=1` добавляется только необязательное `correction`; невалидный `correct` → 400.
10. **Бюджет и слоты:** ответ ≤ 400 мс + таймаут возвращает исходный ответ; слот освобождается **только по завершении работы** (тест с заблокированной БД: ответ в бюджете, слот занят до `statement_timeout`, при 3 зависших проходах четвёртый запрос сразу без исправления, потом слоты возвращаются); не более 3 одновременных проходов; поздний результат отброшен, нет `unhandledRejection`; словарь — единственный полёт; обычные запросы без добавки; замер p95 добавки ≤ 150 мс.
11. **Язык интерфейса:** для одного запроса `ru` и `kk` дают одинаковые `correction` и порядок id результатов; слова с казахскими буквами не исправляются и не берутся кандидатами; RU/KK строки совпадают по ключам, KK помечены на вычитку; 320 px, ×2 и длинный запрос без обрезки.
12. **Границы и регрессия:** нет синонимов, перевода, смены раскладки, склейки/разрыва слов, нового движка/расширения/таблицы; словарь ≤ 20 000 слов с кэшем; `search-empty-states`, карточки, страница Offer, «Рядом», экраны продавца/оператора без изменений; `pnpm verify` зелёный.

## 8. Verification (агентская)
Unit — классы правок и пороги, группировка по словоформам, положительный/негативный/синтетический корпуса, алфавит, словарь, разбор `correct`, формат `v: 4`; integration — `/api/search` с `correct=1` и без (snapshot), один проход, `ru`/`kk`-идентичность, исправленный нуль, миграция (upgrade, CHECK) и запись D0, жизненный цикл слота (блокировка БД, 3 зависших прохода, возврат слотов, отсутствие `unhandledRejection`); E2E (mobile + desktop, ru + kk) — исправление, блок, «как введено», Back/перезагрузка/«Поиск» в навигации, отсутствие блока для неисправленных, «машина», 320 px и ×2; замер задержки; полный `pnpm verify`. Тестовые карточки для приёмки готовит агент и записывает ID. **Не проверено** (будет в отчёте): реальные телефоны, KK-вычитка, качество на реальном словаре продакшена.

**Фактическое выполнение замера задержки (запись от 2026-10-09; уточнение, не изменение требований).** Замер сделан на **малой dev-БД** (≈ 26 Offers, словарь ≈ 1 100 слов), а не на тестовом наборе контракта; поэтому критерий 10 (добавка p95 ≤ 150 мс) **не считается полностью подтверждённым**. Измерено по 200 запросов на строку (изолированная сборка, без `correct` и с `correct=1`, запрос с опечаткой): один клиент — p95 24 мс без исправления и 28 мс с исправлением; шесть клиентов — 31 и 54 мс. Разность двух p95 (4 и 23 мс) — это **разность процентилей, а не измеренный p95 добавки на запрос**. Холодный старт отдельно: первый запрос после запуска процесса ≈ 0,4 с (загрузка словаря и соединения), следующие ≈ 40 мс.
**Предлагаемый ограниченный повторный замер** (по решению PO; код не меняется без доказательств): изолированная БД из миграций с Production KB и синтетическими Offers до границы словаря (≈ 5 000 Offers, ≈ 20 000 слов); **парные** запросы (с `correct=1` и без, поочерёдно, один и тот же текст) — не менее 500 пар на режим при 1 и 6 клиентах; отчёт — p50/p95/p99 **разностей внутри пар** и p95 абсолютного времени ответа; холодный старт — первый запрос после 10 перезапусков процесса; ограничение по времени — один рабочий час. Критерий: p95 разностей ≤ 150 мс; при превышении — STOP и отчёт, порог не ослабляется.

**Результат ограниченного парного повторного замера (2026-10-09; отдельная задача проверки, код не менялся).** Стенд: изолированная БД `kaida_perf` (миграции, Production KB v1, 5 000 активных Offers, ≈ 20 000 различных слов в названиях — граница словаря), сборка принятого checkpoint `v0.0.70` (`4016ff0`), порт 3400, запрос с опечаткой «малако» (исправление ведёт к 20 Offers). Метод: парные запросы без `correct` и с `correct=1`, порядок внутри пары чередуется; показатель — **разность времён внутри пары** (то есть измеренная добавка на запрос), не разность процентилей.
| Режим | Пар | p50 добавки | **p95 добавки** | p99 | max | Исправление применено |
|---|---|---|---|---|---|---|
| 1 клиент | 500 | 15,4 мс | **25,3 мс** | 32,6 мс | 41,5 мс | 500 / 500 |
| 6 клиентов параллельно | 504 | 26,4 мс | **44,5 мс** | 55,1 мс | 75,2 мс | 362 / 504 |
Критерий «p95 добавки ≤ 150 мс» **выполнен** (25,3 и 44,5 мс). Абсолютное время ответа с исправлением: p95 38,9 мс (1 клиент) и 65,4 мс (6 клиентов). При 6 параллельных клиентах исправление применено в 72 % пар: остальные пропущены **по замыслу** — лимит 3 одновременных прохода на процесс (§3.8), поиск при этом отвечает исходным результатом.
**Холодный старт** (10 перезапусков процесса; первый исправляющий запрос после старта, включая инициализацию маршрута, пула и загрузку словаря ≈ 20 000 слов): p50 730 мс, минимум 665 мс, **максимум 2 763 мс** (один выброс из десяти); второй запрос — ≈ 38 мс; исправление применено во всех десяти. Для холодного старта критерия в контракте нет; значение фиксируется как есть.
**Ограничения замера:** одна локальная машина (Windows, PostgreSQL в Docker); сборки и тесты на ней во время замера не запускались, но фоновые процессы пользователя не контролировались; синтетические слова из случайных букв без морфологии и без реальной ширины совпадений; один запрос с опечаткой и один результат из 20 Offers; без сети; нет замера на целевой инфраструктуре; 10 перезапусков — малая выборка для хвоста холодного старта. Вывод ограничен этими условиями; провала критерия нет, изменений кода не требуется.

## 9. Manual acceptance (PO, телефон)
(тестовые карточки: «Молоко фермерское», «Молоко свежее», «Творог домашний», «Малина»; агент создаёт и сообщает ID)
1. «помидры» (и «малако») → сразу результаты «помидоры»; над ними две строки: «Показаны результаты по запросу «**помидоры**»» и ссылка «Искать вместо этого «помидры»»; в поле остаётся «помидры».
2. Ссылка «Искать вместо этого» → обычный нуль для «малако»; Back → снова исправленные; перезагрузка и «Поиск» в навигации в режиме «как введено» остаются как введено.
3. «малако свежее» → «молоко свежее» с двумя строками.
4. **«машина»** (при наличии карточки «Малина») → без исправления, обычный нуль; «бараина», «единорог», «молоко бетон» — без исправления; «Творог» (даёт карточки) не исправляется.
5. Казахский интерфейс и крупный шрифт: те же результаты и тот же порядок; ничего не обрезано.
PO принимает: исправление применяется только уверенно, объяснено, возврат к вводу сохраняется, «машина» не исправляется. Технические проверки — агентские.

## 10. Решения PO (с рекомендациями)
- **A. Классы правок (§3.4):** сузить до пропуска/лишней буквы, перестановки и гласных пар; замены согласных для слов 5–7 букв не исправлять (рекомендуется: блокирует «машина → малина», цена — часть реальных опечаток вроде «груща») либо вернуть общие замены (не рекомендуется).
- **B. Минимальная длина:** ≥ 5 букв (рекомендуется).
- **C. D0:** одно событие, исходные значения + `corrected_*` (рекомендуется).
- **D. Исправленный запрос без Offers или «известный товар без предложений»:** не подставлять (рекомендуется).
- **E. «Как введено»:** `typed=1` в адресе и `kaida:last-search v: 4`; снимается новым осознанным поиском (рекомендуется) либо только в памяти вкладки.
- **F. Выключатель `SEARCH_AUTO_CORRECTION`** (рекомендуется).
- **G. Тексты:** RU «Показаны результаты по запросу «молоко»» (исправленный запрос — жирным) / «Искать вместо этого «малако»»; KK ««молоко» сұрауы бойынша нәтижелер көрсетілді» / «Оның орнына «малако» деп іздеу» — на KK-вычитку после реализации (рекомендуется) либо до.
- **H. Охват:** русские слова (алфавит `а–я`), слова с казахскими буквами не исправляются (рекомендуется); KK-исправления — отдельным slice.
- **I. Общий лексикон русского языка** как защита «известное слово»: не вводить в этом slice (рекомендуется: размер и лицензия; решить отдельно, если найденные контрпримеры накопятся).
Утвердить также визуалы: результаты с исправлением, несколько слов, «как введено», случаи без исправления (включая «машина»), KK, 320 px, крупный шрифт.

## 11. STOP conditions
Нужно менять допуск, релевантность, сортировку, словоформы или resolver; нужен внешний/отдельный поисковый движок, новая таблица/индекс/расширение; исправление применяется к запросу, вернувшему Offers, или показывает пустой исправленный результат; возможна петля; слот освобождается до фактического завершения работы либо появляется неограниченная фоновая работа; режим «как введено» молча сбрасывается; результат зависит от языка интерфейса; нужны идентификаторы или исходное написание в D0; автоподстановка считается отдельным поиском; негативный корпус (включая «машина») не даёт 0 ложных исправлений; PO не утвердил визуалы или решения A/C/D/E.
