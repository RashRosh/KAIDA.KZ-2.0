# Local Bootstrap Verification — чистый локальный запуск KAIDA без AI и платной инфраструктуры

**Status:** APPROVED (PO 2026-10-07, с решениями и уточнениями в §12). Реализация — отдельная ветка после слияния этого контракта.
**Base:** `main` `9ed1ba40c17dfda212fe17d2c9a43be67f862d0e` (checkpoint `v0.0.61-search-demand-events`; после него смержены только docs).
**Plan:** шаг R1 «Local readiness track» (`EXECUTION_PLAN.md`, решение PO 2026-10-07): продолжать разработку без платной инфраструктуры. Это **не** подготовка к немедленному пилоту и **не** разрешение публичного запуска без AI.
**Граница доставки:** mobile + русский (`PROJECT_RULES.md` §18.5). UI не меняется.

## 1. Цель

Доказать, что KAIDA поднимается **с нуля** по записанной инструкции — чистый checkout, изолированные база и хранилище фото, секреты, миграции, Production KB, production build — и что на этом окружении проходит существующий ручной путь Seller → Buyer. Результат — точная воспроизводимая инструкция и доказательства прогона, а не новая функциональность.

## 2. Фактическое состояние на `main` (evidence)

- `README.md` описывает `corepack`, `pnpm install --frozen-lockfile`, `.env`, `IDENTITY_OTP_HMAC_SECRET_HEX`, `docker compose up -d --wait`, `pnpm db:migrate`, `pnpm db:seed`, `pnpm dev`. **Шага установки Production KB нет**; `pnpm db:seed` каталог KB не ставит (команда `pnpm db:import:production-kb`, `src/cli/import-production-kb.ts`, идемпотентна). Требование Node (`engines` `>=24 <25`, `.node-version` `24.19.0`) в README не указано.
- `pnpm db:seed` — **демо-данные**: вымышленные Products «Баранина»/«Говядина» с фиксированными UUID, продавец, точка, две активные карточки; upsert, таблицы не очищает. Отдельного «чистого» bootstrap-пути и его проверки нет; E2E-БД собирается как migrate + seed + KB-импорт (`tests/e2e/global-setup.ts`).
- `docker-compose.yml` жёстко занимает `127.0.0.1:5432`, том `postgres_data` и создаёт `kaida` и `kaida_test`; второй стек рядом без изменений конфигурации не поднимается. Хранилище фото — `PHOTO_STORAGE_DIR` (по умолчанию `.data/photos` относительно рабочего каталога, `.data/` в `.gitignore`).
- Обязательный секрет — `IDENTITY_OTP_HMAC_SECRET_HEX` (64 hex). Остальные переменные имеют значения по умолчанию или выключают функцию, если пусты (`INTERNAL_JOB_SECRET`, `WEB_PUSH_*`, `OPERATOR_PHONES`, `SELLER_COMMENT_TRANSLATOR`). `.env*` (кроме `.env.example`) не отслеживается Git.
- Никакой проверки «чистого окружения» не проводилось: все прогоны шли на рабочей копии с существующими `node_modules`, `.env`, dev-БД и фото.

## 3. Behavior (что должен сделать slice)

### 3.1 Изоляция

- **Свежий checkout:** `git clone` указанного SHA `main` в новый каталог вне рабочей копии (временный каталог ОС); `pnpm install --frozen-lockfile` с нуля. Ничего не копируется из рабочей копии: ни `node_modules`, ни `.env`, ни `.data`, ни `tmp/`, `scripts/`, `.vscode/`, `.mimosa/`.
- **Свежая БД:** одноразовый PostgreSQL 18 (тот же образ, что в CI и compose) со своим именем контейнера, своим томом и свободным портом, **не равным** `5432`, `3000`, `3100`, `3101`. Способ (compose-проект с override или `docker run`) выбирает реализация внутри этих ограничений.
- **Свежее хранилище фото:** `PHOTO_STORAGE_DIR` внутри каталога проверки, задан явно.
- **Нельзя:** подключаться к dev-БД `kaida`/`kaida_test`, использовать том `postgres_data`, порт 5432, `.data/photos` рабочей копии, `docker compose down -v` или иные команды по дефолтному compose-проекту. Удалять — только созданные проверкой ресурсы по их точным именам.

### 3.2 Секреты и конфигурация

- Секреты (минимум `IDENTITY_OTP_HMAC_SECRET_HEX`) генерируются **в момент проверки** и живут только в неотслеживаемом `.env` свежего checkout или в окружении процесса. В Git, документы и evidence значения не попадают (в отчёте — только факт и формат).
- Инструкция содержит таблицу переменных: обязательные / необязательные / только локальные (`IDENTITY_COOKIE_SECURE=false` допустим лишь для http localhost; для HTTPS-развёртывания — `true`, это относится к шагу R3, здесь только записывается) / что происходит при пустом значении.
- Прогон фиксирует, что происходит **без** обязательного секрета (понятная ошибка или нет) — как наблюдение; код ради этого не меняется.

### 3.3 Два режима начальной БД (явно разделены)

| Режим | Состав | Для чего |
|---|---|---|
| **Clean bootstrap** | миграции `0000…0023` на пустой БД + `pnpm db:import:production-kb`; **больше ничего** | основа любого реального окружения: каталог есть, вымышленных данных нет |
| **Demo bootstrap** | Clean bootstrap + `pnpm db:seed` | только локальная демонстрация и разработка |

Проверки (SQL после шага, значения в отчёте):
- **Clean:** `products = 682`, `product_aliases = 210`, категории `= 35`, запись установки KB есть; **все прочие таблицы (кроме каталожных и журнала миграций) пусты** — нет продавцов, точек, карточек, пользователей, сессий, фото, событий поиска. Повторный `import:production-kb` ничего не меняет (идемпотентность). Миграции применяются на пустую БД без ошибок и повторный `db:migrate` — no-op.
- **Demo:** вымышленные записи seed присутствуют; зафиксировано, как seed-Products «Баранина»/«Говядина» соседствуют с KB (нет ли дублей канонических названий, влияющих на Search). Любой конфликт — **находка для PO**, а не молчаливая правка seed/KB.
- Инструкция однозначно говорит, что `db:seed` не входит в реальное окружение.

### 3.4 Production-smoke существующего ручного пути

На production build (`pnpm build` → `pnpm start` на свободном порту), с `DATABASE_URL`/`PHOTO_STORAGE_DIR` изолированного стека, `SEARCH_EVENTS_ORIGIN=test`, на базе **Clean bootstrap**. Данные smoke создаёт сам через публичный интерфейс приложения (HTTP/браузер), не записью в БД, с синтетическим телефоном; они остаются только в изолированной БД и не являются частью bootstrap.

1. Сервер стартует; `/` отвечает 200; без обязательного секрета — см. §3.2.
2. **Каталог с чистой БД:** поиск «баранина» → HTTP 200, `resolvedProduct` найден, 0 Offers (известный товар без предложений).
3. **Seller:** вход по test OTP → торговая точка с адресом, координатами и режимом работы (существующий ручной путь) → карточка из каталожной подсказки (Product из Production KB), цена и единица, одно фото → Change Set подтверждён → Offer активен. Вторая карточка со свободным названием.
4. **Фото:** файл появился в изолированном `PHOTO_STORAGE_DIR`, отдаётся покупателю (`200`, `image/webp`).
5. **Buyer без входа:** тот же поиск находит Offer (цена, точка, фото, режим работы); открывается карточка `/offers/[id]`; ссылка маршрута строится; карточка со свободным названием находится по словам названия.
6. **Operator (`OPERATOR_PHONES` = синтетический номер):** новые карточки видны в ленте пост-проверки.
7. События поиска, созданные smoke, имеют `origin = test`; строк `organic` нет.

### 3.5 Остановка и очистка

Сервер остановлен; одноразовые контейнер, том и каталог проверки удалены по точным именам. Evidence очистки: ресурсов нет; **dev-стек не тронут** — контейнер/том/порт 5432 те же, что до проверки (read-only сверка идентификаторов и счётчиков до/после, без записи).

### 3.6 Артефакты

- Инструкция `docs/ops/LOCAL_BOOTSTRAP.md` (точные команды в POSIX-shell и PowerShell, требования: Node, pnpm, Docker, свободные порты; таблица переменных; оба режима; smoke; очистка) и правка `README.md`: ссылка на инструкцию, шаг KB-импорта, требование Node, пометка «seed — только demo».
- Минимальный smoke-раннер (механизм выбирает реализация, см. §12), не входящий в `pnpm verify` и CI по умолчанию, не использующий `testDatabaseUrl`/`global-setup`/тестовые БД.
- Отчёт прогона (в PR description / отчёте PO): SHA, версии Node/pnpm/Docker, точный список команд, время шагов, результаты SQL-проверок и smoke, доказательство очистки и неизменности dev-стека, найденные отклонения.

## 4. Scope / out of scope

**В scope:** проверка, инструкция, README, smoke, отчёт.
**Вне scope:** изменение продуктового поведения; новый UI; backup/restore (R2); развёртывание/Dockerfile/HTTPS/планировщики (R3); покупка или развёртывание хостинга; AI; настоящая аутентификация, abuse-защита, юридические тексты, операторская доставка OTP, allowlist, оповещения о free-title (**не добавляются**); D1, чипы; изменение Production KB, seed-содержимого или compose без решения PO; оптимизация CI; Issue #116; KK-вычитка.

## 7. Risk flags

Infrastructure/data safety (случайно задеть dev-БД или фото — главный риск, §3.1); secrets (§3.2); process (демо-данные не должны попасть в реальное окружение). DB schema, public API, auth, privacy не меняются.

## 8. Acceptance criteria

1. Прогон выполнен из свежего clone зафиксированного SHA; ни один файл/каталог/БД рабочей копии не использовались.
2. Clean bootstrap: счётчики и «все прочие таблицы пусты» подтверждены SQL; повторный импорт и повторные миграции — без изменений.
3. Demo bootstrap описан и проверен отдельно; соседство seed и KB задокументировано.
4. Smoke §3.4 пройден целиком на production build; фото лежит в изолированном хранилище.
5. `docs/ops/LOCAL_BOOTSTRAP.md` и README позволяют повторить результат без знаний из чата; инструкция не содержит значений секретов.
6. Очистка и неизменность dev-стека подтверждены.
7. Branch CI `KAIDA verify` зелёный; полный `pnpm verify` — по `PROJECT_RULES.md` §7 (docs/скрипты, продуктовый код не менялся).
8. Все находки перечислены; продуктовые находки не исправлены молча.

## 9. Verification (агентская)

Прогон по §3 на физической машине PO (Windows, Docker Desktop) с точными командами в отчёте; при невозможности чего-либо — явное «не проверено», без замены предположением. CI не заменяет локальный чистый прогон и наоборот. Повторный прогон второй средой (Linux-контейнер/CI) — не требуется этим slice.

## 10. Manual acceptance (PO)

UI не меняется, телефонного сценария нет. PO принимает отчёт и инструкцию: достаточно ли однозначны шаги и evidence, чтобы считать R1 закрытым. Запускать команды PO не нужно.

## 11. STOP conditions

Любая необходимость подключиться к dev-БД/фото; секрет оказался в изменяемом Git-файле; находка требует изменения продуктового кода, KB, seed, миграций или compose; ресурс удаляется по неточному имени; необходимость платного сервиса.

## 12. Решения PO (приняты 2026-10-07) и уточнения

Решения:
1. **Разделение seed:** инструкция + явные проверки состояния БД; **новой защиты у `db:seed` нет**.
2. **Smoke:** отдельная Playwright-конфигурация, mobile-viewport, вне `pnpm verify` и CI по умолчанию.
3. **Checkout:** временный каталог ОС, удаляется после прогона.

Уточнения:
- «Все прочие таблицы пусты» означает **таблицы бизнес-данных до действий smoke**. Метаданные миграций исключены; любые необходимые технические записи (например, запись установки KB) исключаются явно и перечисляются в отчёте с обоснованием.
- Адрес и геопозиция — существующий ручной путь (manual address/geo fallback). Проверяется **построение** ссылки маршрута; успешная навигация у стороннего сервиса и платные сервисы не требуются.
- Сначала изучается существующая поддержка Compose; предпочтителен узкий override или изолированная конфигурация, дефолтный dev-стек не меняется.
- Smoke-раннер минимален и воспроизводим; второй общий тестовый фреймворк не строится. Закоммиченный инструментарий лежит в репозиторно-уместном месте (не в личной папке `scripts/`, которую запрещено коммитить).
- Реальный конфликт seed/KB — в отчёт PO, без молчаливой правки продуктового поведения.
- Проверки по diff: полный набор не повторяется ради docs; CI ветки обязателен.
