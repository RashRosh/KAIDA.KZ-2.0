# Source-wide login OTP protection — Slice Contract

**APPROVED by PO2026-10-11; implementation authorized after normal docs PR publication.** Initial policy and final previews approved. Temporary shared-network blocking is an accepted tradeoff. Voice/translation experiments remain paused; test delivery only.

## 1. One task / authoritative sources

A person signs in through the existing modal while a requester cycling through phone numbers on the same network cannot obtain unlimited codes. A temporary denial explains the wait and preserves an already issued usable code.

- O-ABUSE / [Execution Plan](../../product/EXECUTION_PLAN.md) section4.2 and [Project Rules](../../PROJECT_RULES.md) section16 require a separate pre-launch abuse decision; they supply no source quota or retention values.
- CLOSED [auth-otp-protection](../auth-otp-protection/SLICE_CONTRACT.md) section3 owns canonical-phone60s /5 requests per rolling15min, five incorrect guesses per challenge, recovery, atomic replacement and all login entry points. These values remain unchanged. Section5 excluded source/IP protection: this proposed contract explicitly extends that boundary.
- S2, UX1A2 and seller-contextual-auth contracts remain authoritative for sessions, test delivery, anonymous search, caller intent and existing shared-modal composition. Only new request admission/errors/countdown handling and additive schema extend those contracts; no retroactive alteration of historical source documents.
- R3 local TLS evidence does not verify a public/provider proxy. R2 backup/restore remains a full database/photo bundle; this proposal does not silently exclude tables from it.

## 2. Policy / atomic admission

| Policy | Initial value specified by PO for final contract review |
|---|---|
| Source quota | 20 **accepted** login-code requests per exact canonical source IP per rolling15min, across every phone, including repeat requests |
| Source cooldown | None; no source-wide60s spacing |
| Phone / guesses | Existing approved limits unchanged |
| Missing trustworthy source when enabled | No issuance/delivery;503 AUTH_UNAVAILABLE, no invented countdown. Existing-code verification remains usable under its existing rules |

Normalize/validate phone and source before admission. Initial requests, resend, recovery, change-number, every existing login entry point and direct API calls use the same server admission path. Trading-point contact verification is excluded. Count requests only when challenge issuance commits, before post-commit test delivery; delivery/response failure does not refund the budget.

Phone and source checks, both budget charges, and old-code superseding/new challenge creation must commit as **one transaction**. Stable lock ordering across phone/source/maintenance locks prevents deadlocks; database state provides cross-process/restart enforcement. Exactly one concurrent request obtains the final slot. A denial consumes **neither budget**, creates no challenge/session, replaces no current code and calls no delivery. No lost increments or partial charge on rollback. Verification/replacement concurrency retains the CLOSED contract's atomic guarantees.

Membership is acceptedAt > serverNow −900s; an event drops out at exactly900s. The retry time is the later of existing phone eligibility and source capacity. A source denial returns429 OTP_SOURCE_THROTTLED, positive integer retryAfterSeconds, matching Retry-After, Cache-Control:no-store, without disclosing other phones or User existence. Both-limit denial presents the applicable wait consistently. Denied/malformed requests do not extend waits or count toward the accepted-issuance cap; this is not a general traffic/flood limiter. New requests remain server-checked when the displayed countdown reaches zero.

## 3. Supported source configurations / spoofing boundary

1. **Direct/local, protection OFF:** existing local test login works unchanged; no source collection. The current port3000 private-snapshot arrangement remains OFF and untouched.
2. **Enabled isolated local reference:** a dedicated locally managed proxy fronts an isolated test app. It derives the source from its actual connection peer, strips client-supplied source/forwarded headers and writes exactly one canonical X-Kaida-Client-IP header. The app's listener is reachable only through that proxy (isolated network, not a publicly published bypass port). Local loopback addresses may be test sources. Multiple-source tests use real controlled source addresses, not browser-provided override headers.
3. **Enabled trusted-proxy deployment:** the same single-header contract, but actual ingress topology, trusted peer allowlist/upstream-chain parsing and app network isolation require separate deployment verification. Trust only explicitly configured peers; never trust all private ranges or an arbitrary leftmost X-Forwarded-For value. The edge must remove/overwrite the canonical header supplied by clients. An upstream CDN requires its own verified trust configuration.

The inspected Next Request handler has no verified connection-peer API. **Enabled direct-to-Next mode is unsupported**; a header alone does not establish trust. Protected deployment startup/preflight must require the isolated/verified ingress arrangement. Missing, invalid or multiple canonical source values produce503 without issuance; no fallback to a shared “unknown” bucket or unlimited budget. The app must reject malformed/multiple values even inside the trusted boundary. A syntactically valid forged single header is prevented by edge overwriting and blocked direct access, not by pretending the app can infer its sender.

Parse IPs without DNS lookup. Equivalent IPv6 spellings normalize to one address; IPv4-mapped IPv6 normalizes to the same IPv4 source. Reject header lists, hostnames, zone IDs, address-with-port syntax and malformed addresses; source ports are not part of identity. Exact IPv6 address only, no /64 aggregation. Address rotation/distributed sources remain limitations. The IP is a network source, not proof of a person/device.

## 4. Retained fields / key lifecycle / backups

Source admission events retain only a random event ID, keyed source digest, nonsecret key-generation ID and server acceptedAt timestamp. No raw IP, phone, User/challenge ID, OTP, text or user agent in these new records. A small maintenance row contains only key generation, last successful full cleanup time, worker health and any issuance-quarantine deadline. No permanent per-source profile. Existing phone/challenge storage is unchanged; correlation by timestamps is still possible, so this is **pseudonymous, not anonymous** data.

Use HMAC-SHA256 with a separate random256-bit secret shared by all app/cleanup workers, outside Git/database dumps, not the OTP secret. Restart retains the same key/generation; missing/mismatched key config blocks issuance, not verification. Do not reset budgets by hot key rotation. Rotation is a coordinated issuance pause of at least15min across instances, followed by cleanup and replacement of key/generation on all workers before resuming; existing-code verification continues. Keep the outgoing key only through that transition, then remove it from active configuration. Persist the pause/generation so restart cannot shorten it. No automatic daily rotation or silent reset.

R2 full dumps can contain these pseudonymous rows; deleting live rows **does not erase backups, PostgreSQL WAL or forensic/storage copies**. Local acceptance uses synthetic sources/phones only and records disposable resource IDs; private dumps/keys are not uploaded. Restore must run cleanup before enablement and enforce a fresh15min issuance quarantine, preventing quota bypass from an older snapshot; phone budgets/verification follow existing restore limitations. Protect restored rows as personal/security data even without the old key. No R2 exclusions are added implicitly. Production backup/log/WAL retention, expiry and erase policy are still unapproved; a system-wide24h erase guarantee must not be claimed or real users enabled before that separate policy is resolved.

## 5. Concrete cleanup mechanism / honest guarantee

Implement one idempotent Identity cleanup operation and a **separate supervised worker process**, not request-triggered cleanup, an unsupervised app timer, or a new paid scheduler. It starts with the isolated protected stack, runs a full sweep at startup and every5min by server/DB time, deletes source events at least15min old and leaves no empty per-source rows. One database maintenance lock coordinates competing workers/rotation; cleanup transactions cannot delete an in-window event or race admission into a reset budget. A full successful sweep updates the persisted heartbeat only after commit. Partial/failed sweeps do not report success. Readiness waits for the first successful sweep; supervisor restarts failures. If no successful sweep within15min, protected issuance fails closed with503; verification remains usable. Worker retry/health reporting continues independently of user traffic.

**Supervision/freshness/recovery:** the proposed isolated reference stack runs the cleanup worker as a dedicated Compose service with restart:unless-stopped. A failed startup/sweep exits nonzero so the supervisor can restart it; the initial sweep is repeated idempotently on each restart. Docker does not automatically restart a merely unhealthy process: the worker must exit on failed sweeps, while an independent health probe exposes stale cleanup. Protected request admission reads the persisted successful-sweep heartbeat in its transaction; missing or more than15min-old heartbeat returns503 before either budget or the current code changes. Verification does not depend on cleanup freshness. After an outage shorter than the24h live-retention bound, a successful full sweep and current key/config automatically restore issuance, subject to unchanged active quotas and any rotation/restore quarantine. A detected24h retention breach is recorded as an operational incident and requires operator acknowledgement/remediation before re-enablement; recovery never silently waives it. Monitoring/alert delivery and actual supervisor uptime must be verified at deployment; this draft does not claim that restart policy alone guarantees availability.

**Deletion within24h is a live-table operational bound conditional on database/worker availability**, not a promise of physical erasure while hardware/database is stopped. The normal5min sweep removes events shortly after their15min quota lifetime, far inside24h, even with zero requests. Tests must prove no-traffic cleanup with the worker actually running, not only manually calling a purge fixture. A supervisor/health probe flags a stale heartbeat before the24h bound; any actual24h breach is a retention incident, blocks protected issuance/re-enablement and requires recording/remediation. Startup/restore purges overdue rows before enablement. If storage is unavailable, physical deletion is impossible: no invented “guarantee” or approved exception hides that failure. Deployment must separately verify continuous scheduling/monitoring/recovery and approve the live-only versus backup retention boundary before real-user use.

## 7. Scope / risks / acceptance

**Scope:** login request adapter/source normalization, Identity atomic source/phone admission, additive source-event/maintenance storage, cleanup worker/reference isolated ingress operations and existing modal errors/countdown. **Risks:** migration, public API, auth/privacy, concurrency, cleanup operations and proxy trust. Preserve existing challenge/session/phone data; no destructive migration. No real SMS/provider/purchases, CAPTCHA, fingerprinting, permanent bans, general rate limiting, reviews/moderation or public launch. Shared NAT/Wi-Fi users can temporarily block one another: accepted proposed tradeoff, approved by PO2026-10-11. Distributed IPs, IPv6 rotation, victim-phone exhaustion and general flood defence remain unresolved beyond this bounded slice; do not mark all O-ABUSE complete.

Acceptance criteria after separate implementation approval:
1. Existing phone60s/5-per15min and five-guesses policy/session/login contexts unchanged; no source-wide cooldown.
2. Twenty issuances across phones from one source succeed when phone limits permit;21st is denied; other source eligible. IPv4/IPv6 aliases share the proper budget.
3. Concurrent final-slot/multi-phone/phone-and-source contention and rollback prove one atomic admission; denial preserves both allowances/current code and calls no delivery.
4. Restart retains budgets; boundary900s/recovery and post-commit failure preserve counting. Verification remains usable during source/config/cleanup outage.
5. Forged/multiple/invalid headers, edge overwrite, untrusted upstream and direct bypass prove the supported reference trust boundary; unspecified deployment not claimed verified.
6. Missing trustworthy source/key/healthy cleanup blocks issuance only. UI preserves draft/caller intent/code, displays server-derived wait and ignores stale responses; all login entry points covered.
7. New stored/logged fields meet section4; key rotation/restore quarantine cannot silently reset admission. Additive upgrade preserves old challenges/sessions.
8. Separate worker demonstrably purges expired rows without requests, has restart/heartbeat/failure evidence, and never deletes active budget evidence. Backup/physical-erasure limits are documented, not silently waived.
9. Current/proposed actual-component RU/KK narrow320px previews reviewed; implementation verification must cover large text/accessibility and preserve existing layout/styles/navigation. Full final executable regression/branch CI and manual acceptance required before merge/tag.
