# S15C / D0 — Search Demand Events

**Status:** DRAFT — на approval PO.
**Base:** `main` после `v0.0.60-search-sorting-control` (S15B закрыт).
**Plan:** первый slice Demand Data Foundation (`EXECUTION_PLAN.md`, 10C; Issue #55; `KAIDA_DEMAND_PRODUCT_CONCEPT_v0.1.md` D0; `SEARCH_SYSTEM_SPEC_v0.1.md` §18). Цель — **надёжно записывать осознанные поиски покупателей уже сейчас**, чтобы реальный спрос можно было измерить, когда начнётся живое использование. D0 не требует существующих продавцов, трафика или накопленного спроса и **не вводит ожидание данных перед AI Input** (накопление идёт параллельно, как в плане). Только запись: аналитика (D1), популярные чипы, Seller Demand UI, watch, AI, fuzzy — вне slice.
**Граница доставки:** mobile + русский (`PROJECT_RULES.md` §18.5).

## 1. User task (внутренняя)

Оператор получает достоверные, приватные события «осознанный поиск покупателя → исход» без влияния на работу Search и без накрутки от служебных действий (смена сортировки, Back, восстановление, повтор после ошибки).

## 2. Фактическое поведение на `main` (evidence)

- Событий поиска нет. `/api/search` (GET/POST) вызывается из UI при: submit поля, выборе подсказки, клике по чипу, смене сортировки/сбросе, смене языка, восстановлении по адресу/last-state/Back, повторе после ошибки — **без признака намерения**; сервер не отличает их.
- Результат Search содержит `resolvedProduct` (выбранный или найденный exact resolver, S15B-4a), `offers.length` (known-zero = `resolvedProduct ≠ null` и 0 Offers, S15B-2); состояние `ambiguous` существует только внутри resolver.
- Сервер не хранит идентификаторов покупателя; `sessionStorage` держит только last-state (запрос, сортировка, `productId`).

## 3. Behavior

### 3.1 Что такое один осознанный поиск (единица события)
Событие создаёт **успешный** Search (ответ 200), инициированный одним из осознанных действий:
- **`submit`** — Enter или кнопка «Искать» (Search Home) при введённом тексте;
- **`suggestion`** — выбор Product в подсказках (поиск запускается сразу);
- **`chip`** — клик по curated-чипу (записывается и помечается, чтобы будущая аналитика могла исключить собственную подсказку из популярности).

Не создают событие: ввод символов и показ подсказок; смена сортировки и «По умолчанию»; смена языка и перезапрос карточек; восстановление по адресу `/?q=`, «Поиск» в навигации, Back; повторный запрос при тех же `q`/`productId`; любой запрос без признака намерения (в т. ч. внешний API-клиент). «Сообщить, когда появится», «Искать как введено» и watch — не D0.

### 3.2 Момент записи и поля (минимум, без идентификатора)
Событие пишется **на сервере после вычисления ответа**, из тех же значений, что получил покупатель; клиент исход не сообщает. Поля:
- время `occurred_at` — **с точностью до часа** (усечение);
- `entry` — `submit` | `suggestion` | `chip`;
- `query_normalized` — нормализованный текст (как `searchWords`: нижний регистр, ё→е, без пунктуации), без исходного написания;
- `resolved_product_id` — `resolvedProduct.id` ответа или `NULL` (known / unresolved demand);
- `resolution` — `selected` (Product выбран из подсказки и согласован) | `resolved` (exact resolver) | `ambiguous` | `unresolved`;
- `result_count` — число Offers в ответе (0 + `resolved_product_id` = known-zero; 0 без Product = unresolved zero-result);
- `geo_cell` — **грубая** ячейка (округление до 0,05° ≈ 5 км) buyer location, **только если** запрос нёс location, т. е. покупатель явно включил геолокацию (`По расстоянию`); точные координаты и радиус не хранятся;
- `origin` — происхождение данных: `organic` | `dev` | `test` | `synthetic` (§3.6).
**Нет:** `user_id`, session/device/anonymous key или иного постоянного/сессионного идентификатора (требование плана 6F/6G; необходимость не доказана — см. §9), IP, user agent, locale, исходного написания, перечня Offers/продавцов.

### 3.3 Защита от ложного спроса
- **Признак намерения** передаёт только UI на осознанных действиях §3.1: необязательный параметр `intent` (`submit|suggestion|chip`) в GET и POST `/api/search`. Без него ответ прежний и событие не пишется; не-валидное значение → `400`. Ответ Search не меняется.
- **Повтор после ошибки:** событие пишется только при успешном ответе; если исходный поиск не удался (сеть, 503), UI сохраняет намерение до первого успешного ответа — повтор создаёт ровно одно событие, неудавшиеся попытки — ни одного.
- **Двойной submit / повтор подряд:** клиент не отправляет `intent`, если `q` (нормализованный) и `productId` совпали с последним записанным намерением в этой вкладке за **60 с** (хранится только в памяти страницы, не в `sessionStorage` и не на сервере). Параллельный запрос блокируется существующим guard.
- Смена сортировки/сброс/язык/Back/восстановление — без `intent` ⇒ без события. Повторный осознанный поиск **другого** запроса — новое событие.
- Остаточный риск, принимаемый в D0: сервер не может отличить подделанный `intent` (нет идентификатора); общий rate limit и quality-фильтры unresolved — предмет D1/Anti-abuse, не D0.

### 3.4 Приватность
- Событие внутреннее: **публичного чтения нет** (ни Seller, ни buyer API не возвращают события, `query_normalized`, `geo_cell`).
- Не пишутся события для запросов, похожих на персональные данные: нормализованный текст длиннее 100 символов или содержащий цепочку ≥ 6 цифр (телефон/номер) — запрос выполняется, событие пропускается.
- Координаты в событие не попадают, кроме грубой ячейки при явной геолокации; autocomplete-запросы не пишутся.

### 3.5 Retention и сбой записи
- Сырые события хранятся **не дольше 90 дней** (настройка `SEARCH_EVENTS_RETENTION_DAYS`, по умолчанию 90). Удаление просроченных — функция очистки, вызываемая **оппортунистически при записи** (малая доля записей, ограниченная пачка), чтобы срок соблюдался без планировщика; изменение политики — конфигом.
- **Сбой записи не влияет на Search**: событие пишется после готового ответа в `try/catch`; ошибка логируется без текста запроса (`Search event failed`), покупатель получает обычный ответ. Рекомендуемый вариант — запись, ожидаемая до ответа (`await`, без fire-and-forget), без retry/outbox. Компромисс: потеря отдельного события при сбое БД (приемлема для D0, видна в логе) и небольшая задержка записи; взамен нет фоновых задач и очередей, исход события всегда соответствует отданному ответу.

### 3.6 Происхождение данных, synthetic fixtures
- `origin` задаёт сервер из конфигурации `SEARCH_EVENTS_ORIGIN`: `organic` пишется **только** если переменная явно задана в боевом окружении; по умолчанию — `dev`; тестовые прогоны — `test`. Публичный API не позволяет задать origin.
- **Synthetic** fixtures — только для тестов механики записи/будущей агрегации; создаются тест-хелпером с `origin = 'synthetic'` напрямую в тестовой БД; в production-коде пути записи `synthetic` нет. Реальные запросы не имитируются; гипотетические счётчики не считаются популярностью.
- Будущая аналитика (D1) обязана читать только `origin = 'organic'` (в D0 фиксируется ограничением значений поля и тестом).
- Не входит: смешивание curated/evidence-контента, затухание, агрегаты, правила замены — будущий slice readiness-gated чипов/Discovery.

## 4. Scope / out of scope

**In scope:** таблица `search_events` (миграция + upgrade-путь); запись на сервере по §3.2–§3.5; параметр `intent` (GET/POST) и его передача UI из осознанных действий §3.1 с клиентским подавлением повторов; retention-очистка; конфигурация `origin`/retention; тесты и synthetic-фикстуры; приведение `SEARCH_SYSTEM_SPEC` §18 к решению PO.

**Out of scope:** D1 агрегаты/аналитика/operator validation; популярные чипы и curated-fallback логика; Seller Demand UI; D2 watch/«Сообщить, когда появится»/«Искать как введено»; пользовательские и сессионные идентификаторы, dedupe уникальных людей; точная геолокация и радиус; AI Input; модерация; fuzzy; оценка поисковой системы; не связанные правки CI (в т. ч. Issue #116).

## 5. Expected modules

Новый модуль `search-events` (`db` schema/migration, `application/record-search-event.ts`, retention), `src/app/api/search/route.ts`, `src/modules/search/contracts/*` (параметр `intent`), `SearchScreen` (передача `intent`, подавление повторов), конфиг; тесты `tests/unit`, `tests/integration` (включая migration upgrade), `tests/e2e`. Каталог, ранжирование и eligibility не меняются.

## 6. Closed contracts — ревизии

- **S0 / S6 (API Search):** GET/POST `/api/search` получают необязательный `intent`; строгая POST-схема расширяется; ответ и поведение без `intent` не меняются.
- **S15B-3 (подсказки/выбор):** выбор подсказки теперь передаёт `intent=suggestion`; адрес/last-state/Back не меняются и событий не создают.
- **`SEARCH_SYSTEM_SPEC_v0.1.md` §18 (target):** «Минимальная сущность» приводится к D0: без `user_id` и `anonymous_session_key_hash`, без `query_display` и точной геолокации/радиуса, с `entry`, `resolution`, грубой `geo_cell` и `origin`; события `Искать как введено` и watch — не D0.
- Не ревизии: S15B-1/2/4a/4b (семантика `resolvedProduct`, known-zero, relevance читается как есть), Rev 3/сортировка, last-state, Nearby, каталог.

## 7. Risk flags

public API: **YES** (additive `intent`) · **DB migration: YES** (новая таблица) · **auth/security/privacy: YES** (текст запросов покупателей; без идентификаторов, retention 90 дней, фильтр персональных данных, нет публичного чтения) · concurrency/atomicity: no (одна вставка после ответа) · data loss: no (события вспомогательные; потеря отдельного события при сбое допускается) · external service: no.

## 8. Acceptance criteria

1. Успешный submit / выбор подсказки / клик по чипу с `intent` создаёт ровно одно событие с полями §3.2; запрос без `intent` не создаёт; неверный `intent` → 400; ответ Search идентичен ответу без события.
2. Не создают события: смена сортировки, «По умолчанию», смена языка, восстановление (адрес, «Поиск», Back), показ подсказок/ввод символов.
3. Исходы корректны: известный Product → `resolved_product_id`, `selected`/`resolved`; ambiguous; unresolved; known-zero (Product + 0) и unresolved-zero различимы по полям.
4. Неудавшийся поиск не пишет событие; повтор после ошибки пишет одно при успехе.
5. Повтор того же запроса/Product в течение 60 с в той же вкладке не создаёт второго события; другой запрос — создаёт.
6. В событии нет идентификатора покупателя, исходного написания, IP/UA, точных координат; время — с точностью до часа; `geo_cell` — только при явной геолокации; запросы >100 символов или с цепочкой ≥ 6 цифр события не создают (Search работает).
7. Сбой записи (искусственный) не меняет ответ Search и не пишет текст запроса в лог.
8. События старше срока удаляются очисткой; срок конфигурируется.
9. `origin`: по умолчанию `dev`, `organic` только при явной конфигурации; synthetic-записи тестового хелпера помечены `synthetic` и не проходят как `organic`; публичный API не читает и не задаёт события/origin.
10. Backend ранжирование, eligibility, API-ответ, last-state, Nearby и существующие тесты Search не изменены.

## 9. Verification

Unit — нормализация, фильтр персональных данных, усечение времени, `geo_cell`, подавление повторов (клиентская логика), выбор `origin`; integration (изолированная БД) — вставка и поля, исходы (resolved/selected/ambiguous/unresolved/known-zero), отсутствие события без `intent`, сбой записи не ломает Search, retention-очистка, migration upgrade-путь; E2E mobile RU — submit, подсказка, чип дают по одному событию; сортировка/сброс/Back/восстановление/язык — ни одного; двойной Enter — одно; ошибка сети → повтор → одно; полный `pnpm verify`, branch CI. Synthetic-фикстуры — только для механики, помечены `synthetic`.

## 10. Manual acceptance (телефон, русский; dev-БД, `origin=dev`; события показывает агент SQL-выборкой по ходу, PO ничего технического не делает)

1. Ввести `баран`, выбрать «Баранина» → 1 событие: `suggestion`, Product, `result_count` > 0.
2. Сменить сортировку (цена, актуальность), выбрать «По умолчанию», сменить язык → новых событий нет.
3. Открыть карточку, Back; «Ещё» → «Поиск» → новых событий нет.
4. Ввести «Говядина», Enter → 1 событие `submit`. Тот же запрос ещё раз сразу → нового нет.
5. Ввести абракадабру (`zzqx`), Enter → событие `unresolved`, `result_count` 0, без Product.
6. Выбрать «Тунец» → событие `selected`, Product, `result_count` 0 (known-zero).
7. Клик по чипу → событие `chip`.
8. Агент показывает: нет идентификатора/исходного текста/координат; время усечено до часа; `origin=dev`.

## 11. STOP conditions

- Нужен идентификатор покупателя/сессии, точные координаты, исходное написание запроса или публичное чтение событий.
- Запись начинает влиять на ответ/задержку Search сверх допустимого или требует очереди/планировщика.
- Нужны агрегаты, затухание/blending, чипы, Seller UI, watch или изменение ранжирования.
- Нужна имитация реальных запросов в production.

## 12. Нерешённые решения PO (рекомендация первой)

1. **Идентификатор:** без любого идентификатора (рекомендуется; соответствует плану) — тогда D1 сможет считать **поиски**, но не **уникальных людей**; либо отдельным решением с доказанной необходимостью (напр., короткоживущий неперсистентный dedupe-токен) — позже, не в D0.
2. **Точность времени:** час (рекомендуется) или день.
3. **Текст запроса:** только нормализованный + фильтр длины/цифр (рекомендуется); либо дополнительно хранить исходное написание (не рекомендуется).
4. **Геолокация:** грубая ячейка 0,05° только при явной геолокации (рекомендуется — иначе D3 потеряет данные), либо вообще без гео в D0.
5. **Чипы:** писать клик по чипу как `chip` (рекомендуется) или не писать.
6. **Окно подавления повторов:** 60 с в памяти вкладки (рекомендуется) / другое.
7. **Retention-очистка** оппортунистически при записи (рекомендуется) или отдельным операторским запуском.
8. **Конфигурация `origin`:** `organic` только по явной переменной боевого окружения, по умолчанию `dev` (рекомендуется).
9. **Сбой записи:** ожидаемая запись в `try/catch` без retry (рекомендуется) либо фоновая запись.
