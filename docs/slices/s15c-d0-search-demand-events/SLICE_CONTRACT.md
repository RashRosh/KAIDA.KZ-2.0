## 1. User task (внутренняя)

Оператор получает best-effort события «осознанный поиск покупателя → исход» без влияния на работу Search и без накрутки служебными действиями (смена сортировки, Back, восстановление, перезагрузка).

## 2. Фактическое поведение на `main` (evidence)

- Событий поиска нет. `/api/search` (GET/POST) вызывается без признака намерения при: submit, выборе подсказки, клике по чипу, смене сортировки, смене языка, восстановлении по адресу/last-state/Back, повторе после ошибки.
- Вход с First Entry (`/welcome`): форма делает `router.push('/?q=…')` — клиентская навигация, которую `SearchScreen` обрабатывает как восстановление по адресу (без намерения). Других ссылок на `/?q=` в buyer UI нет.
- Результат содержит `resolvedProduct` (выбранный, найденный по `productId`, иначе exact resolver — S15B-4a) и все допустимые Offers (**лимита выдачи нет**); known-zero = `resolvedProduct ≠ null` и 0 Offers (S15B-2).
- Сервер не хранит идентификаторов покупателя. Пул БД: `max: 5`, `connectionTimeoutMillis: 5000`, `statement_timeout` не задан.

## 3. Behavior

### 3.1 Что такое один осознанный поиск
Событие создаёт **успешный** Search (200), запущенный осознанным действием:
- **`submit`** — Enter или «Искать» с введённым текстом (экран результатов, Search Home, **First Entry**);
- **`suggestion`** — выбор Product в подсказках;
- **`chip`** — клик по curated-чипу (отличим от submit/suggestion).

Не создают событие: ввод символов и подсказки; смена сортировки и «По умолчанию»; смена языка и перезапрос карточек; восстановление по адресу, «Поиск», Back, **перезагрузка страницы**; любой запрос без признака намерения (в т. ч. внешний API-клиент). «Сообщить, когда появится», «Искать как введено», watch — не D0.

### 3.2 Поля события (без идентификатора, без гео)
- `occurred_at` — **час** (усечение);
- `entry` — `submit` | `suggestion` | `chip`;
- `query_normalized` — как `searchWords` (нижний регистр, ё→е, без пунктуации), без исходного написания;
- `resolved_product_id` — `resolvedProduct.id` **ответа** или `NULL`;
- `resolution` — `selected` | `resolved` | `ambiguous` | `unresolved` (правила — §3.7);
- `result_count` — **число Offers, возвращённых в ответе** (см. §3.7);
- `origin` — `organic` | `dev` | `test` | `synthetic` (§3.6).

**Нет:** `user_id`, session/device/anonymous key и любого постоянного/сессионного идентификатора; IP, user agent, locale; исходного написания; **никакой геолокации** (ни точек, ни ячеек, ни радиуса — buyer location в запросе для Search не даёт права собирать локацию спроса; гео — только отдельным утверждённым контрактом); перечня Offers/продавцов.

### 3.3 Признак намерения и его одноразовая передача
- Необязательный параметр `intent` (`submit|suggestion|chip`) в GET и POST `/api/search`; без него ответ прежний и событие не пишется; невалидное значение → `400`. Ответ Search не меняется.
- **Точки входа и их намерение:**
  1. Форма на экране результатов/Search Home → `submit`; выбор подсказки → `suggestion`; чип → `chip` — `intent` передаётся в том же вызове `executeSearch`.
  2. **First Entry** (`/welcome`, `router.push('/?q=…')`): перед навигацией форма кладёт **одноразовый in-memory handoff** `{ нормализованный q, entry: 'submit', время }` в модульную переменную клиента; `SearchScreen` при обработке адреса **потребляет** handoff (читает и очищает) и использует его, только если нормализованный `q` совпал и прошло ≤ 15 с.
- **Почему нет повторов (reload/Back/restoration):** handoff не пишется в URL, `sessionStorage`, last-state или куки; потребляется один раз; перезагрузка и «полная» навигация обнуляют модульное состояние; Back/«Поиск»/восстановление запускаются без handoff ⇒ без `intent`. Closed-поведение адреса `/?q=…[&product=…]` и `kaida:last-search` не меняется (формат, чтение, восстановление, Back).
- **Намерение до успеха:** UI хранит ожидающее намерение (в памяти, ссылкой) до первого успешного ответа; ручной «Повторить» после ошибки несёт его снова. Перезагрузка стирает его (событие теряется, не воспроизводится).

### 3.4 Подавление повторов (эвристика, 60 с, в памяти вкладки)
- **Ключ:** `нормализованный q` (тот же `searchWords`-вид, что в событии) + `\0` + `productId` выбранного Product (пусто, если выбора нет). `entry` в ключ **не входит**.
- **Окно:** 60 секунд, отсчёт от **последнего успешного (200) ответа на запрос с `intent` по этому ключу**; хранится в памяти страницы (до 10 ключей), не в `sessionStorage`, не на сервере.
- Повтор по ключу внутри окна идёт **без `intent`** (событие не пишется). Другой запрос или тот же текст с другим `productId` (напр., ввод руками vs выбор подсказки) — новое событие. Окно не продлевается подавленными повторами.
- Перекрывающиеся запросы: уже существующий guard (`pending`) отклоняет второй `executeSearch`, пока первый в полёте, — второй submit не создаёт запроса.
- Это эвристика против случайных повторов, не защита от злоумышленника: `intent` может быть подделан клиентом; общий rate limit и quality-фильтры — D1/Anti-abuse.

### 3.5 Семантика доставки (best-effort, не exactly-once)
Гарантии **нет ни «ровно одного», ни «не менее одного»**: каждый запрос с `intent` пишет **не более одного** события; возможны оба вида отклонений.
- **Дубль:** ответ потерян после записи события, клиент не видит успеха и повторяет с тем же намерением → два события (серверной идемпотентности нет; идентификатор ради неё не вводится).
- **Потеря:** запись упала/не уложилась в бюджет (§3.8), превысила лимит одновременных записей, либо подавление окна 60 с скрыло повтор при тихо потерянном первом событии; перезагрузка до успеха.
- Неудавшийся поиск (не 200) события не создаёт. Ошибка записи события ответ Search не меняет.

### 3.6 Происхождение данных, synthetic fixtures
- `origin` задаёт сервер из `SEARCH_EVENTS_ORIGIN`: **по умолчанию `dev`**; `organic` — только при явной настройке боевого окружения; тестовые прогоны — `test`. Публичный API не задаёт origin.
- **Synthetic** fixtures — только тест-хелпер с `origin = 'synthetic'`, прямая запись в тестовую БД; в production-коде такого пути нет. Реальные запросы не имитируются; гипотетические счётчики — не популярность.
- Будущая аналитика (D1) читает только `organic` (в D0: ограничение значений поля + тест). Blending, затухание, агрегаты, замена curated-контента — не D0.

### 3.7 Семантика исхода
- **`result_count`** — число Offers **в возвращённом ответе** (не «всего совпадений»). Сейчас лимита выдачи нет, поэтому оно равно числу допустимых совпадений; при будущем лимите/пагинации поле остаётся «возвращено», а смысл «всего совпадений» потребует ревизии контракта.
- **Product и `resolution` следуют ответу:** `resolved_product_id = resolvedProduct?.id`. Это Product, **о котором сообщил ответ Search**, а не доказанное предпочтение покупателя и не обязательно Product, применимый для L1 релевантности (S15B-4b).
  - `productId` в запросе найден в каталоге → Product = выбранный, `resolution = selected` (приоритет выбора, как в 4a) — в т. ч. если exact resolver по тексту вернул **другой** Product или не нашёл/неоднозначен: событие фиксирует то, что Search показал покупателю; отдельного состояния «конфликт» нет (UI не создаёт рассогласования: правка текста сбрасывает выбор — конфликт возможен только при подмене клиента);
  - `productId` **устарел/не найден** → игнорируется, Product и `resolution` определяет resolver по тексту;
  - resolver `resolved` → Product = найденный, `resolution = resolved`; `ambiguous` → `NULL`, `ambiguous`; иначе `NULL`, `unresolved`.
- Known-zero (Product ≠ NULL, 0) и unresolved-zero (NULL, 0) различимы.

### 3.8 Ограниченная запись: бюджет времени и сбой
- Событие пишется **после** готового ответа, до его отправки. Бюджет **250 мс** (конфигурируемо) — **дополнительная граница ожидания записи, а не гарантия, что весь запрос Search укладывается в 250 мс**: `Promise.race` между записью и таймером; по истечении Search возвращает обычный ответ. `Promise.race` запись **не отменяет**: она дорабатывает или падает самостоятельно, поздняя ошибка перехвачена (без `unhandledRejection`), слот лимита одновременных записей **удерживается до фактического завершения операции**, транзакция гарантированно завершается (COMMIT/ROLLBACK), соединение возвращается в пул (при ошибке — освобождается с признаком ошибки).
- **Таймаут БД:** запись идёт в короткой транзакции с `SET LOCAL statement_timeout = <бюджет>`; **получение соединения** не ограничено пулом (5 с) — поэтому его покрывает общий таймер бюджета, а число **одновременно незавершённых записей ограничено** (например, 3): сверх лимита событие пропускается, чтобы медленная БД не занимала пул Search.
- **Сбой не делает успешный Search ошибкой:** вся запись обёрнута в `try/catch` + бюджет; лог `Search event failed` — **без текста запроса и без любых данных запроса**. Нет очереди, retry и фоновых задач.
- Доказательства (тесты, §9): запись падает → ответ 200 тот же; запись «зависает» → ответ в пределах бюджета; соединение не выдаётся (пул исчерпан) → ответ в пределах бюджета; медленная вставка (блокировка таблицы) → статемент-таймаут, ответ 200, события нет; лог без текста.

### 3.9 Приватность
- События внутренние: **нет публичного чтения** (ни Seller, ни buyer API).
- Запросы длиннее 100 символов или с цепочкой ≥ 6 цифр (пробелы, дефисы, точки, скобки и плюс между цифрами игнорируются) событие **не создают** (Search работает). Это снижает риск, но **не гарантирует отсутствие персональных данных** в `query_normalized` (свободный текст может содержать имена и иное); поэтому событие внутреннее, без идентификаторов, с ограниченным сроком хранения.
- В логах событий и ошибок текста запросов нет.

### 3.10 Retention (честная формулировка)
- Срок хранения сырых событий — **90 дней** (`SEARCH_EVENTS_RETENTION_DAYS`); **фактическое хранение — 90 дней плюс интервал очистки (сутки)** при условии успешного регулярного выполнения. Приложение само срок **не гарантирует**: Next.js-сервер не имеет планировщика, а удаление «при записи» не работает, когда поисков нет.
- Механизм: **операторская команда очистки** (идемпотентная: удаляет события старше срока, печатает число удалённых и возраст самого старого оставшегося), которую оператор запускает внешним планировщиком **не реже раза в сутки** (процедура описывается в runbook). Дополнительно, как страховка, очистка ограниченной пачки выполняется иногда при записи (не заменяет команду).
- Ограничение раскрыто: срок соблюдается ровно настолько, насколько оператор запускает команду. **Organic-запись остаётся выключенной, пока расписание очистки не настроено и не проверено** (условие запуска, а не гарантия кода): `SEARCH_EVENTS_ORIGIN=organic` включается в боевом окружении только после проверенного ежедневного запуска. Операторская процедура: `pnpm search-events:purge` (опция `--dry-run` показывает число и возраст без удаления).

## 7. Risk flags

public API: **YES** (additive `intent`) · **DB migration: YES** · **auth/security/privacy: YES** (текст запросов; без идентификаторов и гео; внутренние; retention через операторскую процедуру; фильтры не гарантируют отсутствие ПД) · concurrency/atomicity: **YES, ограниченно** (лимит одновременных записей и бюджет времени вокруг одной вставки; без транзакционной связи с Search) · data loss: no (события вспомогательные; потеря/дубль допустимы) · external service: no.

## 8. Acceptance criteria

1. Запрос с `intent` (submit / suggestion / chip / First Entry) после успешного ответа пишет не более одного события с полями §3.2; без `intent` не пишет; неверный `intent` → 400; ответ Search идентичен.
2. Не создают событий: сортировка, «По умолчанию», язык, восстановление (адрес, «Поиск», Back), **перезагрузка** страницы, показ подсказок.
3. First Entry: поиск оттуда пишет одно событие; перезагрузка `/?q=…`, Back и повторное открытие адреса — ни одного (handoff потреблён/сброшен); URL и last-state прежние.
4. Исходы §3.7: выбранный Product, resolver, ambiguous, unresolved, known-zero; устаревший `productId` игнорируется; конфликт выбор≠resolver фиксирует Product ответа.
5. Неудавшийся поиск не пишет событие; повтор после ошибки несёт ожидающее намерение (пишется при успехе); дубль при потерянном ответе — допустим и документирован.
6. Подавление 60 с: тот же ключ (нормализованный `q` + `productId`) в окне — без события; иной ключ — событие; окно от последнего успешного ответа.
7. В событии нет идентификатора, исходного текста, IP/UA, гео; время — час; запросы >100 символов / ≥ 6 цифр подряд — без события; в логах нет текста запроса.
8. Сбой/зависание/нехватка соединения/блокировка таблицы: ответ Search 200, тот же, в пределах бюджета; при превышении лимита записей событие пропускается.
9. Операторская очистка удаляет события старше срока и сообщает счётчик; срок конфигурируется; в контракте и runbook раскрыто, что гарантия зависит от запуска.
10. `origin` по умолчанию `dev`; `organic` только по явной настройке; synthetic помечены `synthetic` и не проходят как `organic`; публичного чтения/записи origin нет.
11. Ранжирование, eligibility, API-ответ, URL, last-state, Nearby и существующие тесты Search не изменены.

## 9. Verification (агентская; PO её не выполняет)

Unit — нормализация, фильтры длины/цифр, усечение времени, ключ и окно подавления, одноразовый handoff (потребление, истечение, несовпадение), выбор `origin`, правила исхода §3.7; integration (изолированная БД) — вставка и поля, исходы, отсутствие события без `intent`, сбой записи / зависание / исчерпанный пул / блокировка таблицы → 200 в пределах бюджета и лог без текста, лимит одновременных записей, очистка, migration upgrade-путь; E2E mobile RU — submit/подсказка/чип/First Entry дают по одному событию; сортировка/«По умолчанию»/язык/Back/«Поиск»/перезагрузка — ни одного; двойной Enter — одно; ошибка сети → «Повторить» → событие при успехе; полный `pnpm verify`, branch CI. **SQL-проверка таблицы событий — часть агентской верификации; результат отчитывается PO, но не является его действием.** Synthetic-фикстуры — только для механики, помечены `synthetic`.

## 10. Manual acceptance (PO, телефон, русский — только поведение покупателя)

D0 невидим для покупателя, поэтому приёмка подтверждает, что **Search ведёт себя как раньше** во всех входах:
1. Первый вход (`/welcome`): ввести запрос → результаты как раньше; перезагрузить страницу и нажать Back — результаты как раньше, без ошибок.
2. `баран` → выбрать «Баранина»; чип; Enter в поле — всё работает, скорость прежняя.
3. Смена сортировки, «По умолчанию», язык, карточка → Back, «Ещё» → «Поиск» — как раньше.
4. Двойной быстрый Enter; запрос без результатов («zzqx») и «Тунец» — прежние тексты.
5. Отчёт агента (отдельно, не действие PO): по таблице событий — число, поля и отсутствие запрещённых данных соответствуют §8.

## 11. STOP conditions

- Нужен идентификатор покупателя/сессии, любая геолокация, исходное написание или публичное чтение событий.
- Запись начинает влиять на результат или заметно на время Search либо требует очереди/планировщика внутри приложения.
- Нужны агрегаты, затухание/blending, чипы, Seller UI, watch, изменение URL/last-state или ранжирования.
- Нужна имитация реальных запросов в production.

## 12. Решения PO (приняты) и остаток

Приняты PO: (1) без идентификаторов, метрики = события; (2) час; (3) только нормализованный запрос, фильтры длины/цифр без гарантии отсутствия ПД, без текста запросов в логах; (4) без гео в D0; (5) чипы пишутся как `chip`; (6) подавление 60 с — эвристика, ключ §3.4; (7) `origin=dev` по умолчанию, `organic` явно, synthetic только тестовые; (8) ограниченная ожидаемая best-effort запись без очереди и автоматического retry.

Решения по остатку приняты PO (2026-10-07): (1) ежедневная операторская очистка принята, organic выключен до настроенного и проверенного расписания, фактическое хранение = 90 дней + интервал очистки; (2) бюджет 250 мс (дополнительная граница, не гарантия времени запроса) и лимит 3 незавершённых записей с удержанием слота до завершения операции; (3) при конфликте фиксируется Product ответа (с оговоркой §3.7); (4) one-shot in-memory handoff First Entry принят — тесты: одноразовое потребление, истечение, несовпадение запроса, перезагрузка, Back.

Было к утверждению:
1. **Retention:** согласиться с операторской командой очистки (раз в сутки внешним планировщиком) как механизмом, с раскрытым ограничением, и с условием «`organic` только после настройки очистки» (§3.10).
2. **Бюджет записи:** 250 мс и лимит одновременных записей 3 — приемлемые значения по умолчанию?
3. **Правило конфликта** (§3.7): при выборе, не согласованном с текстом, событие фиксирует Product ответа (выбор) — принять.
4. **One-shot handoff** для First Entry (in-memory, ≤ 15 с, без URL/last-state) — принять как способ учесть первый поиск без изменения закрытого URL/last-state поведения; альтернатива — не считать First Entry (потеря самого первого поиска каждого нового покупателя).
