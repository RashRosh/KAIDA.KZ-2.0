## 1. User task

Покупатель, у которого уже есть результаты поиска, явно выбирает порядок подходящих предложений — по **расстоянию**, по
**цене** или по **актуальности** — и может развернуть направление выбранного порядка. Выбранный критерий на экране — это
настоящий первичный порядок: скрытого взвешенного ранжирования, которое ему противоречит, нет.

## 2. Фактическое поведение на `main` (evidence)

- UI: кнопка «Фильтры» открывает bottom sheet с сортировкой («Сначала ближе» / «Сначала актуальнее»), радиусом
  1 / 3 / 5 км / «Любое», «Показать N предложений», «Сбросить», чипами применённых фильтров, счётчиком и summary.
  Радиус — клиентская фильтрация; выбор «Сначала ближе» или радиуса — явный запрос геолокации.
- API: `GET /api/search?q&sort` и `POST /api/search` (`q`, `buyerLocation`, `sort`), `sort ∈ {actuality, distance}`;
  отсутствие — `actuality`; неизвестное значение — `400 INVALID_SEARCH_REQUEST`; POST строгий (лишние поля отвергаются).
  `distanceMeters` в DTO есть только в запросе с локацией.
- Ранжирование: сначала жёсткий слой «свежие выше ageing» (`compareActualityTier`), внутри слоя — взвешенный score
  (веса из серверной политики `SEARCH_RANKING_WEIGHTS_*`), в `distance` geo-known перед geo-less; без координат —
  чистая свежесть → id.
- Состояние 6C (`sessionStorage`): запрос + `sort` + `radiusMeters`, формат `v: 1`; без координат distance и конечный
  радиус нормализуются в «актуальность»/«Любое».
- Nearby (S11) использует `compareActualityTier` и `distanceMetersForRanking` из того же модуля ранжирования.

## 3. Behavior

### 3.1 Контрол сортировки (UI)
В режиме выдачи вместо bottom sheet «Фильтров» — компактный popover, привязанный к существующей кнопке рядом с полем
поиска. В нём **ровно три строки**: `Расстояние`, `Цена`, `Актуальность`.

- Нет: bottom sheet, радиуса, summary, счётчика активных фильтров, чипов применённых фильтров, «Показать N», «Сбросить»,
  черновика/применения, отдельного empty-состояния «из-за фильтров». Диапазон цены Rev 2 не вводится.
- Выбор применяется сразу, без шага подтверждения. Активный критерий и его направление наглядны (стрелка и/или текст,
  не только цвет); доступное имя строки содержит критерий, направление и состояние.
- Нажатие на неактивный критерий делает его активным с его естественным направлением; нажатие на уже активный меняет
  направление. Popover остаётся открытым после выбора и закрывается по нажатию вне него, `Esc` или повторному нажатию на
  кнопку; фокус и клавиатура — по `PROJECT_RULES.md` §18.4 (Overlay): фокус входит один раз, возвращается на кнопку, не
  перехватывается при смене состояния.
- Search Home (6C) без изменений: на нём контрола сортировки нет.
- Отдельный кадр дизайнера не нужен: композиция из существующих токенов и классов Search; визуальную приёмку проводит PO.

### 3.2 Семантика порядка
Критерии `actuality | distance | price`, направления `asc | desc`.

| Критерий | По умолчанию | `asc` | `desc` |
|---|---|---|---|
| actuality | `desc` | старее первыми | свежее первыми |
| price | `asc` | дешевле первыми | дороже первыми |
| distance | `asc` | ближе первыми | дальше первыми |

- Выбранный критерий — **первичный порядок среди всех buyer-eligible предложений**. Слой «свежие выше ageing» и
  взвешенный score больше не владеют этими режимами (явная ревизия, §6).
- Подходящесть (buyer eligibility) и пороги lifecycle/actuality **не меняются**: сортировка не делает предложение
  видимым и не скрывает видимое.
- Tie-breakers: `price` → свежее первыми → стабильный `Offer.id`; `distance` → свежее первыми → `Offer.id`;
  `actuality` → `Offer.id` при равной актуальности. Скрытого взвешенного score после явной сортировки нет.
- По умолчанию (нет выбора) — `actuality`, `desc`.

### 3.3 Цена
Сравнивается только числовая номинальная сумма KZT (`price.amount`, десятичная строка): единицы и размеры упаковки не
нормализуются и не конвертируются. Пример: `800 ₸ / упак.` идёт раньше `1000 ₸ / кг` при возрастании цены. Инвариант цены
buyer-visible предложения не меняется.

### 3.4 Расстояние и геолокация
Выбор `Расстояние` — явное геолокационное намерение покупателя.

- Нет текущих координат → браузерная геолокация запрашивается из-за этого действия; разрешили → применяется сортировка по
  расстоянию; отказ/недоступность → эффективная сортировка возвращается в `actuality`/«свежее первыми» (и в UI, и в
  состоянии), показывается краткое сообщение, что для сортировки по расстоянию нужен доступ к местоположению.
- Геолокация не запрашивается автоматически только потому, что прежний поиск использовал distance; не запрашивается при
  восстановлении состояния; не запрашивается без явного выбора `Расстояние`.
- Предложения без координат остаются видимыми в обычном Search (Stage 5A). При сортировке по расстоянию все geo-known
  идут перед всеми geo-less при **обоих** направлениях; внутри geo-known первичен фактический distance; geo-less не
  получают выдуманного расстояния и упорядочиваются между собой «свежее первыми → `Offer.id`».
- Сырые координаты не сохраняются и не публикуются; в DTO остаётся только производное `distanceMeters` запроса с
  локацией.

### 3.5 Публичный Search API
Канонический запрос: `sort=actuality|distance|price`, `direction=asc|desc`.

- `GET /api/search?q&sort&direction` и `POST /api/search` (`q`, `buyerLocation`, `sort`, `direction`).
- `sort` не указан → `actuality`; `direction` не указан → естественное направление выбранного `sort`
  (actuality → `desc`, price → `asc`, distance → `asc`).
- Политика ошибок сохраняется: неизвестные `sort` или `direction`, лишние поля POST → `400 INVALID_SEARCH_REQUEST`.
  `sort=cheaper` — не поддерживается (никогда не выходил в `main`).
- `sort=distance` **требует координат покупателя**. Без `buyerLocation` — `400 INVALID_SEARCH_REQUEST`: API не принимает
  `distance` и не сортирует фактически по другому критерию (инвариант Rev 3: запрошенная и видимая сортировка — реальный
  первичный порядок). `GET` координат не несёт, поэтому `GET ... sort=distance` всегда `400`; сортировка по расстоянию —
  через `POST` с `buyerLocation`.
- UI не отправляет такой запрос: до отправки он получает геолокацию по явному действию; при отказе/недоступности
  нормализует состояние в `actuality`/`desc` и отправляет уже запрос `actuality`; восстановление прежнего `distance`
  без координат нормализуется в `actuality`/`desc` до вызова API. Обычный сценарий UI не получает этот `400`.
- Форма DTO не меняется; `distanceMeters` — только при запросе с локацией, как сейчас.
- Серверная политика весов (`SEARCH_RANKING_WEIGHTS_*`) выводится из эксплуатации: явные режимы больше не используют
  веса. Результат сортировки по-прежнему определяется только сервером (клиент не сортирует и не подставляет веса).

### 3.6 Состояние последнего поиска (6C)
Состояние вкладки хранит только текущие валидные предпочтения Search: **запрос, `sort`, `direction`**. Радиус исчезает из
модели. Результаты и координаты не сохраняются. Возврат на `Поиск` — как в 6C (явный адрес `/?q=…`, результаты
запрашиваются заново).

Совместимость минимальна, без фреймворка миграций; ранее сохранённое значение должно безопасно деградировать:

- валидный сохранённый запрос сохраняется; устаревший радиус отбрасывается;
- прежнее состояние «актуальность» → `actuality` + `desc`;
- прежнее состояние `distance` без текущих координат → `actuality` + `desc`;
- `price` с направлением (формат Rev 3) восстанавливается как есть; геолокация при восстановлении не запрашивается;
- повреждённое/чужое значение → Search Home, как в 6C.

Исторические контракты не переписываются: этот контракт явно заменяет только перечисленное поведение.

- **S9 Search ranking:** явный выбранный критерий становится первичным порядком; взвешенный score не владеет явными
  режимами; жёсткий слой «свежие выше ageing» при явной сортировке не действует (в том числе при `actuality`: `asc`/`desc`
  — по возрасту напрямую).
- **Stage 5A `search-visibility-without-coordinates`:** обычная видимость geo-less предложений сохраняется;
  правило «geo-known перед geo-less» для расстояния сохраняется и уточняется как независимое от направления.
- **UX1C (явное геонамерение):** выбор `Расстояние` — явное геонамерение; отказ → безопасный возврат к актуальности с
  кратким сообщением.
- **Offer actuality / lifecycle (#31):** eligibility и пороги не меняются; актуальность теперь также явный критерий
  сортировки.
- **6C `search-home-last-state`:** из сохраняемых предпочтений уходит радиус, добавляется направление; нормализация без
  координат расширяется до `distance → actuality/desc`.
- **Публичный Search API (S0/S7, Stage 5):** аддитивный параметр `direction`, значение `price` в `sort`; `cheaper` не
  существует; `sort=distance` без `buyerLocation` (ранее принимался и сортировал по свежести) теперь `400 INVALID_SEARCH_REQUEST`.
- **Отклонённый `search-price-sort-range` Rev 2:** остаётся superseded и неслитым evidence, не целью совместимости.

Не затрагиваются: S11 Nearby, S6/S10, seller-контракты, offer-price-unit и mandatory-offer-price (гарантии цены
переиспользуются как предусловие сортировки), First Entry, inline-язык.

## 7. Risk flags

1. В режиме выдачи вместо листа есть popover с ровно тремя строками `Расстояние`, `Цена`, `Актуальность`; нет листа,
   радиуса, summary, счётчика, чипов фильтров, «Показать N», «Сбросить», empty-состояния фильтров; на Search Home
   контрола нет.
2. По умолчанию — `actuality`/`desc` (свежее первыми). Выбор применяется сразу; активный критерий и направление видны не
   только цветом.
3. Нажатие на неактивный критерий включает его с естественным направлением (price → дешевле первыми, distance → ближе
   первыми, actuality → свежее первыми); нажатие на активный — меняет направление.
4. Выбранный критерий — первичный порядок среди всех подходящих предложений при обоих направлениях; tie-breakers
   (свежее → `Offer.id`) детерминированы; слой «свежие выше ageing» и веса при явной сортировке не действуют.
5. Цена сравнивается по номинальной сумме KZT без нормализации единиц (`800 ₸ / упак.` перед `1000 ₸ / кг` при
   возрастании); eligibility и пороги lifecycle не изменились.
6. `Расстояние` без координат запрашивает геолокацию только из-за этого выбора; разрешено — сортировка применена;
   отказ/недоступность → `actuality`/`desc` и краткое сообщение о необходимости доступа к местоположению (UI и состояние
   согласованы).
7. При сортировке по расстоянию все geo-known перед всеми geo-less при `asc` и `desc`; geo-less не получают расстояния;
   предложения без координат остаются видимыми.
8. API: `sort=actuality|distance|price`, `direction=asc|desc`; значения по умолчанию по таблице §3.2; неизвестные значения
   и лишние поля → `400 INVALID_SEARCH_REQUEST`; `sort=cheaper` отвергается; DTO без изменений; `sort=distance` без
   `buyerLocation` (в том числе любой `GET`) → `400 INVALID_SEARCH_REQUEST`; обычный UI-сценарий этот `400` не получает
   (геолокация до запроса, при отказе — актуальностью).
9. Состояние 6C хранит запрос, `sort`, `direction` (без радиуса, результатов и координат); прежнее состояние
   деградирует по правилам §3.6; при восстановлении геолокация не запрашивается, `distance` нормализуется.
10. Приватность: сырые координаты не пишутся в `sessionStorage`/`localStorage`/cookie/URL и не попадают в DTO; запроса
    геолокации без явного выбора `Расстояние` нет.
11. Nearby (S11) и общие хелперы ранжирования ведут себя как прежде; First Entry, inline-язык, Search Home 6C не изменены.
12. Существующие проверки, которые прямо утверждают отменённое поведение (лист «Фильтры», радиус, взвешенный порядок
    Stage 5/S9), обновлены или сняты как устаревшие; остальная регрессия проходит.

## 9. Verification

- **Unit:** сравнение по каждому критерию и направлению; tie-breakers; geo-known перед geo-less при обоих направлениях;
  номинальная цена с разными единицами; схема запроса (значения по умолчанию, неизвестные значения, лишние поля,
  `cheaper`); последнее состояние (формат Rev 3, деградация прежнего, отсутствие радиуса/координат).
- **Integration (БД):** `GET`/`POST` с `sort`/`direction` на фикстурах с разными ценой, единицей, свежестью, расстоянием и
  geo-less предложением; DTO и приватность (нет сырых координат); неверные параметры → 400; `sort=distance` без координат → 400.
- **E2E (mobile RU):** композиция popover (ровно три строки, отсутствие снятых элементов), значения по умолчанию,
  переключение направления, мгновенное применение, порядок по цене со смешанными единицами, distance с подменой
  геолокации (оба направления, geo-less после), отказ геолокации → актуальность + сообщение, отсутствие запроса
  геолокации без выбора `Расстояние`, восстановление через `Поиск` (price + direction сохраняются, distance → актуальность,
  без запроса геолокации), содержимое `sessionStorage`, Search Home без контрола.
- Полная регрессия и branch CI на точном SHA.

## 11. Manual acceptance (телефон, русский, после First Entry)

1. Найти «Баранина»: рядом с полем кнопка сортировки; на Search Home её нет.
2. Нажать её: рядом открывается компактный popover из трёх строк — `Расстояние`, `Цена`, `Актуальность`; активна
   `Актуальность` (свежее первыми), листа и радиуса нет.
3. Нажать `Цена`: сразу «дешевле первыми»; нажать `Цена` ещё раз — «дороже первыми», стрелка меняется.
4. Нажать `Актуальность` — порядок по свежести; ещё раз — «старее первыми».
5. Нажать `Расстояние`, разрешить геолокацию: «ближе первыми», предложения без координат в конце; нажать ещё раз —

6. Запретить геолокацию в браузере и нажать `Расстояние`: остаётся «актуальность», краткое сообщение о доступе.

   выбрать `Расстояние`, уйти и вернуться: актуальность, диалога геолокации нет.
