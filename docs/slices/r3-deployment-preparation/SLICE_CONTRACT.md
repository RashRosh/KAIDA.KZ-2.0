# Slice Contract — R3: Воспроизводимая подготовка развёртывания (без хостинга)

**Статус: APPROVED — IMPLEMENTATION AUTHORIZED (PO, 2026-10-09; одобрен после уточнений §3.2–§3.5).** Контейнерный образ как формат поставки, локальные Hadolint и Trivy в рамках R3 и минимальный `GET /api/health` одобрены. Реализация — в отдельной ветке; merge и checkpoint tag — только после ручной приёмки PO. При нехватке памяти сборки: отчёт с доказательствами и минимальным предложением; ресурсы Docker Desktop без одобрения PO не менять; обычные настройки сборки в границах scope допустимы. Часть Local readiness track (`EXECUTION_PLAN.md`, R3); продолжение R1 (`v0.0.62`) и R2 (`v0.0.64`). Рекомендуемый reasoning effort реализации: **high** (инфраструктура, секреты, security).

## 1. Цель

Из чистого checkout можно **воспроизводимо собрать образ приложения и поднять эталонный стек** (приложение + PostgreSQL + постоянный том фото) **на проверенной платформе (§3.3)**, имея только файл окружения: проверка конфигурации, миграции, импорт Production KB, работа за TLS-прокси с Secure-cookie, сохранность данных при перезапуске, backup/restore средствами R2. Всё проверяется локально и изолированно. **Хостинг-провайдер не выбирается, ничего не покупается, публичный запуск не разрешается, запись `organic` не включается.**

## 2. Что показало чтение кода и документов

- `Dockerfile` нет; `next.config.ts` минимален; `pnpm start` = `next start`. Образ собирается с нуля.
- `drizzle-kit` и `tsx` — devDependencies: миграции, `db:import:production-kb`, `backup:*`, `search-events:purge` без них не запустятся. Нужны два target: runtime и tools.
- Endpoint здоровья нет; приложение не читает `X-Forwarded-*`/Host-заголовки (поиск по `src`): TLS-прокси нужен ему только ради Secure-cookie.
- Фоновая работа в процессе: `src/instrumentation.ts` (напоминания раз в 15 мин при VAPID-ключах, с DB-lock; переводчик по умолчанию `off`). Процесс предполагается **один**.
- **Test OTP:** код входа возвращается клиенту (`delivery.code`) и показывается в окне входа. Любой достижимый из сети экземпляр позволяет войти под любым телефоном. R3 это не меняет (O-AUTH), поэтому **доступ к эталонному стеку ограничивается технически, а не предупреждением** (§3.2).
- R2 guards отказывают для баз `kaida`/`kaida_test`, хост-порта 5432 и compose-проекта корня репозитория; эталонный стек обязан их соблюдать.
- Машина PO: Windows 11, Docker Desktop 29.8 (сервер `linux/amd64`, ВМ с ≈3,7 ГБ памяти, 12 CPU), Node 24.14. Сборка `next build` на слабой машине ранее падала перемежающимся образом (R1).
- `SECURITY_AUTOMATION.md`: production `Dockerfile` — триггер стопа; PO авторизовал Hadolint и Trivy локально в рамках R3 (§3.5).

## 3. Решение (предлагается)

### 3.1 Результат (deliverables)

1. **`Dockerfile` + `.dockerignore`.** Многоэтапная сборка, база Node 24 по `.node-version` (тег и digest записываются в отчёт), `pnpm install --frozen-lockfile`, непривилегированный пользователь. Target `runtime` (`next start`) и `tools` (полные зависимости: миграции, импорт KB, backup, purge). В образ не попадают `.env`, `tmp/`, `scripts/`, `.vscode/`, `.mimosa/`, `.pnpm-store/`, `.data/`, логи.
2. **Эталонный стек `ops/deployment/`.** Compose-проект `kaida-deploy-check`: `app`, одноразовые `migrate`/`import-kb` (target `tools`), `postgres` (наружу **не** публикуется), именованные тома БД и фото; база не называется `kaida`/`kaida_test`. `env.template` без секретов и дефолтных паролей. Справочный пример для Docker-хоста, не конфигурация провайдера.
3. **`pnpm deploy:preflight`** — проверка конфигурации и безопасности доступа до старта; секреты не печатает. Проверяет: обязательные переменные; `IDENTITY_OTP_HMAC_SECRET_HEX` (64 hex); `IDENTITY_COOKIE_SECURE=true`; каталог фото доступен для записи; БД доступна; нет неприменённых миграций; Production KB установлена (682 / 210 / 35); **адрес публикации порта (§3.2)**; `SEARCH_EVENTS_ORIGIN=organic` → **отказ** («заблокировано до O-D0-ORG»).
4. **`pnpm deploy:up`** — единственный поддерживаемый запуск: preflight → compose. Прямой `docker compose up` тоже безопасен по умолчанию (§3.2), но не проверяет остальное.
5. **`GET /api/health`** — 200 при живом процессе и доступной БД, иначе 503; без данных, без аутентификации, `no-store`. Единственное изменение кода приложения.
6. **Runbook `docs/ops/DEPLOYMENT.md`** + ссылка из README: сборка, env (таблица «обязательно / необязательно / запрещено» с источниками), первый запуск, обновление, откат, перезапуск, backup/restore через R2, границы (§4), раздел «проверено / ожидается / не проверено» (§3.3, §6).

### 3.2 Безопасный доступ по умолчанию (Test OTP)

- Опубликованные порты эталонного стека привязаны к **loopback**: `127.0.0.1:${KAIDA_APP_PORT}` (по умолчанию значение из env.template). Порт PostgreSQL наружу не публикуется никогда.
- Доступ из локальной сети — только сознательно, для **приватного тестирования**: нужно явно задать `KAIDA_BIND_ADDRESS=<частный IP хоста>` **и** `KAIDA_PRIVATE_TEST_ACK=yes`. Допускаются только частные адреса (10/8, 172.16/12, 192.168/16); `0.0.0.0`, `::`, публичные адреса и имена хостов — **отказ без исключений**, даже с подтверждением. Само по себе предупреждение недостаточно: preflight завершается ошибкой, и `deploy:up` не запускает стек.
- Runbook помечает LAN-режим «только приватное тестирование с Test OTP, не публиковать, не пробрасывать порты, не использовать на публичной сети»; снятие ограничения возможно только после O-AUTH отдельным решением PO.
- Прямой запуск compose без `deploy:up` по умолчанию тоже слушает только loopback (значение по умолчанию в compose).

### 3.3 Платформа проверки (что проверено, что только ожидается)

| Категория | Содержание |
|---|---|
| **Проверяется и заявляется** | Хост Windows 11 + Docker Desktop 29.x (Linux-ВМ, **linux/amd64**), запуск из Git Bash; образ собран и запущен на этой связке; Node 24.19.0 (`.node-version`) внутри образа. |
| **Ожидается, не проверяется** | Другой Docker Engine на Linux amd64 (тот же образ и compose должны работать; логика не зависит от ОС хоста). Записывается как ожидание, не как результат. |
| **Не поддерживается и не проверяется** | linux/arm64 (образ под него не собирается и не тестируется; `sharp` — нативная зависимость); macOS; PowerShell-воспроизведение; Podman; запуск без Docker. |

Отчёт прогона записывает версии Docker, ОС ВМ, архитектуру, digest базы, размер и время сборки, использованную память ВМ.

### 3.4 TLS-проверка (ровно эта конфигурация)

- **Прокси для приёмки:** официальный образ **Caddy 2** (версия и digest фиксируются при реализации и записываются в отчёт), только в проекте проверки `kaida-deploy-check`, слушает `127.0.0.1:${KAIDA_TLS_PORT}`; режим `tls internal` (локальный CA Caddy, листовой сертификат для `localhost`), `reverse_proxy app:3000`.
- **Доверие сертификату:** корневой CA в хранилище ОС **не устанавливается**. Playwright запускается с `ignoreHTTPSErrors`; PO в браузере один раз принимает предупреждение о самоподписанном сертификате и понимает, что оно ожидаемо.
- **Что проверяется через него:** вход продавца по test OTP (cookie `Secure`+`HttpOnly`, вход по HTTP при `COOKIE_SECURE=true` не работает — зафиксировать), сквозной путь продавец → покупатель, загрузка фото типичного размера и крупного (проверка лимита тела запроса), перезапуск.
- **Что это НЕ доказывает:** поведение любого прокси провайдера (nginx, облачный балансировщик, CDN): заголовки `X-Forwarded-*` (приложение их не использует — подтверждено поиском по коду), лимиты размера тела и таймауты, HTTP/2/3, HSTS, выпуск и продление сертификатов, публичный DNS. Эти пункты записываются как ожидания и проверяются при выборе хостинга.

### 3.5 Оценка находок безопасности (Hadolint и Trivy)

Запускаются локально как контейнеры с зафиксированными версиями/digest (без установки на хост и без изменения CI). Отчёт фиксирует: версию инструмента, дату базы уязвимостей Trivy (база не старше 24 часов на момент прогона, иначе перезапуск), цели (`runtime`, `tools`), команду и код выхода. Полные отчёты прикладываются к PR; в репозиторий — только итоговая таблица и файл исключений.

| Находка | Правило оценки |
|---|---|
| Hadolint `error`, `warning` | Исправить **или** внести исключение (§ ниже). `info`/`style` — записать, не блокирует. |
| Trivy secret (в образе) | Всегда блокирует: STOP, исправить и пересобрать; исключений нет. |
| Trivy misconfig (Dockerfile/образ) | Как Hadolint: исправимое исправить, остальное — исключение. |
| Trivy уязвимость HIGH/CRITICAL **с доступным исправлением** (обновить зависимость/базу) | Исправить; если нельзя — исключение с обоснованием. |
| Trivy HIGH/CRITICAL **без исправления** | Записать с оценкой достижимости в `runtime`; принять можно только исключением, утверждённым PO. |
| MEDIUM/LOW | Перечислить сводкой, не блокирует. |
| Находки только в target `tools` | Оцениваются отдельно (target не публикуется наружу), но фиксируются и подлежат тем же правилам для HIGH/CRITICAL. |

**Исключение** — запись в `ops/deployment/security-exceptions.md`: идентификатор (CVE/правило), пакет и версия, цель (`runtime`/`tools`), почему не эксплуатируема или не исправима сейчас, смягчающие меры, условие пересмотра (например, выход исправления), **подтверждение PO**. Без утверждённой записи находка считается открытой.

**Что считается «пройдено»:** оба сканера успешно выполнены (код выхода, версия, свежая БД записаны), результаты по обеим целям оценены по таблице, все actionable-находки исправлены или исключены с подтверждением PO, секретов нет. **Запуск сканера сам по себе — не прохождение.** Если сканер не удалось выполнить (нет сети для обновления БД, сбой инструмента, устаревшая БД) — результат **«не выполнено»**: критерий 9 не считается выполненным, образ остаётся помеченным «не разворачивать», PO получает отчёт с причиной; подмены «пройдено» нет.

## 4. Scope / вне scope

**В scope:** §3.1; изолированная локальная проверка (§6); отчёт прогона в PR; обновление `CURRENT_STATE.md`/плана при закрытии.

**Вне scope:** выбор или покупка хостинга, домен, выпуск публичного сертификата, прокси провайдера; CI/CD-деплой, публикация образа в registry (триггеры SBOM/SLSA); **ежедневный purge D0 и включение `organic` (O-D0-ORG — отдельная Ops-задача)**; настоящая аутентификация/SMS (O-AUTH), защита от злоупотреблений, юридические тексты, объём пилота; AI; мониторинг и журналы; HA, автомасштабирование, управляемая БД, менеджер секретов; расписание, off-site хранение и шифрование backup; интеграция Hadolint/Trivy в CI; изменения схемы и продуктового поведения; **публичный запуск**.

## 5. Закрытые contracts

Только читаются: `local-bootstrap-verification` (compose-паттерн, guards, smoke), `backup-restore` (используется как есть; ревизия — только по STOP), identity/auth (Secure-cookie), `actuality-reminders` (один процесс), `s15c-d0-search-demand-events` (`organic` выключен), `offer-photos` (неизменяемые файлы — основа backup).

## 6. Risk flags

**Фактические:** infrastructure; **secrets**; **security** (Dockerfile → оценка находок §3.5); **Test OTP** (§3.2: доступ ограничен технически); public API (`/api/health`, аддитивно); supply chain (база образа, lockfile, build scripts `sharp`/`esbuild`); data safety (не задеть dev-стек); память ВМ Docker ≈3,7 ГБ (сборка может падать — ограничить параллелизм, записать результат; если сборка невозможна на этой машине — STOP, не обход).
**Не затрагиваются:** DB schema/migrations, auth-логика, UX/UI, AI, ranking.

## 7. Acceptance criteria

**Проверяется локально на платформе §3.3 (агентом):**

1. **Сборка:** из свежего клона на записанном SHA `docker build` создаёт `runtime` и `tools`; в образах нет `.env`, `tmp/`, `scripts/`, `.vscode/`, `.mimosa/`, `.pnpm-store/`, `.data/`, секретов; процесс не от root; размер, время, digest базы записаны.
2. **Preflight:** положительный сценарий проходит; отрицательные (нет переменной, короткий секрет, `COOKIE_SECURE=false`, недоступная БД, неприменённая миграция, KB не установлена, `organic`, **небезопасный адрес публикации**) дают отказ без утечки секретов.
3. **Доступ:** по умолчанию порты слушают только `127.0.0.1` (проверено `docker inspect`/сканом портов с другого интерфейса); `0.0.0.0`, `::`, публичный адрес и частный адрес без подтверждения → отказ; частный адрес с подтверждением → разрешён и помечен как приватное тестирование; PostgreSQL никогда не опубликован.
4. **Первый запуск и повтор:** `migrate` → `import-kb` → `app`; повтор шагов безопасен; `/api/health` = 200, при остановленной БД = 503.
5. **Изоляция:** guards R1/R2 соблюдены; dev-стек (контейнер, том, порт 5432, `.data/photos`, порты 3000/3100/3101) до/после без изменений.
6. **HTTPS (§3.4):** вход продавца, `Secure`+`HttpOnly`, адаптированный R1 smoke против контейнера через Caddy, загрузка крупного фото.
7. **Сохранность:** `down` без удаления томов → `up`: данные и фото на месте; процесс напоминаний не дублируется.
8. **Backup/restore эталонного стека:** `backup:create` → `backup:restore` в чистую цель → `backup:verify`, без изменения R2-кода.
9. **Безопасность (§3.5):** оба сканера выполнены и оценены по правилам; нет открытых actionable-находок без исключения, утверждённого PO; секретов нет. Иначе критерий не выполнен, образ помечен «не разворачивать».
10. **Runbook** воспроизводит пп. 1–8; присутствуют разделы «проверено / ожидается / не проверено».
11. **Диф:** продуктовый код, схема, миграции не изменены (кроме `/api/health`); CI `KAIDA verify` зелёный; находки перечислены, продуктовые не исправлены молча.

**Не проверяется без будущего окружения (в runbook — «не проверено»):** реальный домен и сертификат; любой прокси провайдера (§3.4); сетевой периметр; управляемая БД; нагрузка и память под реальным трафиком; другая ОС/архитектура хоста (§3.3); планировщик ежедневного purge и `organic`; off-host backup, расписание, шифрование; журналы и мониторинг; настоящая аутентификация; несколько экземпляров.

## 8. Manual acceptance (PO)

Технические действия выполняет агент. PO открывает эталонный стек на этой же машине по `https://localhost:<порт>` (принимает ожидаемое предупреждение о самоподписанном сертификате), входит продавцом по тестовому коду, создаёт карточку с фото, как покупатель находит её; после перезапуска стека карточка и фото на месте; затем принимает отчёт, включая итог проверок безопасности и список «не проверено». Приёмка не означает готовности к публичному запуску.

## 9. Решения PO

**Приняты 2026-10-09:** (1) контейнерный образ — формат поставки; (2) Hadolint и Trivy авторизованы локально в рамках R3, без изменения CI; правила оценки — §3.5; (3) `GET /api/health` одобрен в принципе (утверждается вместе с контрактом); (4) доступ по умолчанию — loopback, LAN только осознанно (§3.2).

**Открытых блокирующих вопросов к PO нет.** Требуют внимания при реализации (не блокируют утверждение): по §3.5 исключения для находок без исправления утверждает PO; если сборка образа невозможна на машине с ≈3,7 ГБ памяти ВМ — STOP.

## 10. STOP conditions

Нужно подключиться к dev-БД/фото/портам; секрет в образе, Git, build-arg, логах или bundle; найден секрет сканером; потребовалось изменить схему, миграции или закрытое поведение; потребовалась ревизия R2 (guards, формат bundle) или R1; образ нельзя собрать без платного/внешнего сервиса или на доступной памяти; сканер не выполнен, а требуется «пройдено»; потребовался прокси-специфичный код в приложении; предложение открыть стек во внешнюю сеть, использовать `0.0.0.0` или публичный адрес; включение `organic`; выбор хостинг-провайдера.
