# S15B-4b — Search «По соответствию» (relevance) как режим по умолчанию

**Status:** DRAFT — на финальный approval PO (уточнения PO от 2026-10-06 внесены).
**Base:** `main` после `v0.0.58-product-as-search-signal`.
**Plan:** последний семантический slice S15B (`EXECUTION_PLAN.md`); следом — отдельный Search sorting control UX refresh, затем S15C. Классификация L1/L2/L3 отдельным slice не делается: она существует только как часть режима «По соответствию» (самостоятельного пользовательского результата у неё нет).
**Граница доставки:** mobile + русский (`PROJECT_RULES.md` §18.5); казахский текст — в каталоге строк, перевод — на вычитку.

## 1. User task

Покупатель, не выбравший сортировку, видит сверху те карточки, что лучше отвечают его запросу (карточка Product, точные слова названия, потом приставки слов) — вместо порядка по давности подтверждения. Явные «По цене» / «По расстоянию» / «По актуальности» работают как раньше.

## 2. Фактическое поведение на `main` (evidence)

- Сортировки: `actuality` (дефолт, `desc`), `price`, `distance`; выбранный критерий — первичный порядок всех допустимых Offers, без tier и score (Rev 3 §3.2). Порядок `actuality`: `lastConfirmedAt` (по `direction`), tie → `Offer.id` asc.
- `GET /api/search`: `sort` / `direction` необязательны (дефолт `actuality` / естественное направление); `distance` без координат → 400. `POST`: то же в strict-схеме.
- Адрес результата — `/?q=…[&product=<uuid>]`; **сортировки в адресе нет**. Сортировка живёт в `sessionStorage` `kaida:last-search` (`v:2`/`v:3`: `query`, `sort`, `direction`[, `productId`]).
- Контрол сортировки (`SortPopover`): ровно три критерия; тап по активному меняет направление; отказ геолокации при «Расстояние» → возврат к `actuality`.
- Допуск (S15B-4a, E1): объединение — Offers выбранного/resolved Product ∪ Offers, где каждое слово запроса (≥ 2 букв) — начало слова `title_search`. Уровней соответствия нет.

## 3. Behavior

### 3.1 Уровни соответствия (детерминированные признаки, не вероятность)

Для каждой допустимой карточки вычисляется один уровень (лучший из выполненных); в публичный DTO он не попадает.
- **L1 — Product.** `offer.product_id` совпадает с **применимым** Product-сигналом (§3.2).
- **L2 — целые слова.** (не L1) каждое слово запроса (≥ 2 букв, нормализация `searchWords`) равно целому слову названия карточки.
- **L3 — остальное допустимое.** Любая допустимая карточка, не получившая L1 или L2: слова запроса совпали с началами слов (хотя бы одно только как префикс), либо карточка попала в набор только по Product-сигналу, который к запросу не применим (§3.2).

Допуск (E1) не меняется: ни ограничения префикса от 3 букв, ни стоп-слов, ни частичного покрытия слов запроса. Уровни ничего не добавляют и не отсекают — только упорядочивают в режиме `relevance`.

### 3.2 Применимость Product-сигнала (точно)

Product даёт L1 только когда запрос согласован с ним. Применимость определяется так:
- **Resolved Product.** Применим, когда exact resolver вернул `resolved` по тексту запроса. Resolver сравнивает нормализованный текст с **каноническим названием, localized-названием или alias** — любое из трёх даёт применимый Product; применимость **не** сводится к равенству каноническому названию. Статусы `ambiguous` и `not_found` применимого Product не дают.
- **Selected Product** (`product_id` / `productId`). Применим, только если он совпадает с Product, который resolver вернул `resolved` по тому же тексту (т. е. текст запроса — каноническое, localized-название или alias selected Product). Только факт выбора L1 не даёт.
- **Selected конфликтует с текстом** (resolver вернул другой Product, `ambiguous` или `not_found`): selected Product остаётся в наборе кандидатов (union S15B-4a, набор не сужается), но L1 по одному выбору не получает. Его Offers получают уровень по названию: L2, если все слова запроса — целые слова названия, иначе L3.
- Если применимый Product есть, L1 получают Offers (`offer.product_id`) именно этого Product.
- Связь с Product не делает карточку выше свободной, которая точнее отвечает уточнённому запросу (пример — §10).

### 3.3 Режим `relevance`

Порядок, полностью (все пункты по возрастанию значения, затем фиксированные tie-breakers):
1. уровень: L1, затем L2, затем L3;
2. `lastConfirmedAt`: свежее первыми (как режим `actuality` с `desc`);
3. `Offer.id` по возрастанию.

Это действующий порядок режима `actuality` (`desc`), применённый внутри уровня; Rev 3 убрал ageing-слой из Search, поэтому он здесь не появляется. Режиму нужен только текст запроса (и Product-сигнал); координаты не нужны. Расстояние в DTO по-прежнему присутствует, если запрос нёс местоположение.

### 3.4 Дефолт, `sort` и `direction` в API
- **Существующее поведение (Rev 3 §3.2):** `sort` не указан → `actuality`; `direction` не указан → естественное направление выбранного `sort`. Поэтому запрос **только с `direction`** (без `sort`) сегодня валиден и означает `actuality` с этим направлением (GET и POST, и `searchOffers`).
- **Новое:** ни `sort`, ни `direction` не указаны → **`relevance`**. Это публичное изменение дефолта; явные значения не меняются.
- **Правило совместимости:** `direction` без `sort` по-прежнему валиден и сохраняет прежний смысл — `sort=actuality` с указанным `direction`. 400 для такого запроса не вводится.
- `sort=relevance` допустим в GET и POST. Явный `sort=relevance` вместе с `direction` → `400 INVALID_SEARCH_REQUEST` (направления у режима нет). Явные `actuality` / `price` / `distance`: `direction` необязателен (естественное направление).
- `distance` без координат (GET) — 400, как сейчас.

### 3.5 Адрес и last-state
- Адрес не получает параметра сортировки; результат по адресу `/?q=…[&product=…]` без сохранённого состояния открывается в дефолтном `relevance`.
- `kaida:last-search` (форматы `v:2`/`v:3`) допускает `sort: 'relevance'`, при котором `direction` **отсутствует** (для остальных режимов — обязателен, как сейчас). Повреждённое / чужое по-прежнему = «нет последнего поиска»; `v:1` читается как раньше.
- **Явный сохранённый `actuality` (и любой явный sort) не переинтерпретируется.** Прежние состояния читаются как есть; новые поиски без выбора сохраняют `relevance`.
- Возврат из отказа геолокации при «Расстояние» и нормализация `distance` без координат при восстановлении переходят в дефолтный режим `relevance` (раньше — в `actuality`; смысл прежний: «вернуться к умолчанию»).

### 3.6 Контрол сортировки (минимально, без кадра дизайна)
- В существующий `SortPopover` добавляется четвёртый пункт **«По соответствию»** (первым в списке); RU «По соответствию», KK — предложение «Сәйкестік бойынша» (на вычитку, не утверждено).
- Выбор применяется сразу (как остальные). Для «По соответствию» нет стрелки направления и нет смены направления по тапу на активный пункт (тап активного — без эффекта).
- Подпись порядка: RU «лучшие совпадения первыми»; KK — предложение «ең сәйкестері алдымен» (на вычитку).
- Переход relevance ↔ остальные: выбор `price` / `distance` / `actuality` из `relevance` начинает с естественного направления критерия; выбор `relevance` из любого режима сбрасывает направление (его нет).
- Активный пункт по умолчанию — «По соответствию». Иконка фильтра и остальной UX без изменений (рефакторинг контрола — отдельный slice).

## 4. Scope / out of scope

**In scope:** классификация L1/L2/L3 в Search runtime; режим `relevance`; дефолт без `sort`; `sort=relevance` / `direction` в API; last-state; четвёртый пункт контрола и тексты; приведение `SEARCH_SYSTEM_SPEC_v0.1.md` §8 (строка «Результат fallback нельзя визуально смешивать…», «Похожие предложения», §874) к принятому решению: одна общая выдача, без отдельной секции fallback; тесты.

**Out of scope:** изменение допуска (E1 сохраняется); fuzzy, опечатки, транслит, candidate suggestions, prefix по alias; два направления у relevance; изменение `price` / `distance` / `actuality`, их `direction` и tie-breakers; Nearby (S11); публичный уровень в DTO; Search sorting control UX refresh (иконка, current-sort control, dropdown и т. д. — **следующий отдельный slice до S15C**, требования записаны в `EXECUTION_PLAN.md`); Search Events / S15C; Demand; AI; миграции БД.

## 8. Acceptance criteria

1. Без `sort` и без `direction` (GET, POST, UI «новый поиск») порядок — `relevance`: L1 → L2 → L3, внутри уровня свежее первыми, затем `Offer.id` asc.
2. L1 только у Offers применимого Product-сигнала (§3.2): resolved по каноническому названию, localized-названию или alias; selected Product, не согласованный с текстом, L1 по выбору не получает; набор кандидатов не сужается.
3. Свободная карточка, точнее отвечающая уточнённому запросу, стоит выше Product-linked карточки, у которой L1 неприменим (пример §10).
4. Допуск (E1) не изменился: те же Offers, что и до slice, различаются только порядком по умолчанию.
5. Явные `actuality` / `price` / `distance`, их `direction`, tie-breakers и geo — без изменений (существующие тесты Rev 3 / S9 зелёные без правки утверждений порядка; при необходимости тесты, полагавшиеся на дефолт без `sort`, получают явный `sort=actuality`).
6. Явный `sort=relevance` + `direction` → 400; `direction` без `sort` по-прежнему даёт `actuality` с этим направлением (не 400); `sort=relevance` без координат работает; неизвестный `sort` → 400.
7. last-state: `relevance` хранится без `direction`; явный сохранённый `actuality` восстанавливается как `actuality`; v1/v2/v3 читаются; повреждённое игнорируется; `distance` без координат при восстановлении → `relevance`.
8. Контрол: четыре пункта, «По соответствию» первый и активный по умолчанию; у него нет стрелки и смены направления; переходы relevance ↔ остальные по §3.6; подпись порядка.
9. Nearby (S11), seller-подсказки, S15B-2 known-zero, S15B-3 выбор/адрес без изменений.
10. `SEARCH_SYSTEM_SPEC` §8 больше не требует визуального разделения fallback и не противоречит одной общей выдаче.

## 10. Пример: свободная карточка точнее Product-linked

Запрос `/?q=баранина на кости&product=<Баранина>` (адрес или API с рассогласованными `q` и `product_id`):
- A — Product-linked «Баранина» (`product_id` = Баранина);
- B — свободная «Баранина на кости».

Набор кандидатов (union 4a) содержит A (по selected Product) и B (все три слова). Selected Product «Баранина» не согласован с текстом «баранина на кости» → L1 неприменим. A: название не покрывает все слова, попала только по неприменимому сигналу → **L3**. B: каждое слово запроса — целое слово названия → **L2**. Порядок: **B, затем A**. При наивном «любая связь с Product = L1» A стояла бы выше B.

В UI такой запрос набирается руками: правка текста сбрасывает выбор (S15B-3), и в Search идёт только текст — в выдачу попадает только B (A недопустима по E1). Пример важен для API и адреса и для будущих расширений допуска.

## 11. Manual acceptance (телефон, русский; БД с KB, есть связанные «Баранина» и свободная «Баранина на кости (свободная)»)

1. Ввести `баран`, выбрать «Баранина»: активен «По соответствию»; сверху связанные «Баранина», ниже свободная.
2. Открыть сортировку: четыре пункта, активный «По соответствию» (без стрелки); тап по нему ничего не меняет.
3. Выбрать «Цена» — порядок по цене, стрелка есть; тап по ней меняет направление. Выбрать «Актуальность» — как раньше.
4. Выбрать «По соответствию» снова — порядок по соответствию.
5. Открыть карточку, Back: тот же режим сохранён.
6. Новая вкладка/новый поиск «Баранина» — снова «По соответствию».
7. «Тунец» — «Сейчас предложений нет.».

## 12. Решения PO (приняты) и открытое

Приняты PO: возврат из отказа геолокации «Расстояние» — в `relevance`; явный `sort=relevance` + `direction` → 400; допустимая карточка без применимого Product и без полного совпадения целых слов — L3; порядок внутри уровня — действующий порядок `actuality` `desc` (свежее первыми → `Offer.id`); `direction` без `sort` — совместимость (§3.4).

Открыто: казахские тексты — **черновики на вычитку, не утверждены** («Сәйкестік бойынша», «ең сәйкестері алдымен»).
