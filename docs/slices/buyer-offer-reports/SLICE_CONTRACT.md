## 1. One complete task

A buyer reports a problematic card from its Offer page; an operator finds the report in the existing operator application, reviews what the buyer reported against the current card, and records a disposition, using the existing whole-card removal/return operations where appropriate.

## 3. Approved initial local policy

| Decision | Approved decision and boundary |
| --- | --- |
| Authentication | Show the report entry to guests, but require the existing phone/test-OTP login before sending. Preserve the selected card, reason and text through login. This limits anonymous spam without inventing a new identity flow. Test OTP does not prove control of a phone and allows many accounts: this is a local safeguard, not production anti-spam proof. |
| Reasons/text | Price differs; photo mismatch; incorrect description; other. Optional plain text, trimmed, maximum 300 characters; no uploaded evidence or contact fields. These buyer reasons do not automatically select an operator removal reason. |
| Duplicates/spam | One report per User + whole card + captured card version, including after closure; changed versions may be reported again. Maximum five new reports per User in a rolling 24 hours, server-enforced atomically. Retries/duplicates return the existing receipt and consume no extra quota or change the first message. This is the approved local policy, stricter than the brief's one-active-report suggestion. No IP/device fingerprinting, clustering or automatic sanctions. |
| Lifecycle/outcome | Two states: open and closed. Opening/reading does not close a report. An operator records: removed, already removed, returned, or no moderation action. Removal uses the existing reason/comment confirmation; no-action and return require a short private rationale. A report is never evidence by itself that the buyer is correct. |
| Buyer feedback | Immediate acknowledgement only: one heading `Жалоба отправлена` and short message `Спасибо, мы проверим предложение.` Stable receipt metadata supports safe retries internally; normal UI has no receipt-number block, duplicate explanation or response-time promise. Relevant duplicate/stale guidance appears only when that situation occurs. No buyer outcome inbox, notifications or appeal flow in this slice. Operator disposition remains durable and reviewable internally. |

For photo mismatch, the selected immutable existing photo ID is evidence attached to a whole-card complaint, not a request to hide only that photo. Multiple photos require selection, one is selected automatically; with none, explain that another reason must be chosen. No report is submitted silently on login or reason selection: final Send is explicit.

## 4. Approved end-to-end behavior

- **PO-directed preview navigation:** selecting a reason immediately opens the next step; there is no `Далее` button. Non-photo reasons open optional comment. Photo mismatch opens the relevant photo-selection/comment step, with the existing single/multiple-photo rules above. Selecting or reselecting a reason never submits or creates a report. Back returns to reason selection while retaining the reason, comment, selected photo and bound card context/version. Changing reason preserves the comment; only photo mismatch includes the selected photo in the final submission. Only explicit `Отправить жалобу` submits, subject to authentication and validation.
- Accept only an Offer currently available to buyers. Persist its exact Offer, card and selected point identifiers, server time, reason/text and a server-captured immutable snapshot of the displayed title, pack, price/unit, comment and photo references. Store no buyer coordinates. If the card changes or becomes unavailable before Send, retain the draft, show the conflict and require review of refreshed context; never bind the report silently to a different version.
- A stable submission receipt belongs to its authenticated User. Retrying a committed Send returns that receipt even after the card changes or is removed; new-report visibility/version checks do not invalidate a prior acknowledgement. Reusing the same retry identity with different input is a conflict, not permission to overwrite evidence. Different submissions that match the duplicate key return the first report without replacing its text.
- Operator receives the report through a separate open-reports view/count inside `/operator`, 30 per page, oldest first, plus closed reports for audit review. No email, push or external notification; existing post-check feed events/last-view marks remain unchanged. Include loading, empty, error and retry states.
- Review shows reported context, private buyer text, current card and any existing removal. Hide buyer phone/identity from the seller and public UI; operator UI also needs no buyer phone. Text is rendered literally, never as HTML. The server retains User ID only for ownership, quota and audit.
- A report has no automatic effect on visibility, ranking, interests, seller state or rating. Removal/return affects the whole card through existing domain operations. Rejection never automatically returns a removed card. Return is a separate explicit confirmation and restores visibility only when existing visibility conditions hold.
- Resolve atomically: final state, actor/time, disposition/rationale and the linked moderation event commit together. Already-removed disposition links the existing event without inventing another removal. Concurrent resolutions permit one winner; an identical retry returns the recorded result, a conflicting decision requires refresh. A card changed since operator review requires refreshed context before a new removal/return. A resolved report stays historical when a seller republishes or an operator later returns the card; other reports are not silently closed.
- Reporter text is never copied automatically into the seller-visible removal comment. The existing seller removal reason/comment, republish behavior and moderation audit remain the only seller-facing consequences.

## 5. Boundaries, risks and design decisions

### 5.1 Clarification: card version and frozen versus current evidence

These approved semantics are not a claim that immutable card revisions are already implemented.

- `cardId` groups one card's point-specific Offers. Existing `offers.revision` is per Offer, so a single point's number cannot identify the whole card. The report version is a server-derived identity combining the latest committed create/update publication event for that card (the same confirmed ChangeSet ordering used by post-check) with a deterministic fingerprint of its public content: title, pack, original comment, ordered photo IDs, and sorted point/Offer identities, price/currency/unit and public point labels/addresses. A legacy card without such an event has a stable legacy marker plus that content fingerprint. No new global Offer revision system is proposed.
- A confirmed edit/republish is a new reporting version even if it restores earlier values; switching off/on, renewing actuality alone, operator removal/return and viewing in another language do not reset the duplicate allowance. Public content changed outside a card edit, such as a point's address, is caught by the content fingerprint. The selected Offer/point remains the report's concrete context, but duplicate protection applies to the whole card. All snapshot fields and the version identity are read consistently from the server; a client cannot invent or replace them.
- At form opening, bind the shown context to its server version. On first Send, compare against current committed context and eligibility. A mismatch means refresh and explicit re-review, not silently taking a newer snapshot. A committed retry still returns its original receipt. Operator write confirmation similarly checks the current card version AND removal/visibility state against the context just reviewed; a concurrent edit/return/removal means refresh, not an action against unseen state.
- Freeze the report-time display fields, selected point, ordered immutable photo references, selected disputed photo, submission time, reason and original buyer text. Preserve displayed locale/text alongside the original seller text where needed; translation or later edits never rewrite evidence. Operator review labels two separate sections: **At report time** and **Current card**, with differences and current availability. Reported price is not evidence of an independently verified shop price; buyer text remains an allegation.
- If a photo was replaced, the old photo remains report evidence; current photos appear separately. If current context cannot be loaded, show that explicitly, retain historical evidence, and disable removal/return until current state can be checked. Do not substitute the nearest/current photo or claim historical evidence is current.

### 5.2 Closure after return

Report state and card visibility are independent. Closing with `removed` records a historical disposition linked to its moderation event. A later explicit return or seller republish updates current card state and that moderation event's existing return/clear audit; it does not reopen the report, change `removed` to `returned`, delete evidence, or release the same-version duplicate allowance. Show **Closed — card removed at decision time** plus **Current card: returned / republished** and the later event separately. Other open reports remain open. `returned` is a disposition only when that return was the action taken while resolving an open report.

### 5.3 Evidence retention and the R2/photo boundary

- Proposed local policy: report evidence, original text, disposition and audit persist while this isolated test installation exists, including after closure, return and photo replacement; no timed purge or user-facing delete in this slice. At acceptance cleanup, remove only recorded synthetic fixture resources after preserving the agreed verification evidence. This is not a production indefinite-retention policy: launch requires a separately approved retention/erasure policy covering live records AND backup copies. No 30/90-day deadline is invented here.
- Existing [offer-photos, Storage](../offer-photos/SLICE_CONTRACT.md) and [R2 §3.2](../backup-restore/SLICE_CONTRACT.md) guarantee immutable photo bytes; replacement uploads a new ID, detachment does not delete the old row/files. Reference existing photo IDs in report evidence; do not duplicate files, overwrite photos, delete orphan files, or create a new evidence-upload store. Future physical cleanup must first revise report retention/access and R2 consistency together.
- **Concrete access gap:** the delivered media reader allows an operator to read a non-public photo only while attached to an Offer. After replacement detaches an old photo, an operator cannot necessarily fetch it. The proposal therefore needs one explicit closed-contract extension: an allowlisted operator may read an immutable photo referenced by a report they are authorized to review, even when no longer attached to an Offer. This must be report-scoped, checked on every request, private/no-store, and return404 to other users; it must not broaden ordinary/public photo URLs or grant access to arbitrary orphan photos. PO approved this bounded extension on 2026-10-10.
- R2 already dumps all DB tables and copies immutable display/thumb files. New report/evidence/audit rows therefore belong in its normal DB snapshot; their photos stay in the normal photo directory. No backup format change is presumed. Required implementation verification includes isolated R2 backup/restore of a closed report whose disputed photo was detached: both snapshot/text/audit and authorized old-photo reading must survive, with ordinary unauthorized access still denied. No backup or migration is run during this preparation.
- A backup now also contains private report text and reporter linkage. Keep bundles/dumps out of Git and public artifacts, with existing confidential-backup guards. A stored formerly public photo is not made newly public by a report; previously cached public copies cannot be retroactively revoked by this slice.

### 5.4 Buyer identity and private text

The server derives reporter User ID from the session, never from submitted identity fields. Ordinary buyer UI receives only its acknowledgement/opaque receipt; no endpoint lists other users' reports. Every report/evidence read and disposition requires the existing operator allowlist on every request, not just entry to the page. Operator screens show receipt/time, reason, evidence and buyer text, but no buyer phone, account ID, coordinates or identity profile. The seller and public screens receive none of those report fields.

Free text can contain identifying details despite a neutral hint not to include names/contact details. Do not claim automated anonymization: authorized operators may read the original text; it remains operator-only, escaped as plain text, excluded from URLs, analytics and routine logs, and never automatically copied into seller-visible comments. Seller-visible removal comments are separately authored; the operator UI warns not to include buyer text or identity. This cannot technically prevent an authorized operator manually disclosing what they read; preview/privacy tests must make that limit explicit. User/phone linkage stays in private persistence for quota/ownership/audit, with no public report counts or ratings.

## 6. Acceptance and verification

1. Guest report action leads through existing login without losing draft; authenticated Send is explicit.
2. Selecting a reason immediately opens optional comment or the relevant photo/comment step, without a Next button or submission. Back preserves the draft; reselecting a reason cannot send it. Whole-card reasons and conditional photo selection obey the approved flow; invalid input is explained.
3. Stored evidence is server-derived and immutable; changed/unavailable context cannot be silently substituted.
4. Duplicate/concurrent sends create one report/receipt; quota admission is atomic and retry does not consume allowance.
5. An authorized operator finds and reviews a report; every new operator route denies non-operators with 404 and exposes no private reporter data publicly or to the seller.
6. No moderation action occurs until an operator explicitly decides; each disposition has actor/time and an appropriate rationale/event link.
7. Removal preserves existing whole-card visibility/seller/audit behavior; return uses existing eligibility and never happens merely because a report is rejected.
8. Concurrent resolve/retry and stale card review cannot duplicate or overwrite decisions; failures roll back report and moderation side effects together.
9. Additive upgrade preserves all existing rows and moderation audit; report evidence survives later card edits/republish.
10. Mobile form/queue errors, acknowledgement and retry are accessible; full required regression/branch CI and manual acceptance precede merge/tag.

Verification: unit reason/text/policy boundaries; PostgreSQL integration for authorization, privacy, version identity (including edits back to earlier values and return without allowance reset), server snapshots, quota/duplicate/decision races and rollback; actual upgrade/fresh migration proof; mobile E2E buyer → operator → seller/buyer visibility, plus duplicate/no-action and closed-after-return cases; isolated R2 restore of detached report-photo evidence with private-access checks. No benchmark, paid provider or general abuse audit.

**Manual scenario:** use two recorded synthetic accounts (buyer and allowlisted operator) and a two-photo card. Buyer reports photo mismatch, selects the second photo and sends a short explanation; retry shows the same receipt. Operator opens Reports, compares saved/current context and removes the whole card through the existing confirmation. Buyer can no longer open it; seller sees only the operator reason/comment, not the reporter. Operator sees the closed report/audit, explicitly returns the card and checks it is visible while the historical disposition stays recorded. Report a second fixture and close it with no action; it remains visible. Fixture IDs are recorded when implementation is separately authorized, not created during preparation.

Clarification acceptance extension: after return, the seller replaces the reported photo through the existing editor/confirmation. The operator still sees the old report photo and original price/text separately from the current card; the report stays closed and the buyer identity/text never appears on the seller screen. The R2 restore variant is automated on separate disposable fixtures, not a backup of port3000's private snapshot.
