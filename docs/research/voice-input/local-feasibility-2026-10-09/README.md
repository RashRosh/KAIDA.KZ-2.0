## Verdict and remaining validation

The initial measurements do not justify a general conclusion about multilingual ASR or extraction. They describe nine very short synthetic examples, small ASR weights and a weak extraction setup. Formatting, language selection, decoder differences and scoring explain part of the surprising results; substantial product, number and omission errors remain after controls. No safe seller-draft readiness has been demonstrated.

**The representative audio-validation gate is passed by the PO.** All three clips were generally intelligible, with incorrect word stress in places and no content mismatch reported. This limited synthetic-corpus check does not validate natural seller speech or every recording independently. The [offline audition](audition.html) remains available. The authorized small comparison stopped at the memory preflight; see [the follow-up report](small-comparison/REPORT.md) and timestamped memory evidence. No download or inference started.

## Audio and ASR diagnosis

The 18 preserved WAVs are mono 16-bit PCM at 22,050 Hz. Native ASR used explicit 16,000-Hz resampling; maximum duration drift was 0.062 ms. Signal energy is present; maximum clipped-sample fraction is 0.00283%. There is no measured sample-rate/duration mismatch or gross clipping explanation. The corpus was generated offline: eSpeak NG 1.52.0 and Piper 2023.11.14-2, with separate RU/KK voices. Mixed clips concatenate language-specific synthesis segments and are not natural code-switching recordings. See [signal measurements](diagnostic/audio-analysis.json), [fixed neural corpus](baseline/neural/fixed-corpus.json) and [synthesis sources](baseline/speech-sources.json).

Both ASR runtimes used the multilingual Whisper **base** family: whisper.cpp 1.9.5/b5454, floating GGML weights; faster-whisper 1.2.1 / CTranslate2 4.8.2, CPU int8. Two CPU threads, beam/best-of five. Pure RU/KK language was supplied from the corpus, whereas mixed input used automatic detection: an optimistic language oracle for pure examples, not a demonstrated automatic seller flow. Native decoding allowed temperature fallback from zero in 0.2 increments; Python decoding used zero only, no VAD and no previous-text conditioning. Quantization/decoder differences prevent treating this as a controlled ranking of runtime implementations. Exact commands, detected languages, API defaults and help are preserved in [ASR analysis](diagnostic/asr-analysis.json), [raw logs](baseline/results/), [neural logs](baseline/neural/results/), [Python signature](diagnostic/faster-whisper-signature.txt) and [native help](diagnostic/whisper-cli-help.txt).

WER is edit count / reference-word count, not the fraction of words “wrong.” Repetition adds insertions and can produce WER above 100%. The same reference set contains only 68 whitespace words. A diagnostic presentation normalization maps unambiguous spoken numbers and currency/unit spelling to their numeric/canonical forms; it does not fix product spelling or interpret ambiguous “two five hundred.” Merging number words reduces the denominator to 58. Thus percentages can increase even when edit counts decrease; differences between the two percentages are not a measure of substantive error removed.

| Audio / runtime | Raw edits / words; WER | Presentation-normalized edits / words; WER |
| --- | --- | --- |
| Robotic / native | 70/68; 102.9% | 65/58; 112.1% |
| Robotic / Python | 201/68; 295.6% | 199/58; 343.1% |
| Neural / native | 63/68; 92.6% | 49/58; 84.5% |
| Neural / Python | 85/68; 125.0% | 75/58; 129.3% |

Neural native raw errors comprise 43 substitutions, 19 deletions and one insertion; neural Python has 46 substitutions, 17 deletions and 22 insertions. Robotic Python has 135 insertions: repetitions drive its extreme WER. The normalization and all edit alignments are reproducible from [diagnose.py](diagnostic/diagnose.py). This is a narrow diagnostic normalizer, not a general RU/KK number parser.

For example, reference `Морковь триста тенге за килограмм.` becomes native neural `Марков 300 теньги за килограмм.`: `триста` versus `300` is formatting, while the product and currency spelling differ. Other outputs omit products, lose the 250 price or repeat words. Native auto-detection classified the three neural mixed clips as Lithuanian, Ukrainian and Lithuanian; Python as Lithuanian, Russian and Lithuanian. That is a concrete confounder. Four same-weight [ASR controls](diagnostic/asr-controls.json) disable native fallback and force known languages: pure RU/KK transcripts remain unchanged, and RU/KK hints change mixed output but still do not recover its 250 price. Language detection is part of the problem, not a complete explanation. These forced hints are diagnostics, not a proposed user-facing language picker.

## Extraction diagnosis

The **exact original system prompt** is [prompt.txt](diagnostic/prompt.txt); the **complete output schema** is [schema.json](diagnostic/schema.json). User messages were the unmodified reference or ASR transcript, with no examples. Output is `items[]`, each requiring `product`, numeric-or-null `price`, enumerated-or-null `unit`, and boolean `clarify`; additional properties are forbidden. It is a six-product toy draft schema, not a SellerChangeSet implementation. Original prompt:

```text
Extract seller product drafts from Russian, Kazakh or mixed-language speech transcripts. Output JSON items in spoken order. Vocabulary: carrot=морковь/сәбіз, potato=картофель/картоп, apple=яблоко/алма, cheese=сыр/ірімшік, milk=молоко/сүт, trout=форель. Never invent products, prices or units. If price or price basis is absent or ambiguous, use null and clarify=true. If facts are clear, clarify=false. Do not repair unreliable recognition by guessing. Do not create locations, brands, sizes or facts not stated. Prices are numeric KZT amounts; kg means per kilogram, liter means per liter. Convert unambiguous spoken number words to numbers.
```

The original schema constrained decoding via `response_format`; it was **not embedded in the prompt**. llama.cpp 0.6.0-dev/b11524 served Qwen2.5 Instruct 0.5B and 1.5B Q4_K_M locally, one slot, two threads, context 2048, temperature zero, seed 42, output limit 256 tokens. Version, licence, download revision and SHA records are in [manifest](baseline/manifest.json), [versions](baseline/versions.json) and [licences](baseline/licenses/). No model weights are included here.

Clean references isolate extraction from ASR. All 18 original reference responses ended normally and parsed as valid JSON. Nevertheless, the smaller extractor matched 27/48 positional fields, zero of nine complete cases and added eight extra items; the larger matched 35/48 fields, two cases and invented three values in expected unknown fields. Excluding null/clarification credits gives only 17/31 and 21/31 correct non-null facts. A correct null or `clarify` flag inflated partial field scores; extra items were separately reported rather than penalized in that denominator. These field percentages therefore overstate complete usable-draft quality. The invented-unknown count is a lower bound, not a comprehensive hallucination score. Wrong known facts from ASR input also cannot be attributed solely to extraction. See [per-result scoring](diagnostic/extraction-analysis.json).

Representative clean-reference failures:

- `Картофель двести пятьдесят тенге за килограмм. Яблоки пятьсот тенге за килограмм.`: smaller model returned carrot 50/kg and apple 50/kg; expected potato 250/kg and apple 500/kg.
- A no-cache repeat with the larger model returned carrot 250/kg and apple 500/kg. Reversing product enum order did not fix it. An English single-potato control added an unmentioned carrot before the correct potato.
- Explicitly showing the schema plus “one item per actually mentioned product” fixed that English control, but dropped the second product in the Russian example. On ambiguous `Сыр две пятьсот. Единицу уточню потом.` it invented price 500 and unit `piece` despite `clarify=true`; expected both null.

All six diagnostic controls retain exact requests, full responses and rendered chat templates in [controls.json](diagnostic/controls.json), with [server properties](diagnostic/server-properties.json) and logs. The Qwen system/user/assistant template was present. Cache disabling and enum reversal did not eliminate the errors. Schema visibility contributed to the setup weakness, but does not explain away the remaining semantic failures. These six controls are selected diagnostic examples, not a new acceptance benchmark.

Across the original 90 outputs, five reached the token limit and were malformed, all on repetitive robotic ASR input. No clean-reference or final neural-pass response was malformed. Thus repetition/truncation affected some end-to-end results but cannot explain the clean-text failures. JSON constraints ensure structure only; they do not prove source-grounded facts. [Original extraction harness](baseline/extract_bench.py) and raw responses remain unchanged.

## Corrected first voice task and safety boundary

If feasibility and a later contract are approved, the first complete user task remains **dictation → transcription → proposed SellerChangeSet → seller review → explicit confirmation**, with manual fallback. Shared text extraction is internal infrastructure and cannot count as a completed seller flow.

The **first implementation already requires** safe retries/idempotency across upload, processing, result delivery and confirmation; cancelled, superseded and late results must not overwrite newer seller work or create duplicate Offers. A result must be bound to its owner and operation, remain only a proposal and require explicit confirmation. Failure/retry/fallback behaviour must be accepted in that first contract.

An **approved private-audio lifecycle is also a first-slice prerequisite**, not deferred convenience: access control, accepted formats/size/duration, storage boundary, retention/deletion triggers, cancellation/error cleanup, backup inclusion/exclusion and demonstrable cleanup must be decided and tested. This study does not invent a retention period or authorize public audio access. The original report's third-slice “resumable processing/audio lifecycle” grouping is superseded: only convenience enhancements to resumability can follow later; essential retry/late-result/privacy safety cannot. Later proposals can add multi-product review/ambiguity UX and photo/video tasks without reducing existing requirements.
