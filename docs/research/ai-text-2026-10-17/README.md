## Цель и вывод

Цель продукта: сообщение продавца → черновики карточек → проверка и подтверждение продавцом → предложения. В этих опытах проверялся только текст. Голос, фотографии, видео, реальный SellerChangeSet, сохранение и публикация Offer не проверялись.

Извлечение может дать полезную заготовку, но пока пропускает товары и ошибается в упаковках. PO считает заготовку быстрее для проверки и исправления; это мнение PO, а не измерение времени продавцов. Автоматическую публикацию результаты не обосновывают.

Минимальный вариант для дальнейшей проверки: один извлекатель, программная проверка структуры и фактов, подбор по каталогу, явные неопределённости и проверка продавцом. Отдельная модель принятия решений остаётся необязательным кандидатом: полезность показана на отдельных примерах, необходимость не доказана сравнением с разумным вариантом без неё. Внешний сервис решений в этих опытах не использовался.

## Роли и воспроизводимость

В соответствии с AGENTS.md идентификаторы моделей не публикуются. Здесь используются `extractor-A`, `extractor-B`, `embedding-A`, `decision-A`. Точное соответствие и исходные версии находятся в оригинальных материалах PO. Без этого соответствия запуск моделей из одного репозитория не воспроизводим.

Окружение Kaggle: Python 3.13.15, PyTorch 2.11.0+cu128, Transformers 5.16.1, Accelerate 1.14.0, huggingface-hub 1.29.0; две Tesla T4 по 15360 MiB. Извлекатель A: FP16, GPU 0, greedy, без reasoning; сравнение B: FP16, GPU 1, eager, собственный reasoning. Во втором случае лимит 2048 токенов против 1024 в сравнительном пакете A, поэтому скорости и завершение нельзя трактовать как универсальный рейтинг моделей.

Для embedding понадобилось изолированное окружение с Transformers 5.21.0.dev0. Точная ревизия embedding в отчёте отсутствует. Версия dev без закреплённого source commit также ограничивает воспроизводимость. FP32 применялся для embedding и decision; обычный venv с ensurepip не создался. Следующий обход использовал venv без pip и управление установкой извне. Попытка читать get_ipython() в дочернем процессе завершилась ошибкой; затем выбор кода из истории исправили через AST. Эти ошибки окружения не являются результатами качества моделей.

Каталог: 682 товара, 210 алиасов из `src/modules/catalog/kb-package/v1/`. Проверенные SHA-256 исходных байтов:

- products.csv: `a32f3cf087e25db57740829afd7bb9c79152e8ff8a70374dc3a88ad31f43dd14`.
- aliases.csv: `b96c4181f6b3efb8609aa9b7b0ba5b33471062200bb05335ad0c5f6e1ec49350`.

Извлекатель сам по себе базу продуктов не проверяет. Подбор кандидатов и решение о соответствии тестировались отдельными этапами. Лексический Python baseline приближает нормализацию resolver, но не заменяет запуск настоящего PostgreSQL resolver/API.

## Ошибки, которые нельзя потерять

1. **Полнота на казахском.** В E04 извлекатель пропустил «сметаны нет». Coverage-проверка C03 сочла неполный результат полным с confidence около 0.968. Повторная модель не гарантирует независимую проверку. C04 с вручную добавленной сметаной является контролем, а не автоматическим исправлением.
2. **Упаковки и условия.** Цена за бутылку 0.5 л превращалась в цену за литр; появлялась недопустимая единица gram. После V2 упаковки 500 г превращались в 0.5 кг вопреки инструкции не конвертировать. Скидки за несколько упаковок и цена при покупке ящика терялись. Отдельный заголовок «курица» мог стать лишним товаром.
3. **Выдумывание полей и инструкции во входе.** У мёда без валюты сохранялась цена; ранее придумывалась единица piece. Чеснок получил ложную цену 1 вместо 1900. Успех более поздней атаки со свёклой не закрывает предыдущую ошибку и не доказывает защиту от injection.
4. **Каталог не источник недостающих фактов.** «Бедро» не задаёт вид птицы, «молоко» не обязательно коровье, «мёд» не обязательно цветочный. Семантический поиск выдавал бедро → фета, пельмени → пенне, выдуманную марсианскую ягоду → ягодный морс. Казахское название куриного филе не вывело правильный товар в top-5. В E04 кандидатов молока также не было.
5. **Алиасы требуют отдельной редакторской проверки.** «мед» разрешался в цветочный мёд, «Мёд» не разрешался. В рамках исследования каталог не исправлялся.
6. **Ошибка тестового harness.** E05 дал 3 карточки, заблокированные точной проверкой source-подстроки из-за регистра. Решения по ним не запускались. Это дефект проверки цитаты, не доказательство неверных фактов во всех трёх карточках. Оригинальные результаты сохранены без ретуши.
7. **Confidence не сертификат.** Для ложной цены и объёма decision выдал unknown вместо ожидаемого contradicted, что полезно как флаг, но не exact PASS. Для неверного наличия выдан contradicted. Высокая уверенность при пропуске сметаны показывает, почему пороги нельзя выбирать по этим десяти примерам.

## Скорость

Исправленный набор 20: примерно 2.11 с на пример. Известные сложные V2: примерно 4.5–26.2 с для A, 40–65 с для B с reasoning и обрезаниями. Это характеристики конкретного запуска, не SLA.

Семантический индекс: около 2.70 с; пакет из 23 запросов около 0.103 с после загрузки. Решения по каталогу: первый запуск около 3.83 с, остальные около 0.66–0.80 с. Полный пакет шести сообщений: около 151.94 с, включая CPU embedding stage со стартом модели и индексированием (около 47.82 с). Эти числа нельзя использовать как задержку одного прогретого запроса, стоимость VPS или benchmark production-сервера.

## Материалы и повторная проверка

[manifest.json](manifest.json) содержит SHA-256 оригинальных ZIP и опубликованных JSON. Девять пакетов рядом сохраняют инструкции, входы, сырые ответы и флаги запусков: checkpoint, fixed, messy, pack-v2, comparison, semantic, catalog-decision, full-text, guards. Это архив наблюдений; поля review=pending и старые автоматические PASS не заменяют разбор ошибок выше.

Публикационная трансформация заменяет идентификаторы моделей и их ревизии ролями; новые hash относятся к преобразованным файлам. Исходные ZIP, исполняемый semantic helper и notebook из 25 ячеек остаются в материалах PO; SHA notebook указан в manifest. Notebook содержит исторические неудачные ячейки и не является готовым Run All сценарием. Веса не публикуются. Поэтому это проверяемая фиксация результатов, но не полностью автономный воспроизводимый benchmark.

Для независимого повтора нужны оригинальное соответствие моделей ролям и закреплённые ревизии/зависимости, те же байты каталога, сохранённые prompt и параметры генерации. Следует разделить уже использованные примеры и новый закрытый набор; проверять не только JSON и предложенные карточки, но и пропущенные товары, контекст, исходные цитаты, упаковки и неопределённости. Результаты повтора сохранять отдельно, не перезаписывая этот checkpoint.

## Передача следующему этапу

Исследовательское предложение: проверить короткий голосовой ввод → распознанный текст → исправляемые черновики, сохранив эти текстовые ограничения и возможность ручного ввода. Это предложение не меняет production queue и паузу voice/translation в EXECUTION_PLAN/CURRENT_STATE; для реализации требуется отдельное поручение и owning contract.

Ближайшие вопросы качества: полнота на KK, сохранение количества/упаковки и условий цены, безопасный отказ от неподтверждённого product_id, исправление проверки source без скрытого изменения свидетельств. Пока не доказано, что дополнительная decision-модель выгоднее программных проверок и проверки продавцом. Новые модели и платный хостинг этим checkpoint не утверждаются.
