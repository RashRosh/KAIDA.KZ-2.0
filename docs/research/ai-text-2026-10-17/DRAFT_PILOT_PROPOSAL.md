# Текст → исправляемая заготовка: предложение первого прохода

Статус: исследовательское предложение, не утверждённый production Slice Contract и не реализованный интерфейс. Основание: PO подтвердил направление «быстрее поправить заготовку, чем вводить всё руками». Текущее приложение исследовано на main a736c4d793db8280b2ba9d6ccfb4c41622007de3; verify и Analyze JavaScript / TypeScript имеют success. Локальная среда отключена, UI/БД и runtime здесь не проверялись.

## Пользовательская задача

Продавец видит исходное сообщение рядом с заготовкой, исправляет товары, цены, единицы и фасовки, выбирает подходящие связи с каталогом и явно подтверждает согласованные изменения. Исследовательский проход заканчивается экспортом проверенной заготовки; предложение продавца и Product в каталоге не создаются.

Это ограниченный шаг к целевому пути Seller Input → SellerChangeSet → подтверждение → Offer. Экспорт проверенной заготовки не равен SellerChangeSet или публикации.

## Что уже есть и где границы

| Область | Фактический код | Что можно использовать |
| --- | --- | --- |
| Точное соответствие каталогу | src/modules/catalog/application/resolve-product.ts | resolved / not_found / ambiguous; не генерация productId моделью |
| Подсказки каталога | src/modules/catalog/application/suggest-products.ts | До 5 лексических кандидатов; выбор продавцом, не автоматическое семантическое назначение |
| Неполная заготовка карточки | src/modules/offers/drafts/offer-draft.contract.ts | Пустые поля допустимы; payload не содержит provenance и available |
| Полная карточка с фасовкой | src/modules/seller-input/contracts/seller-card.contract.ts | title, productId|null, обязательные price и unit, pack, points |
| Создание/изменение полной карточки | src/modules/seller-input/application/card-change-sets.ts | Подготовка ChangeSet; подтверждение отдельно; одна карточка может иметь несколько точек |
| Пакет разных товаров S12 | src/modules/seller-input/application/create-batch-seller-change-set.ts | Несколько actions и атомарное подтверждение; create получает каталоговое название, pack=null |
| Подтверждение | src/modules/seller-input/application/confirm-seller-change-set.ts | Owner/revision проверки, atomic apply, idempotence |

Важное ограничение: старый batch shape не принимает pack или свободный title. Вызвать его для AI-пельменей с фасовкой без потери данных нельзя. Несколько createCardChangeSet + несколько confirm не дают атомарности общего пакета, поэтому не подменяют S12. Изменение API нужно отдельно описать и проверить перед интеграцией.

Каталог не обязателен для каждой карточки текущего редактора: собственное название и productId=null допустимы. «Проверить каталог» не означает придумать конкретный Product или заблокировать свободное название.

## Предлагаемый исследовательский проход

1. Взять сохранённый C2-ответ вместе с неизменным исходным текстом. Явно показать, что это replay, а не новое распознавание.
2. Показать все предложенные строки и исходник целиком. Разрешить добавить пропущенный товар, удалить лишнюю строку, исправить поля. Не показывать «проверено всё» на основании успешного JSON.
3. Подбирать каталог по реальным названиям и алиасам KB v1. Отдельно хранить название продавца, выбранную связь и статус resolved / ambiguous / not_found. Пустой результат не даёт права создавать Product.
4. Цена и единица остаются пустыми, если подтверждения нет. Источник и пометки видны; наличие флага не гарантирует, что все ошибки найдены. Уверенность не вычислять из самооценки модели.
5. Для available=false искать цели только среди предложений этого продавца в выбранной точке, учитывая фасовку. Пока таких данных нет, показать «нет, требуется выбрать существующее предложение». Не создавать бесценовую карточку «нет» и не выключать предложения по одному productId.
6. После правок показать итог и отдельное подтверждение продавца. Результат replay: экспорт заготовки с provenance и правками, без вызовов API публикации.
7. Когда понадобится настоящая интеграция, подготовить owning Slice Contract на адаптер к SellerChangeSet с сохранением фасовок, текущих title/productId semantics, ownership, stale revision и атомарности. Контракт не считается утверждённым этим предложением.

## Пример для проверки человеком

Исходник: «Сегодня есть куриное филе по 2400 за килограмм, бёдра по 1800, пельмени наши, пачка пол кило — 1400 тенге. Хотя нет, филе уже 2500, сметана закончилась.»

Ожидаемые факты как контрольный пример, не вывод нового запуска:

- Филе: последняя цена 2500 за kg; первоначальная 2400 остаётся в исходнике.
- Бёдра: 1800; вид птицы и единицу не додумывать из соседнего товара. Требуется проверка.
- Пельмени: 1400 за упаковку 0.5 kg; упаковка не превращается в отдельный товар или цену за kg.
- Сметана: отсутствует; обновление требует конкретной существующей цели продавца и точки. Без неё оставить запись для проверки.

Этот известный пример не становится закрытым контрольным тестом после разработки по нему.

## Acceptance для исследовательского replay

1. Явно обозначены сохранённый ответ и отсутствие live-модели.
2. Исходник не меняется при редактировании заготовки; исправленные поля и до/после сохраняются отдельно.
3. Пропущенные виноград и яблоки в price_null_01 можно добавить; они не объявляются автоматически найденными.
4. Для slang_noise_00 нормализация `кilo` проверяется отдельно, с исходным значением в provenance. Исправление ещё не реализовано.
5. Для REAL_04 неподтверждённое kg у огурцов становится явным вопросом; молча переносить единицу нельзя.
6. Название продавца и каталоговый Product разделены; неоднозначное «бёдра» не назначается индейке или курице автоматически.
7. Фасовка и цена за упаковку сохраняются; неизвестные обязательные поля не получают фиктивных значений.
8. Отсутствие товара не создаёт новую карточку; отсутствие target Offer не обходится.
9. Подтверждение экспортирует согласованную заготовку; до и после экспорта не происходит записей Offer/Product.
10. Время проверки и исправления измеряется отдельно от генерации. Сравнение с ручным вводом на том же примере учитывать как biased; для вывода нужны новые сопоставимые задания.
