# KAIDA.KZ UX Backlog

Этот файл является единым рабочим списком UX/UI-проблем и наблюдений.

Он не является закрытым product contract сам по себе. Пункт становится обязательством только после включения в утверждённый Slice Contract.

## Правила работы

- Новые UX/UI-наблюдения фиксируются здесь сразу после обнаружения.
- Не исправлять соседний UX-долг попутно в функциональном slice без явного включения в scope.
- Перед подготовкой нового Slice Contract проверять этот backlog на пункты, непосредственно связанные с user task нового slice.
- Статусы: `OPEN`, `IN_SLICE`, `DONE`, `REJECTED`.
- При `DONE` указывать slice/checkpoint, которым изменение было закрыто.

## Текущее состояние

- Backlog начат после verified checkpoint `v0.0.14-s13`.
- Verified base SHA: `ff8bd7eed8406d35e469c8a0a4bc2f6332068361`.
- Следующий плановый шаг до S14: отдельный UX slice `UX1`.

## Открытые пункты

### UX-001 — Слишком большие скругления

**Статус:** OPEN  
**Область:** Visual system

Скругления кнопок, полей ввода и аналогичных элементов сейчас воспринимаются слишком большими.

**Желаемое направление:** привести базовый радиус таких элементов к `3px` через общий design token/стиль, а не править каждый компонент отдельно.

---

### UX-002 — Свободный ввод там, где система знает допустимые значения

**Статус:** OPEN  
**Область:** Forms / Data entry

Там, где множество допустимых значений известно системе, не заставлять пользователя вводить их вручную.

Исходное наблюдение: окна ввода, где возможно, заменить выбором из готовых вариантов, например единицы измерения и адреса.

**Желаемое направление:**
- единицы измерения и другие короткие закрытые наборы -> select / controlled choice;
- адрес -> поиск/autocomplete по адресам, а не обычный dropdown;
- свободный input оставлять там, где значение действительно произвольное.

---

### UX-003 — Повторное подтверждение после «Что рядом?»

**Статус:** OPEN  
**Область:** Discovery / Navigation

После нажатия на «Что рядом?» появляется дополнительное действие «Показать товары рядом».

Пользователь уже выразил намерение первым нажатием, поэтому второе подтверждение выглядит лишним.

**Желаемое направление:** одно действие должно сразу запускать соответствующий сценарий, если дополнительное подтверждение не требуется по объективной причине.

**Дополнительно:** проверить другие пользовательские пути на аналогичные повторные подтверждения одного и того же намерения.

---

### UX-004 — Seller setup разбит на лишние этапы

**Статус:** OPEN  
**Область:** Seller onboarding

Сейчас данные продавца вводятся несколькими последовательными этапами: сначала название / Location / адрес, затем телефон / WhatsApp / Telegram / Instagram.

Для пользователя это выглядит как одна задача: заполнить данные своей точки и способы связи.

**Желаемое направление:** дать продавцу пройти этот ввод за один логичный проход в одном пользовательском сценарии, не смешивая при этом внутренние доменные сущности и contracts.

---

### UX-005 — Несогласованная верхняя часть приложения

**Статус:** OPEN  
**Область:** App shell / Visual consistency

Верхняя зона приложения с логотипом на главной странице отличается от остальных страниц.

**Желаемое направление:** привести header/app shell к единой системе и явно определить, где различия действительно нужны по сценарию, а где являются случайной несогласованностью.

---

### UX-006 — Нет понятного входа для продавца

**Статус:** OPEN  
**Область:** Information architecture / Seller journey

В интерфейсе нет очевидной точки входа в сценарий продавца.

Пользователь, который хочет стать продавцом или управлять своими предложениями, не должен угадывать, где начинается seller flow.

**Желаемое направление:** определить понятный seller entry point и связать его с целостным seller setup / seller management journey.

---

### UX-007 — В Offer отсутствует пользовательское media-представление

**Статус:** OPEN  
**Область:** Offer card / Seller Input / Media  
**Тип:** UX-проблема + обнаруженный product/domain gap

Сейчас покупательская выдача не предусматривает фото товара, а seller flow не предусматривает добавление медиа к Offer. Для одного Offer потенциально нужны несколько фотографий и, при необходимости, видео.

Это не следует смешивать с будущими AI-сценариями `фото/видео -> распознавание -> Change Set`: там медиа является способом ввода данных, здесь медиа является частью самого предложения, которое видит покупатель.

**Желаемое направление UX:**
- в карточках Search / Discovery / «Для вас» предусмотреть устойчивое место для основного изображения и понятный fallback, если медиа нет;
- в seller create/edit Offer flow предусмотреть добавление, просмотр и управление несколькими фото и видео;
- продумать порядок медиа и выбор cover/primary asset;
- не требовать от П2 повторно загружать одни и те же данные при изменении цены/комментария, если медиа не менялось.

**Архитектурное замечание:** текущая модель Offer не имеет media relation, а отдельной media-сущности/модуля в активной схеме нет. Это нужно закрывать отдельным функциональным slice, а не маскировать только визуальными placeholders в UX1.

**Не решать внутри UX1 без отдельного Slice Contract:** storage provider, upload API, ограничения форматов/размеров, lifecycle, удаление, безопасность, модерация, обработка видео и физическое хранение файлов.

---

### UX-008 — Слишком низкая информационная плотность, нужен marketplace card layout

**Статус:** OPEN  
**Область:** Buyer UI / Layout / Offer cards

Сейчас на основных экранах слишком много пустого пространства и слишком мало полезного контента в первом экране. Текущая композиция ближе к лендингу, чем к рабочему интерфейсу поиска и просмотра предложений.

**Желаемое направление:** перейти к привычной marketplace-модели интерфейса: компактный app shell, заметный поиск, плотная выдача карточками, меньше декоративных пустот и больше полезной информации в viewport.

Ориентир по паттерну — крупные маркетплейсы вроде Ozon, но не копирование визуального стиля или конкретной сетки.

Для Buyer UI предусмотреть:
- Search / Nearby / будущий «Для вас» как card-first выдачу;
- адаптивную сетку/ленту карточек вместо крупных текстовых intro-блоков рядом с пустым пространством;
- карточка должна иметь устойчивую структуру под Offer media, Product, цену, единицу, расстояние/актуальность, продавца/точку и доступные buyer actions;
- на mobile карточки остаются легко сканируемыми и не превращаются в перегруженные мини-страницы;
- на desktop пространство используется для большей плотности карточек, а не для искусственного увеличения отступов.

**Граница с Media:** UX1 может определить card layout и зарезервировать media-slot/fallback. Реальные Offer photos/video появляются только в отдельном M1/M2 slice.

## Примечание по UX1

`UX1` должен быть отдельным небольшим vertical slice перед S14. До утверждения его Slice Contract этот backlog не является разрешением менять код.

`UX-007` требует отдельного product/media решения. UX1 может определить визуальные места и поведение empty/fallback states только если это явно войдёт в его Slice Contract, но реальную media-модель, upload/storage и lifecycle следует реализовывать отдельным vertical slice.

`UX-008` является одним из основных кандидатов на UX1: цель не визуальный редизайн ради редизайна, а повышение информационной плотности и переход к card-first marketplace layout без изменения закрытых бизнес-contracts.
