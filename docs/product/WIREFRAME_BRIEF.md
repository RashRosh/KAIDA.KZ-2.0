# Бриф на вайрфреймы KAIDA.KZ

> Это рабочий бриф для следующего захода в вайрфреймы (Claude Design или руками) — не Slice Contract и не
> замена `EXECUTION_PLAN.md`. Цель — закрыть список экранов и состояний целиком, чтобы разработка велась по
> понятной картинке, а не достраивалась вслепую поверх текущего UI. Источники: `SELLER_JOURNEY.md`,
> `BUYER_JOURNEY.md`, `FEATURE_MAP.md`, `EXECUTION_PLAN.md`, и разбор экранов 1a–1l из первого захода
> (`KAIDA Wireframes.dc.html`).

> **Инструкции на третий заход вынесены в отдельный документ:** `docs/product/WIREFRAME_TASK_PASS3.md`.
> Он отменяет tier-инструкции этого брифа для следующего захода дизайнера (что удалить, объединить, переработать
> и добавить). Результат этого захода и обязательные правки — `docs/product/WIREFRAME_PASS3_REVIEW.md`.
> Настоящий файл сохраняется как история двух предыдущих заходов и опись 42 кадров.
> Поэтому более поздние формулировки ниже об authoritative-статусе второго захода являются историей решения,
> а не текущей командой реализации. Актуальная authority lifecycle — `PROJECT_RULES.md` §18.1.

## Статус после второго захода (2026-09-22)

Второй заход, который готовил этот бриф, состоялся: bundled-артефакт (42 экрана, идентификаторы `1a`–`5e`,
Tier 0–4) — https://claude.ai/artifact/5KhjaPcLntxAY4Mk2BC9zF. Сам артефакт фиксирует свой охват дословно:
«Мобильный набор по брифу закрыт: 42 экрана, Tier 0–4… Осталась desktop-раскладка под UX1A/UX2A.»

Изначально это был **advisory-материал** того же типа, что и внешние UX references (`PROJECT_RULES.md` §18,
`UX_REFERENCE_INDEX.md`). Разбор по `KEEP/ADAPT/REJECT/GAP` — в `UX_REFERENCE_INDEX.md`, раздел «Follow-up
spot-check (2026-09-22)».

**Обновление статуса, 2026-09-22 (позже в тот же день):** Product Owner признал текущий продуктовый UX
неудовлетворительным и отдельным решением поднял именно этот артефакт до **authoritative текущей UX-цели**
presentation-слоя — см. `PROJECT_RULES.md` §18.1 и обновлённый раздел `UX_REFERENCE_INDEX.md`. Он по-прежнему не
подменяет собой Slice Contract и не переписывает `EXECUTION_PLAN.md` напрямую (порядок работ и business-приоритеты
не меняются этим решением), но перестаёт быть просто advisory: уже реализованные экраны, которые он покрывает,
приводятся к нему как к целевому UI через Slice Contract соответствующей области; ещё не реализованные —
проектируются по нему напрямую. Экраны, требующие новой business-механики (не только presentation), а не только
переоформления — по-прежнему проходят через explicit Product Owner подтверждение до реализации.

**Обязательное дополнение Product Owner, 2026-09-22:** KAIDA полностью поддерживает русский и казахский языки.
Отсутствие language switch в отдельных кадрах артефакта не означает, что он optional: новый shared app shell
обязан содержать switch русского/казахского языка: `Русский / Қазақша` на desktop и прямой `РУ / ҚАЗ` в один tap
на mobile без промежуточного меню. Каждый core flow прототипируется и принимается в обеих локалях. Все
KAIDA-owned user-facing strings, system states, validation/errors, accessibility copy и catalog-owned display data
имеют версии `ru` и `kk`. Для seller-authored names/addresses/comments localization Slice Contract обязан выбрать
единую модель перевода и fallback; отсутствие решения нельзя молча подменять разным поведением на разных экранах.

Что это меняет по тирам ниже:

- **Tier 0** — закрыт: `4d`–`4i` явно дорисовывают ровно то, чего не хватало у `1a`/`1b`/`1c`/`1d`+`1g`/`1e`/`1l`
  (невалидная цена, ссылка на карту, ревью AI-черновика, предложение без канала связи, переход из пустого
  результата, лимит продвижения исчерпан). Loading/offline/server-error как общее системное состояние
  тоже нарисованы (`4a`–`4c`) — этого не было в списке тиров вообще, см. новое наблюдение `UX-OBS-002`
  в `docs/UX_BACKLOG.md`.
- **Tier 1** — отрисован (`2a`–`2i`, `3a`–`3c`, `3e`–`3g`): кабинет продавца, точки, Change Set confirm,
  Offer Workspace, свежесть, «Для вас», Избранное. Использовать как reference при подготовке
  Slice Contract для #27 и последующих, **когда** каждый из них реально стартует по очереди
  `EXECUTION_PLAN.md` — готовый экран не заменяет сам Slice Contract.
- **Tier 2** — отрисован (Search Sorting `3d`, Фото M1 `3e`, «Для вас» `3f`, Избранное `3g`) — та же оговорка.
- **Tier 3** — отрисован (Уведомления `5a`, Тариф `5b`, Продвижение+Оплата `5c`, Аналитика drill-down `5d`,
  плюс аналитика-сводка `1j`) — это S23/S25–S29/S33, **После MVP** по `FEATURE_MAP.md` и вне текущей
  COMMITTED очереди `EXECUTION_PLAN.md`. Готовый экран — не approval на старт: очередь не меняется без
  отдельного Product Owner decision (`PROJECT_RULES.md` §20).
- **Tier 4** — подтверждён как места-заглушки (`5e`), без детализации — совпадает с текущим статусом
  INSERTION CANDIDATES, действий не требует.

## Как читать приоритет

- **Tier 0** — уже нарисовано (1a–1l), нужно только дорисовать недостающие состояния.
- **Tier 1** — экраны того, что уже живёт в продакшене, но плохо спроектировано (то, из-за чего был затеян
  этот заход). Самый высокий приоритет: без этого нечего заменять.
- **Tier 2** — экраны NEXT/COMMITTED работы (`EXECUTION_PLAN.md`).
- **Tier 3** — экраны PLANNED-capabilities После MVP (`FEATURE_MAP.md`), часть уже частично покрыта 1j/1k/1l.
- **Tier 4** — insertion candidates / явно отложенные. Не рисовать детально, но обозначить место-заглушку.

## Tier 1 — экраны того, что уже живёт, но требует редизайна

**Статус размещения (2026-09-22, подтверждено Product Owner):** кроме «Результаты Рядом» (Issue #34, COMMITTED) и
`/login` (код не меняется), редизайн всех пунктов ниже (хаб, карточки точек, выбор точки при 2+, управление
предложением, контакты, Change Set confirm) официально входит в scope Issue #27 (Seller Offer Workspace, NEXT) —
это решение зафиксировано, не отдельный `UNPLACED GAP`. Slice Contract для #27 при подготовке должен явно
перечислить эти пять экранов как часть своего scope со ссылкой на этот бриф, а не заново решать вопрос
размещения.

### Кабинет продавца, стартовый экран (hub)
- **Назначение:** первое, что видит вошедший продавец — не форма на полэкрана, а компактный обзор: сколько
  точек, сколько активных предложений, что требует внимания.
- **Состояния:** 0 точек (первый запуск) · есть точки, но 0 предложений · есть и то, и другое.
- **Основа:** прямая претензия из manual acceptance этой сессии («первое, что нужно продавцу — управлять
  товарами, а не полэкрана данных точки»); `SELLER_JOURNEY.md` раздел «Первый раз в кабинете продавца».

### Список торговых точек (карточки)
- **Назначение:** отдельно от создания товара — посмотреть все точки, поправить имя/адрес одной, не трогая гео.
- **Состояния:** одна точка · несколько точек · редактирование identity без геолокации.
- **Основа:** `SELLER_JOURNEY.md` раздел «Несколько торговых точек»; уже реализовано в коде
  (`SellerTradingPoints.tsx`) — нужен именно редизайн, не новая логика.

### Выбор точки при 2+ точках (для одного/пакетного товара)
- **Назначение:** явный шаг выбора, когда точек несколько — не молчаливая привязка к первой.
- **Состояния:** список точек с возможностью выбрать одну · выбор внутри пакетного ввода нескольких товаров.
- **Основа:** `SELLER_JOURNEY.md`, уже реализовано (`SellerChangeSetCreate.tsx`/`SellerBatchChangeSetCreate.tsx`)
  как часть закрытого #36.

### Управление существующим предложением
- **Назначение:** не создание нового, а правка цены/комментария или выключение уже опубликованного Offer.
- **Состояния:** активное предложение · выключенное · просроченное (не подтверждено вовремя).
- **Основа:** `SellerOfferManagement.tsx`, closed S5.

### Контакты продавца
- **Назначение:** что из телефона/WhatsApp/Telegram показывать покупателю; можно убрать канал.
- **Состояния:** ни одного канала не выбрано (предупреждение) · один/несколько выбрано.
- **Основа:** `SellerContactSettings.tsx`, closed.

### Явный экран подтверждения Change Set (одиночный и пакетный)
- **Назначение:** финальный ревью-экран перед публикацией — не одна кнопка «Подтвердить все три» без диффа.
- **Состояния:** одно изменение · несколько изменений в одном Change Set · ошибка подтверждения.
- **Основа:** `/seller/change-sets/[id]`, closed S4/S12; принцип «покупатель ничего не видит без подтверждения».

### Результаты «Рядом» после согласия + пустой результат
- **Назначение:** сам список после того, как разрешили геолокацию (сейчас нарисован только экран запроса).
- **Состояния:** есть результаты · пусто рядом.
- **Основа:** `/nearby`, closed S11; в этой сессии уже убирали дублирующий intro-блок в `NearbyFeed.tsx`.

### `/login` напрямую
- **Назначение:** прямой заход по ссылке, не через контекстный триггер.
- **Основа:** уже реализовано, нужен вайрфрейм для полноты набора.

## Tier 2 — экраны NEXT/COMMITTED работы

### Seller Offer Workspace (Issue #27)
- **Назначение:** следующий этап после hub — сама рабочая поверхность управления предложениями продавца.
- **Основа:** `EXECUTION_PLAN.md`, NEXT. Contract ещё не согласован — вайрфрейм может опередить и помочь
  сформировать Slice Contract, но не заменяет его согласование.

### Напоминание о свежести (баннер/пуш) + просмотр всех «протухающих»
- **Назначение:** сам триггер, который приводит на экран 1k, и bulk-подтверждение сразу нескольких позиций.
- **Состояния:** мягкое напоминание (первый порог) · настойчивое (последний порог перед скрытием).
- **Основа:** Issue #31/32, COMMITTED stage 1–2. Идея bulk-confirm из 1k — сильный кандидат в contract.

### Search Sorting UI
- **Назначение:** явные переключатели сортировки в выдаче (свежесть/близость, затем цена) — уже частично в 1d.
- **Основа:** Issue #12, COMMITTED stage 4–5.

### Загрузка фото товара (M1)
- **Назначение:** шаг в форме создания/правки предложения — сейчас в 1a вообще не заложен.
- **Состояния:** без фото · с фото · загрузка в процессе · ошибка загрузки.
- **Основа:** `FEATURE_MAP.md`, COMMITTED stage 6.

### «Для вас» — лента по избранному
- **Назначение:** отдельная лента по явно добавленным в избранное товарам, в отличие от geo-based «Рядом».
- **Состояния:** есть избранные товары с результатами · есть избранное, но пусто · избранное пусто.
- **Основа:** S14, `FEATURE_MAP.md`, COMMITTED stage 7. Отсутствует полностью — сам файл 1a–1l признаёт это
  дырой в своей финальной подсказке.

### Избранное (список, удалить товар)
- **Назначение:** покупатель видит, что отметил, может снять.
- **Основа:** S13 (closed, write-side уже есть), read/manage-side для S14.
