# Диагностика багов в KAIDA

Дисциплина для сложных багов. Фазы пропускаются только с явным обоснованием. Скилл не отменяет процесс проекта: исправление кода идёт как Development по `docs/PROJECT_RULES.md` (§2, §6), а новый failure классифицируется по §8.

## Скрывай секреты

В командах, выводе и артефактах замени каждый секрет на `<REDACTED>`: ключи OTP/SMS, VAPID, пароли БД, cookies и заголовки авторизации. Собирай проверки на переменных окружения, чтобы секрет оставался в окружении, а не в показанном тексте. Из логов цитируй только строки с сигналом.

## Фаза 1: петля обратной связи

**В этом весь скилл.** Если есть быстрый сигнал pass/fail, который краснеет именно на этом баге, причина найдётся. Если нет, чтение кода не спасёт. Сюда стоит вложить больше всего усилий.

### Способы, примерно по порядку

1. **Падающий тест** на том seam, который достаёт до бага: unit (`tests/unit`), integration на тестовой БД (`tests/integration`), E2E (`tests/e2e`, Playwright).
2. **curl / HTTP-скрипт** против запущенного dev-сервера.
3. **CLI-вызов** (`pnpm tsx …`) с фикстурой и сравнением вывода с эталоном.
4. **Headless-браузер** (Playwright), который проходит сценарий и проверяет DOM, console, network.
5. **Повтор записанного запроса**: сохранить реальный payload и прогнать его через нужный код изолированно.
6. **Одноразовый harness**: минимальная часть системы, которая одним вызовом проходит путь бага.
7. **Property / fuzz-петля**, если баг «иногда неправильный результат»: 1000 случайных входов.
8. **Bisection**, если баг появился между двумя известными состояниями (checkpoint tags проекта как раз для этого): автоматизировать «собрать, проверить» и запустить `git bisect run`.
9. **Дифференциальная петля**: один вход через старую и новую версию, сравнить выводы.
10. **Человек в петле** — последний вариант. PO нетехнический: попроси у него по-русски шаги воспроизведения, скриншот или запись экрана со временем, устройство и браузер. Не проси его запускать команды.

### Подтяни петлю

- Быстрее: кэшировать подготовку, сузить набор тестов (`vitest run <файл>`, `playwright test <spec>`).
- Резче: проверять конкретный симптом, а не «не упало».
- Детерминированнее: зафиксировать время, seed, изолировать сеть.

30-секундная нестабильная петля почти бесполезна, 2-секундная детерминированная — суперсила.

### Недетерминированные баги

Цель — не чистое воспроизведение, а **выше частота**. Повтори 100 раз, распараллель, добавь нагрузку. Баг с частотой 50% отлаживается, 1% нет. Если подозрение на race или teardown тестовой БД, смотри §8 про общий deterministic harness.

### Если петлю построить нельзя

Остановись и скажи прямо, что пробовал. Запиши это в `docs/agents/CURRENT_STATE.md`. Нужен доступ к окружению, где баг воспроизводится, или артефакт (HAR, лог, запись экрана). Без петли к гипотезам не переходить.

### Критерий готовности

Есть **одна команда**, которую ты уже запустил хотя бы раз (покажи вызов и вывод без секретов), и она:

- [ ] проходит реальный путь бага и проверяет **точный симптом** пользователя;
- [ ] даёт один и тот же вердикт каждый раз (или стабильно высокую частоту для flaky);
- [ ] выполняется за секунды;
- [ ] запускается без человека.

Если ловишь себя на чтении кода ради теории до появления этой команды — стоп.

## Фаза 2: воспроизвести, классифицировать, минимизировать

Запусти петлю и убедись, что:

- [ ] она даёт именно ту ошибку, которую описал пользователь, а не соседнюю;
- [ ] ошибка воспроизводится на нескольких прогонах;
- [ ] точный симптом записан, чтобы потом проверить исправление.

**Классифицируй по §8** до исправления: `PRODUCT DEFECT`, `STALE REGRESSION ASSUMPTION`, `TEST IMPLEMENTATION / TEST HARNESS DEFECT` или `ENVIRONMENT / PROCEDURE / TOOLING`. Production не меняется ради устаревшего assertion, тест не ослабляется ради зелёного CI.

Затем сократи сценарий до минимального, который ещё краснеет: убирай входы, вызовы, данные и шаги по одному, перезапуская петлю. Готово, когда каждый оставшийся элемент необходим.

## Фаза 3: гипотезы

Сформулируй **3–5 ранжированных гипотез** до проверки любой из них. Каждая проверяема:

> «Если причина в X, то изменение Y уберёт баг, а изменение Z усилит его».

Запиши список в `CURRENT_STATE.md` или в описание PR, чтобы следующий агент и KAIDA Controller видели ход мысли. PO технические гипотезы не ранжирует, его не ждать.

## Фаза 4: инструментирование

Каждая проба проверяет конкретное предсказание. **Меняй одну переменную за раз.**

1. Отладчик или REPL, если доступны.
2. Точечные логи на границах, которые различают гипотезы.
3. Никогда «залогировать всё и грепать».

**Помечай каждый отладочный лог** уникальным префиксом, например `[DEBUG-a4f2]`, чтобы потом убрать их одним поиском.

**Производительность**: логи обычно не помогают. Сначала базовое измерение (тайминг, `performance.now()`, `EXPLAIN ANALYZE` для запросов PostgreSQL), потом bisect. Сначала измерить, потом чинить.

## Фаза 5: исправление и регрессионный тест

Регрессионный тест пишется **до исправления**, если есть **правильный seam**: тот, на котором тест воспроизводит реальный паттерн бага, как он возникает в месте вызова. Если доступен только слишком мелкий seam, тест даст ложную уверенность. **Отсутствие правильного seam — само по себе находка**, её надо записать.

Если seam есть:

1. Преврати минимальный сценарий в падающий тест.
2. Убедись, что он падает. Если красный получен правкой кода или фикстуры, сравни с чистой копией.
3. Исправь минимальным diff (§6), без попутного рефакторинга.
4. Убедись, что тест проходит.
5. Перезапусти петлю из фазы 1 на исходном, не сокращённом сценарии.

## Фаза 6: уборка

Перед тем как сказать «готово»:

- [ ] исходный сценарий больше не воспроизводится;
- [ ] регрессионный тест проходит (или отсутствие seam записано);
- [ ] все `[DEBUG-…]` удалены (проверено поиском по префиксу);
- [ ] одноразовые harness и прототипы удалены;
- [ ] подтвердившаяся гипотеза записана в описание PR, чтобы следующий диагност её знал.

Commit, push и PR — только по прямому поручению PO (`AGENTS.md`).
