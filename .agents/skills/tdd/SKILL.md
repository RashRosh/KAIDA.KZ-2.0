# TDD в KAIDA

Цикл red → green и правила, по которым тесты получаются полезными. Скилл не меняет процесс проекта: реализацию разрешают только прямая команда PO и утверждённый Slice Contract, а уровни verification выбираются по риску (`docs/PROJECT_RULES.md` §5–§7).

## Что такое хороший тест

Тест проверяет поведение через публичный интерфейс, а не детали реализации. Код может полностью поменяться, тест не должен. Хороший тест читается как пункт acceptance: «покупатель видит предложения продавцов рядом» говорит, какая возможность существует, и переживает рефакторинг.

Примеры: [tests.md](tests.md). Когда мокать: [mocking.md](mocking.md).

## Seams: где живут тесты

**Seam** — публичная граница, на которой наблюдается поведение без залезания внутрь: route handler / server action, функция модуля, экран в браузере. Тесты стоят на seams, а не на внутренностях.

**Seams берутся из Slice Contract, а не у PO.** PO нетехнический, его не спрашивают «какие seams тестировать». Порядок:

1. Каждый пункт acceptance контракта → какой seam его доказывает и каким уровнем (unit / integration / E2E по §7).
2. Каждый реальный risk flag (§5) → какой seam его закрывает. Отсутствующие риски не тестируются «на всякий случай».
3. Перед первым тестом запиши список seams с одной строкой «что ловит / что пропускает» в `docs/agents/CURRENT_STATE.md` (`Next action`) или в описание PR, чтобы KAIDA Controller мог сверить.
4. Если контракт не позволяет однозначно выбрать seam, это вопрос к контракту: зафиксируй его в `CURRENT_STATE.md` и не расширяй scope молча.

Уровни в репозитории:

- unit — `tests/unit/**/*.test.ts`, `pnpm test:unit`;
- integration — `tests/integration/**/*.test.ts` на реальной тестовой БД, `pnpm db:test:prepare`, затем `pnpm test:integration`;
- E2E — `tests/e2e/*.spec.ts`, Playwright на production build (`pnpm build`, затем `pnpm test:e2e`).

## Анти-паттерны

- **Привязка к реализации**: мок внутренних модулей, тест приватных функций, проверка в обход интерфейса (SQL-запрос вместо чтения через тот же API). Признак: тест ломается при рефакторинге, хотя поведение не изменилось.
- **Тавтология**: ожидаемое значение вычисляется так же, как в коде (`expect(add(a, b)).toBe(a + b)`), поэтому тест не может не пройти. Ожидание берётся из независимого источника: литерал, разобранный пример, формулировка контракта.
- **Горизонтальная нарезка**: сначала все тесты, потом весь код. Такие тесты проверяют воображаемое поведение. Работай вертикально: один тест → минимальный код → следующий тест.
- **Ослабление теста ради зелёного CI** запрещено (§8). Новый failure сначала классифицируется по §8.

## Правила цикла

- **Red до green.** Сначала падающий тест, и убедись, что он падает по ожидаемой причине. Потом ровно столько кода, чтобы он прошёл. Никаких спекулятивных возможностей сверх контракта.
- **Один seam, один тест, одна минимальная реализация за цикл.**
- **Рефакторинг не входит в цикл.** Минимальный diff, соседние области не трогать (§6). Если рефакторинг нужен, это отдельное решение, а не часть slice.
- **Финальное доказательство** — один зелёный full branch CI на финальном executable head (§6–§7), а не набор локальных прогонов.
